# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Commands

```sh
# Запуск бота локально
.venv\Scripts\python -m src.main

# Все юнит-тесты
.venv\Scripts\python -m unittest discover tests

# Один тест-файл
.venv\Scripts\python -m unittest tests.test_classifier

# Установка зависимостей
.venv\Scripts\pip install -r requirements.txt
```

## Architecture

Telegram-бот с AI-агентом для менеджера norwik.ru: принимает текст/голос → агент ищет товар в почте и на сайте → отвечает ценами и контактами поставщиков.

### Поток данных

```
Telegram (aiogram) → AuthMiddleware → handlers.py
                                           ↓
                                    Orchestrator (Claude API manual loop)
                                     ├── ToolExecutor.execute(name, input)
                                     │    ├── MailClient (IMAP, sync via to_thread)
                                     │    └── NorwikClient (httpx, sync via to_thread)
                                     └── on_tool callback → edit_text в Telegram
```

### Ключевые детали реализации

**Оркестратор** (`src/agent/orchestrator.py`) — ручной agentic loop, не tool runner. Причина: нужна обработка `stop_reason == "pause_turn"` для серверного `web_search` (Anthropic-hosted). Цикл продолжается до `end_turn` или отсутствия `tool_uses`. Лимит `MAX_ITERATIONS = 30`. Принимает `on_tool` callback — вызывается перед каждым инструментом для обновления статуса в Telegram.

**Инструменты** (`src/agent/tools.py`) — 6 кастомных + 1 серверный:
- `search_emails` / `read_attachment` / `get_email_contacts` — IMAP
- `search_norwik` / `get_norwik_product` — парсинг norwik.ru
- `get_price_history` — «когда меняли цены»: даты из 1С (`by-tm`), источник цены из
  журнала `price_writes`; форматирует ответ код (`src/price_tool/history.py`), не модель
- `web_search` — `{"type": "web_search_20260209"}`, выполняется на стороне Anthropic (случай А: поставщик не найден)

**IMAP-клиент** (`src/email_tool/client.py`) — синхронный, вызывается через `asyncio.to_thread`. Строго read-only: `select(readonly=True)`, только `BODY.PEEK` (не ставит флаг `\Seen`). Операции записи не реализованы намеренно.

**Классификатор писем** (`src/email_tool/classifier.py`) — определяет тип письма (прайс/остатки) в порядке: тема → имя вложения → названия листов Excel. Парсит подпись для извлечения имени и телефона менеджера поставщика.

**NorwikClient** (`src/website_tool/norwik.py`) — поиск через `/search?query=`, цена из `itemprop="price" content="..."`. Один товар имеет несколько `<a href="item/...">` на странице (картинка + текст); выбирается лучший title через `_title_score()` (предпочтение кириллице и тексту с пробелами).

**Режимы работы** (`src/price_tool/modes.py`, §5.2) — «товары+цены» (умолчание), «товары»,
«цены»; команда `/mode`, значение в `app_settings`. Режим задаёт не только этапы, но и
СОСТАВ ЗАМЕЧАНИЙ: `propose_prices` принимает два массива — `warnings` (цены) и
`item_warnings` (справочник), и замечания, которые формирует код, классифицируются в
`_render`, а не моделью. Всегда видны независимо от режима: «1С не отдала N поз.»,
«категория не в списке», потеря загруженной марки — это состояние системы.

**Правка справочника** (§19 спеки) — только контракт, кода нет: ни один эндпоинт в 1С не
реализован. Пять запросов ТЗ сведены к трём чтениям и одной записи `set-items`; перенос в
«снятые с производства» — это `update_item` со сменой `parent_ref`, отдельной операции нет.

**Форма 1С для модели** (`specs/1c-model-form.md`, `specs/1c/agent-commands.bsl`,
`specs/1c/set-model-state.bsl`) — BSL выложен и **проверен живьём**
(`tests/integration_model_state.py`, запускать `python -m tests.integration_model_state`;
пишет в зеркало под номерами 901/902 и вычищает за собой). **Провайдера на стороне бота
нет**: команды
формы никуда не поедут, пока он не появится. Обе стрелки идут ОТ агента, потому что
обработчик HTTP-сервиса работает в своём сеансе и до открытой формы не дотягивается —
отсюда зеркало в 1С, и обойти его нечем. Снимок приходит целиком, но **применяется
разницей**: иначе счётчик `ии_МодельАгентаВерсияСостояния` рос бы на каждом обороте и форма
перерисовывалась бы под руками у админа каждые 5 секунд. У команды ТРИ состояния, а не два
(`ждёт` → `принята` → `выполнена`/`отклонена`): колесико ожидания обязано гаснуть по
результату, а не по факту, что агент команду забрал. `Создана` штампует СЕРВЕР 1С — часы
рабочей станции дали бы одному админу вечный выигрыш в правиле «кто первый». Команды лежат
в РЕГИСТРЕ, а не в справочнике: это очередь, она обязана пустеть, а у записи регистра нет
ни ссылки, ни пометки удаления — уборка это снятие строки. Идентификатор поэтому GUID,
сделанный при постановке: своего у записи регистра нет, а счётчик потребовал бы блокировки.
Переиспользовать идентификаторы нельзя — запоздавший ответ по закрытой команде попал бы в
новую.

**Крупный прайс** (`BIG_PRICE_ROWS`, §6.10) — от 5 000 строк `read_price_file` не отдаёт
таблицу, а требует спросить админа «обработать или пропустить» с оценкой в токенах.
`manual` ≠ «Отложить»: в `deferred_tasks` не попадает, считается обработанным, бот выходит
из режима.

**Ключ кешей по прайсу — хеш СОДЕРЖИМОГО** (`_file_key`), не сигнатура: сигнатура считается
по скелету файла, и прайс следующего месяца имеет ту же — решение и раскладка молча
перешли бы на новый файл.

**Повторный прайс** — два кеша с разным смыслом: `_PARSED` в `parser.py` снимает CPU
(разбор шёл дважды за вызов) и обязан отдавать КОПИЮ, потому что в строки вставляются
маркеры картинок; `price_layout` снимает токены — раскладка брендов по сигнатуре файла,
чтобы не повторять разведку. Оба чистятся, когда от того же поставщика пришёл прайс новее.

**Стоимость контекста.** Цикл ручной: каждый вызов инструмента — отдельный
`messages.create` со ВСЕЙ историей. Поэтому три вещи обязательны и ломать их нельзя:
`_cached()` в `orchestrator.py` ставит точку кеширования (`CACHE`, TTL 1 час) на последний блок (в сохраняемую
историю `cache_control` не попадает); `_prune_file_dumps` оставляет по одной свежей
выгрузке каждого вида (лист прайса и номенклатура) — прочие заменяет заглушкой;
`get_1c_nomenclature` принимает `collection_ref` и в режиме коллекций обязан его получать.
На боевом прайсе история была 197 тыс. токенов, шаг по коллекции стоил ~1,2 млн входных.
Плюс: предложение админу шлёт обработчик из `last_summary` — модель его НЕ переписывает
(было ~2 000 выходных токенов на шаг по цене выхода), а `handle_turn(base_tools=False)`
не подмешивает менеджерские инструменты в режим цен.

**СТАРЫЙ ПРАЙСОВЫЙ ПОТОК ОТКЛЮЧЁН ОТ ТГ** на время обкатки модели: `pricing_router` не
включён в диспетчер (`main.py`), его команды убраны из меню и справки. Код цел, вернуть —
раскомментировать одну строку. Оба потока реагировали бы на один присланный файл.

**Задачи формирует агент** (`src/model/task_builder.py`, §6.1) — читает прайс, сопоставляет
бренды с марками 1С и заводит задачи на РЕАЛЬНЫЕ пары (марка, коллекция). **Выгрузки
номенклатуры 1С у него пока НЕТ**, и промпт обязан это называть: иначе он напишет «завести
12 недостающих позиций», которых не считал. Пустой ответ или сбой — откат на заглушку с
уведомлением: молчаливо пустой список админ прочтёт как «разбирать нечего». Уникальность
(адрес, вид) держится в самом инструменте — модель приходит к одной задаче дважды.

**Артикул нормализуется БЕЗ разделителей** (`refs.norm_article`): «LE-263», «LE 263» и
«le263» — один артикул. Общая `scope.normalize` для этого не годится, она заменяет пунктуацию
пробелом, и «le 263» не совпало бы с «le263».

**Цикл модели** (`src/bot/model_loop.py`, `src/model/service.py`, §9) — обработчики ТГ
**не действуют сами**: кладут команду в очередь и будят цикл (`loop.wake()`). Исключение
одно — приём файла: это поступление данных, а не команда, и таскать содержимое через
очередь незачем. Занятость считается ОТДЕЛЬНО ДЛЯ КАЖДОГО инициатора (`busy_for(actor)`):
свой захват админа не блокирует, общего набора «занятых» не существует. Истёкшие захваты
снимаются ПЕРВЫМ делом на обороте — иначе заброшенный прайс до конца оборота отклонял бы
чужие команды. **Выполнение задачи — ЗАГЛУШКА** (`_execute`), в 1С не пишется ничего;
настоящее выполнение подменит ровно этот метод.

**Захват прайса и маркер поколения** (`src/model/locks.py`, §5 модели) — захватывается прайс
ЦЕЛИКОМ, отнять чужой живой захват нельзя. **Аренда 10 минут считается от признаков жизни, а
не от старта**: работающий прогон продлевает её на каждой итерации, поэтому тяжёлая живая
задача захват не теряет, а зависшая теряет. После выполнения задачи захват держится ещё
минуту. Снятие захвата по таймеру **работу НЕ останавливает** — для этого есть отмена
прогона, а от зомби-записи защищает `valid_for`: **проверка обязана стоять непосредственно
перед записью в 1С**, а не только перед сменой статуса, потому что необратима именно запись.
`generation` при снятии захвата НЕ обнуляется — иначе следующий захват совпал бы с номером
отменённого прогона. Время в чистых функциях передаётся явно: иначе тест на истечение аренды
пришлось бы писать через `sleep`.

**Очередь команд** (`src/model/commands.py`, `src/storage/command_queue.py`, §7) — в базе, а
не в памяти: команда, присланная перед остановкой процесса, должна дождаться подъёма.
Схлопываются только присваивания (статус, описание) и только НЕ взятые: перезаписав взятую,
подменили бы то, что исполняется. **«Кто первый» действует на ВСЕ команды** (решение админа
14.09.2026) и считается по времени создания НА СТОРОНЕ ВИЗУАЛА — порядок обхода провайдеров
сделал бы один визуал главнее другого. Взятие помечает, а не удаляет; при старте
`requeue_stale` возвращает взятое (живых взятых быть не может, агент один).

**Модель работы с прайсами** (`src/model/`, `src/storage/model_store.py`,
`specs/agent-workflow-model.md`) — строится рядом с действующим прайсовым потоком и пока на
него НЕ влияет: команд, меняющих состояние, ещё нет. Домен чистый (ни базы, ни бота).
Ключевое: **пустой `Ref` не совпадает ни с чем, включая пустой** — «неизвестно» не равно
«неизвестно»; совпадение адресов идёт по ЛЮБОМУ непустому идентификатору, но марка обязана
совпасть (артикул «A001» бывает у двух поставщиков). `relink` **пересчитывает ссылки на
самый свежий прайс от нуля**, а не правит по одной: инкрементальная правка обязана угадать
все затронутые записи, пересчёт не может их пропустить. `replace_tasks` не переиспользует
старые `id` — «выполни задачу 7» после пересборки должна не найти задачу, а не выполнить
другую под тем же номером. **Уборка сирот обязана объединять пути из ВСЕХ хранилищ**
(`main.py`): забыть модель — значит стереть файл живого прайса, а прайс без файла
существовать не может.

**Справочники поставщиков** (`src/storage/suppliers.py`, `specs/agent-workflow-model.md` §2) —
три уровня: поставщик → сигнатура формата → файл прайса. **UNIQUE по ПАРЕ (поставщик,
сигнатура)**, а не по хешу: скелеты разных поставщиков могут совпасть, и тогда это две записи
у двух владельцев — поэтому `find_signatures` возвращает СПИСОК, и брать первого нельзя.
Поставщик ищется по нормализованному имени (`scope.normalize`), `add_supplier` идемпотентен.
Непустого поставщика удалять нельзя — для дублей есть `merge_suppliers`, он переносит
сигнатуры с файлами и уничтожает источник; совпавшие сигнатуры вливаются, а не дублируются.
Команды — `src/bot/catalog_handlers.py`, отдельный роутер. **Номера в командах сквозные по
полному списку**: фильтр прячет строки, но не сдвигает номера, иначе `/signature_delete 2`
удалял бы разное в разных видах. Файлы с диска справочник не трогает — это дело
`price_files.sweep`.

**Закрытие прогона — за админом** (§9.9) — `_finish_run` без `confirmed=True` НЕ закрывает
прогон: печатает сводку и спрашивает «Закончить работу с этим прайсом?» с одной кнопкой
«Да». Разобрать план и закончить работу — разные события: у админа остаются задачи по тому
же файлу, а закрытие стирает файл и историю, и текст уходит менеджерскому агенту, который
про 1С ничего не умеет. Флаг — `active_price.awaiting_close`, снимается любой новой работой
(`_run`), поэтому вопрос звучит заново. Сводка печатается ОДИН раз — с вопросом. Новый файл
вместо кнопки закрывает прогон сам (`quiet=True`); прайс В РАБОТЕ так не вытесняется.

**Поиск по всей номенклатуре** (`find_1c_items`, `specs/1c/find-items.bsl`, §19.11) —
проверка «нет ли товара в снятых» по выгрузке ТМ видит ТОЛЬКО СВОЮ МАРКУ, а дубль как раз и
возникает, когда товар заведён под другой. Эндпоинт ищет по всей базе, невыгружаемые
включены ПО УМОЛЧАНИЮ (наоборот, чем в `by-tm` — он написан ради снятых), поиск вхождением.
**Зовётся ПАЧКОЙ — `articles` списком, один раз на коллекцию.** Цену определяет число
вызовов, а не объём: круг ручного цикла несёт всю историю и стоит $0.097 (замер на прогоне
Most Floor), сам ответ — $0.0002, разница в 400 раз. Поштучная проверка 53 позиций стоила
бы $5.13 против $0.77 пачкой. **Требует выкладки BSL в 1С.**

**Непомеченные ТМ видны агенту** (§19.10) — `get_selling_tm` отдаёт все марки с признаком
`selling`. Марку заводят раньше, чем помечают к выгрузке, и в этом промежутке под неё уже
создают товары; раньше агент её не видел и писал «заведите» про заведённую. В план по
умолчанию идут только помеченные — но это решение, а не слепота.

**Справочные чтения — один раз за прогон** (`_SEEN_READS`, `_repeat_answer`, §9.6.5) —
папки марки и свойства вида товара за прогон не меняются. Две потери, закрываются порознь:
лишний круг цикла ($0.097) убирает ТОЛЬКО запрет в промпте — к ответу инструмента круг уже
оплачен; повторную выгрузку в истории убирает `_repeat_answer`, отдавая указатель вместо
данных. Второе важнее, чем кажется: `_prune_file_dumps` эти выгрузки НЕ чистит, и повтор
поедет в каждом следующем запросе (свойства вида — 6 688 токенов, дерево без фильтров —
137 063). Указатель обязан называть, что приходило, — безымянному модель не верит. Отметки
сбрасывает `clear_nomenclature_cache`, и это требование, а не побочный эффект: она зовётся
ПОСЛЕ ЗАПИСИ в 1С, а `set_items` заводит папки и значения свойств.

**Учёт расхода токенов** (`token_usage`, `src/agent/usage.py`, §9.6.4) — строка на КАЖДЫЙ
вызов API, не на ход: ход это десятки вызовов. Снимается в `_record_usage` **до ветвлений**
цикла — `pause_turn` и `refusal` тоже оплачены, и учёт только на успешном пути давал бы
тихий недосчёт. Сбой приёмника не имеет права ронять прогон (всё под `try/except`). В базе
ТОЛЬКО счётчики: доллары считаются при показе, иначе смена тарифа исказит историю задним
числом. Множитель кеш-записи здесь **×2** (часовой TTL), а не ×1.25 из умолчания SDK.
Показ — `/tokens` и строка в итоге прогона (считать до `clear_run`: граница суммирования —
`price_run.started_at`). Главное число — доля чтения из кеша: около нуля значит сломанный
префикс, и это дороже любых настроек `effort`.

**Очередь коллекций** (`price_run.stage`) — марка от `BIG_TM_ITEMS` (300) позиций
дробится: `propose_prices` отказывает, пока не вызван `start_tm_collections`. Порог считает
код, не модель. Хвосты строят модульные `queue_tail`/`next_step` в `pricing_tools.py` —
их же зовёт обработчик кнопок, поэтому они не методы класса.

**Отложенные задачи** (`deferred_tasks` + `src/storage/price_files.py`) — наполняются
кнопками «Пропустить»/«Отложить», живут отдельно от `price_run`, потому что переживают его
очистку. Прайс кладётся на диск лениво и удаляется с последней ссылающейся задачей.
Устаревание — ТОЛЬКО по более свежей `price_date`: тот же прайс, присланный заново, задачу
не роняет, иначе возврат к отложенному ломался бы сам собой.

**Итог прогона** (`_finish_run` в `pricing_handlers.py`) — единственное место, где
печатаются отложенные замечания по прайсу целиком (`price_run.notes`, инструмент
`add_final_note`) и строка «обработан полностью». Один выход на оба пути: и после кнопки
на последней марке, и когда по ней нечего было писать. Замечания уровня файла НЕ должны
попадать в предложение по марке — иначе повторяются под каждым брендом.

**Прогон прайса по маркам** (`price_run` в `src/storage/pricing.py`) — предложение
строится на ОДНУ ТМ (`propose_prices` откажет, если передали несколько), в хвосте
«Осталось обработать: …». После нажатия кнопки обработчик сам продолжает диалог следующей
маркой через `_run(..., user_id=...)` — **user_id передаётся явно**, потому что там
`message` это сообщение бота и `from_user` в нём бот, а не админ. Режим прайса и файл в
`_files` живут до конца прогона. Проверка «загружал, но не предложил» (`_unproposed`)
исключает марки ИЗ ПЛАНА — иначе ругается на каждую соседнюю; имя марки берёт из
`_TM_NAMES` (заполняется в `_selling_tm`), а не из первого слова наименования товара.

**Скачки цен** (`unit_warnings` в `src/price_tool/changes.py`) — изменение больше чем в
1.5 раза выносится наверх предупреждений. Причина определяется ПО КОЛЛЕКЦИИ, в порядке:
часть позиций уже стоит новую цену (значит в папке разные товары) → цены внутри папки
разные → и только для однородной коллекции гипотеза «цена за упаковку». Порядок важен:
на Classen отношение 2.02 совпало с упаковкой 1.974 случайно, цена была верной, а
выбивалась одна позиция. Не блокирует запись.

**История диалога по прайсу** (`_prune_file_dumps` в `pricing_handlers.py`) — в истории
остаётся ТОЛЬКО последняя выгрузка листа, прежние заменяются заглушкой. Каждая весит до
40 000 символов и едет в каждый следующий запрос; на прайсе в 12 870 строк история выросла
до 560 000 символов и модель перестала отвечать. Файл лежит в `_files`, кусок перечитывается
через `contains`/`from_row`.

**Ход очереди марок** — `_run` крутит цикл до `MAX_AUTO_STEPS`: если `PricingTools.advanced_to`
выставлен (марка закрыта без кнопки, писать было нечего), обработчик сам переходит к
следующей. Без этого прогон вставал: кнопки нет — значит нет и обработчика, который двинул
бы очередь.

**Плитка** (`plan_items` в `src/price_tool/changes.py`) — у керамики коллекция
неоднородна: настенная, напольная, декоры и бордюры лежат в одной папке с разными ценами.
`propose_prices` принимает `items[{ref, purchase, rrc}]`, тронуты только перечисленные.
`GroupResult.whole` запрещает групповую форму записи для частичной группы — иначе цена
уехала бы на соседние элементы. Разные цены внутри коллекции плитки не считаются
расхождением.

**Чтение прайса** (`render_preview` в `src/price_tool/parser.py`) — до 1500 непустых
строк на лист, дальше подсказка с `from_row`, и `read_price_file` принимает этот параметр.
Лимит в 250 строк резал боевой лист на 394 строки молча, и хвост был недостижим в
принципе. Обрезка по `MAX_TEXT_CHARS` тоже сопровождается явной пометкой.

**Маппинг колонок прайса** (`src/storage/pricing.py`) — ключ **`(signature, sheet)`**, по
строке на лист. Одна строка на файл приводила к тому, что запомненный лист сужал работу
агента до себя, а остальные листы мультилистового прайса молча выпадали. Блок «ЗАПОМНЕННЫЙ
МАППИНГ» в `read_price_file` обязан явно требовать разбора остальных листов. Старая схема
мигрирует в `init()` (лист достаётся из JSON и переезжает в ключ).

**Категории товаров** (`src/price_tool/scope.py`) — что вообще анализируем; задаётся
командами `/categories` один раз на все прайсы. Пустой список = ограничений нет, а не
наоборот. Сопоставление с `product_type` из 1С нестрогое (вхождение подстроки), поэтому
«плитка» покрывает «Керамическая плитка». `propose_prices` проверяет это независимо от
модели.

**Эксклюзивы поставщиков** (`src/price_tool/exclusive.py`) — надпись «эксклюзив» в прайсе
запоминается заявкой (`exclusive_claims`), действующая пометка **выводится** из заявок и
решений админа (`exclusive_decisions`), а не хранится. Спор двух поставщиков в окне 2 мес →
вопрос админу, пометка до ответа не показывается. Список эксклюзивов вкладывается в
системный промпт (`build_system_prompt`), потому что у менеджерского агента нет кодов 1С,
чтобы сопоставить свой ответ с БД. Функция справочная — на цены не влияет.

**Авторизация** (`src/bot/auth.py`) — middleware проверяет whitelist в SQLite (`src/storage/users.py`). `ADMIN_TELEGRAM_ID` из конфига всегда проходит; добавляет `is_admin: bool` в данные обработчика.

**Транскрипция голоса** (`src/bot/handlers.py`) — OpenAI Whisper API (`whisper-1`, `language="ru"`). Требует `OPENAI_API_KEY` в `.env`; без ключа возвращает пояснение пользователю.

**Статус действий** — при каждом вызове инструмента `on_tool` редактирует одно сообщение в чате (не создаёт новые). Маппинг `_TOOL_STATUS` в `handlers.py`.

### Конфигурация

`src/config.py` загружает `.env` через `python-dotenv`. Обязательные переменные: `TELEGRAM_BOT_TOKEN`, `ADMIN_TELEGRAM_ID`, `MAIL_USER`, `MAIL_PASSWORD`, `ANTHROPIC_API_KEY`. Опциональные: `OPENAI_API_KEY` (голос), `MAIL_HOST`, `MAIL_PORT`, `DB_PATH`.

### Системный промпт

`src/agent/prompts.py` кодирует полную логику агента: валидация запроса (бренд + коллекция обязательны, для плитки — размер) → поиск в почте → сайт → 4 формата ответа (основной / случай А / Б / В). Промпт передаётся с `cache_control: ephemeral`.
