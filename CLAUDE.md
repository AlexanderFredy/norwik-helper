## Architecture

Telegram-бот с AI-агентом для менеджера norwik.ru: принимает текст/голос → агент ищет товар в почте и на сайте → отвечает ценами и контактами поставщиков.

### Поток данных

```
Telegram (aiogram) → AuthMiddleware → handlers.py
                                           ↓
                                    Orchestrator (Claude API manual loop)
                                     ├── ToolExecutor.execute(name, input)
                                     │    ├── MailClient (IMAP, sync via to_thread)
                                     │    └── NorwikClient (httpx, sync via to_thread)
                                     └── on_tool callback → edit_text в Telegram
```

### Ключевые детали реализации

**Оркестратор** (`src/agent/orchestrator.py`) — ручной agentic loop, не tool runner. Причина: нужна обработка `stop_reason == "pause_turn"` для серверного `web_search` (Anthropic-hosted). Цикл продолжается до `end_turn` или отсутствия `tool_uses`. Лимит `MAX_ITERATIONS = 30`. Принимает `on_tool` callback — вызывается перед каждым инструментом для обновления статуса в Telegram.

**Инструменты** (`src/agent/tools.py`) — 6 кастомных + 1 серверный:
- `search_emails` / `read_attachment` / `get_email_contacts` — IMAP
- `search_norwik` / `get_norwik_product` — парсинг norwik.ru
- `get_price_history` — «когда меняли цены»: даты из 1С (`by-tm`), источник цены из
  журнала `price_writes`; форматирует ответ код (`src/price_tool/history.py`), не модель
- `web_search` — `{"type": "web_search_20260209"}`, выполняется на стороне Anthropic (случай А: поставщик не найден)

**IMAP-клиент** (`src/email_tool/client.py`) — синхронный, вызывается через `asyncio.to_thread`. Строго read-only: `select(readonly=True)`, только `BODY.PEEK` (не ставит флаг `\Seen`). Операции записи не реализованы намеренно.

**Классификатор писем** (`src/email_tool/classifier.py`) — определяет тип письма (прайс/остатки) в порядке: тема → имя вложения → названия листов Excel. Парсит подпись для извлечения имени и телефона менеджера поставщика.

**NorwikClient** (`src/website_tool/norwik.py`) — поиск через `/search?query=`, цена из `itemprop="price" content="..."`. Один товар имеет несколько `<a href="item/...">` на странице (картинка + текст); выбирается лучший title через `_title_score()` (предпочтение кириллице и тексту с пробелами).

**Режимы работы** (`src/price_tool/modes.py`, §5.2) — «товары+цены» (умолчание), «товары»,
«цены»; команда `/mode`, значение в `app_settings`. Режим задаёт не только этапы, но и
СОСТАВ ЗАМЕЧАНИЙ: `propose_prices` принимает два массива — `warnings` (цены) и
`item_warnings` (справочник), и замечания, которые формирует код, классифицируются в
`_render`, а не моделью. Всегда видны независимо от режима: «1С не отдала N поз.»,
«категория не в списке», потеря загруженной марки — это состояние системы.

**Правка справочника** (§19 спеки) — только контракт, кода нет: ни один эндпоинт в 1С не
реализован. Пять запросов ТЗ сведены к трём чтениям и одной записи `set-items`; перенос в
«снятые с производства» — это `update_item` со сменой `parent_ref`, отдельной операции нет.

**Форма 1С для модели** (`specs/1c-model-form.md`, `specs/1c/agent-commands.bsl`,
`specs/1c/set-model-state.bsl`) — BSL выложен и **проверен живьём**
(`tests/integration_model_state.py`, запускать `python -m tests.integration_model_state`;
пишет в зеркало под номерами 901/902 и вычищает за собой). **Провайдер —
`src/onec/model_provider.py`**, подключается в `main.py`, только если 1С настроена.
Он же СЛУШАТЕЛЬ: снимок уезжает, лишь когда состояние менялось, — в простое оборот
стоит один GET. Признак «менялось» снимается ТОЛЬКО после успешной отправки, иначе
снимок, не доехавший из-за сети, не поехал бы никогда. Смещение часов измеряется
каждым опросом по `server_time`, и разница ЧАСОВЫХ ПОЯСОВ попадает в то же смещение —
пояс сервера знать не требуется. Исход команды сообщается, когда её не стало в
очереди; схлопнутые команды закрываются ВСЕ (иначе в форме навсегда горит колесико),
а причина отказа сопоставляется по (инициатор, прайс, задача) — это однозначно ровно
потому, что очередь схлопывает команды по объекту. **Связка «команда очереди → команда
1С» лежит в БАЗЕ** (`src/storage/sent_commands.py`) и снимается только после успешного
ответа 1С: в памяти она гибла вместе с процессом, и перезапуск бота, случившийся между
«принята» и исходом, запирал форму НАВСЕГДА — команда отрабатывалась заново, а закрыть её
было уже нечем, потому что GET `agent-commands` отдаёт только «ждёт» (24.09.2026). Админ из 1С и админ из Telegram —
РАЗНЫЕ инициаторы (приставка `1c:`), это решение Ф4, а не недосмотр. команды
формы никуда не поедут, пока он не появится. Обе стрелки идут ОТ агента, потому что
обработчик HTTP-сервиса работает в своём сеансе и до открытой формы не дотягивается —
отсюда зеркало в 1С, и обойти его нечем. Снимок приходит целиком, но **применяется
разницей**: иначе счётчик `ии_МодельАгентаВерсияСостояния` рос бы на каждом обороте и форма
перерисовывалась бы под руками у админа каждые 5 секунд. У команды ТРИ состояния, а не два
(`ждёт` → `принята` → `выполнена`/`отклонена`): колесико ожидания обязано гаснуть по
результату, а не по факту, что агент команду забрал. `Создана` штампует СЕРВЕР 1С — часы
рабочей станции дали бы одному админу вечный выигрыш в правиле «кто первый». Команды лежат
в РЕГИСТРЕ, а не в справочнике: это очередь, она обязана пустеть, а у записи регистра нет
ни ссылки, ни пометки удаления — уборка это снятие строки. Идентификатор поэтому GUID,
сделанный при постановке: своего у записи регистра нет, а счётчик потребовал бы блокировки.
Переиспользовать идентификаторы нельзя — запоздавший ответ по закрытой команде попал бы в
новую.

**Крупный прайс** (`BIG_PRICE_ROWS`, §6.10) — от 5 000 строк `read_price_file` не отдаёт
таблицу, а требует спросить админа «обработать или пропустить» с оценкой в токенах.
`manual` ≠ «Отложить»: в `deferred_tasks` не попадает, считается обработанным, бот выходит
из режима.

**Ключ кешей по прайсу — хеш СОДЕРЖИМОГО** (`_file_key`), не сигнатура: сигнатура считается
по скелету файла, и прайс следующего месяца имеет ту же — решение и раскладка молча
перешли бы на новый файл.

**Повторный прайс** — два кеша с разным смыслом: `_PARSED` в `parser.py` снимает CPU
(разбор шёл дважды за вызов) и обязан отдавать КОПИЮ, потому что в строки вставляются
маркеры картинок; `price_layout` снимает токены — раскладка брендов по сигнатуре файла,
чтобы не повторять разведку. Оба чистятся, когда от того же поставщика пришёл прайс новее.

**Стоимость контекста.** Цикл ручной: каждый вызов инструмента — отдельный
`messages.create` со ВСЕЙ историей. Поэтому три вещи обязательны и ломать их нельзя:
`_cached()` в `orchestrator.py` ставит точку кеширования (`CACHE`, TTL 1 час) на последний блок (в сохраняемую
историю `cache_control` не попадает); `_prune_file_dumps` оставляет по одной свежей
выгрузке каждого вида (лист прайса и номенклатура) — прочие заменяет заглушкой;
`get_1c_nomenclature` принимает `collection_ref` и в режиме коллекций обязан его получать.
На боевом прайсе история была 197 тыс. токенов, шаг по коллекции стоил ~1,2 млн входных.
Плюс: предложение админу шлёт обработчик из `last_summary` — модель его НЕ переписывает
(было ~2 000 выходных токенов на шаг по цене выхода), а `handle_turn(base_tools=False)`
не подмешивает менеджерские инструменты в режим цен.

**СТАРЫЙ ПРАЙСОВЫЙ ПОТОК ОТКЛЮЧЁН ОТ ТГ** на время обкатки модели: `pricing_router` не
включён в диспетчер (`main.py`), его команды убраны из меню и справки. Код цел, вернуть —
раскомментировать одну строку. Оба потока реагировали бы на один присланный файл.

**Марка в адресе задачи СВЕРЯЕТСЯ С 1С** (`task_builder.owner_map`/`fix_marks`): один
прайс — не одна марка, у Most Flooring часть коллекций заведена под A+ Floor, и по вёрстке
файла это не видно. Владелец определяется по дереву папок (от папки коллекции вверх до
`kind == "tm"`), расхождение правится молча, одноимённая коллекция у двух марок —
оставляется с заметкой. Сверка идёт ПОСЛЕ хода обычным запросом из кода, а не вызовом
инструмента: круг ручного цикла несёт всю историю и стоит ~$0.097, а решать тут нечего.

**Нормализация — ОДНА задача на марку**, `TaskSubject.MARK`: имена собираются по единому
шаблону для всей марки, и дробление по коллекциям стоило бы пяти захватов и пяти прогонов
вместо одного. Сделано в `add_task`, а не подсказкой в промпте — модель перечисляет
коллекции, потому что видит их в прайсе.

**Имена в `Ref` хранятся КАК НАПИСАНЫ, сравниваются через `keys`** (нормализованные).
Раньше оседала нормализованная форма, и она же попадала админу на глаза: «most flooring /
ле паркет». Нормализация нужна для сравнения, а не для показа.

**Сверка идёт ПО АРТИКУЛУ, а не по имени коллекции.** Имена расходятся штатно: у Most
Flooring в 1С «Millenium Pro», «Provence», «High Glossy», в прайсе «Миллениум Про»,
«Прованс», «Супер Глянец». Поиск по имени не находил ничего, сверка отвечала «коллекции в
1С нет», и агент завёл СЕМЬ задач «завести всю коллекцию» по давно заведённым — ~56 дублей,
если бы их выполнили. Артикул одинаков в обоих источниках; имя коллекции 1С возвращается
агенту, чтобы он адресовал задачу им.

**АРТИКУЛ НЕ УНИКАЛЕН, и код обязан это переживать** (вопрос админа 25.09.2026). Словарь
«артикул → карточка» схлопывал пару молча: вторая карточка не находилась по артикулу
НИКОГДА, а какая уцелеет — решал порядок выгрузки. Проставь артикулы второй коллекции, и
она исчезла бы из сверки целиком. Теперь ключ ведёт СПИСОК, своя коллекция решает спор, а
два товара ОДНОЙ коллекции под одним кодом — это уже ошибка справочника, и она
называется вслух (`артикул_не_различает_позиции`), а не разрешается наугад. **В выборе
наименьшей цены между поставщиками неуникальный артикул НЕ УЧАСТВУЕТ** (`_cheapest`):
журнал предложений ключуется артикулом, другого межпоставщицкого ключа нет, и чужая цена
по такому коду неизвестно про какую толщину — приняв её, увезли бы цену 3,6 мм на 4 мм.
Своя цена из прайса при этом пишется как обычно, а админу уходит строка почему.

**СВОЯ КОЛЛЕКЦИЯ ПЕРЕВЕШИВАЕТ АРТИКУЛ, если она в 1С есть** (`strangers` в `_compare`).
Один код декора бывает у двух коллекций одной марки в разных толщинах: «6006-4»,
«6009-20» и «1002-32» есть и у Spark (4 мм), и у Modern (3,6 мм). Три кода прайса Spark
нашлись в карточках Modern — и рушилось всё сразу: раз «нашлось», ветка поиска коллекции
по имени не запускалась, агент решал «коллекции SPARK в 1С нет» и предлагал завести
восемь позиций при живых восьми, а сверка цен сравнивала закупку Spark (1150) с ценой
Modern (960) и показывала расхождение, которого нет, — запись испортила бы ЧУЖУЮ
коллекцию. Случаи разделяет ровно один признак: **существует ли в 1С коллекция с этим
именем**. У Most Flooring её нет («Миллениум Про» против «Millenium Pro»), там артикул
остаётся единственным ключом и правило не срабатывает; у Spark она есть, и совпадение за
её пределами — омоним. Отброшенные совпадения НАЗЫВАЮТСЯ поимённо
(`артикулы_заняты_другой_коллекцией`): молча убранное агент прочтёт как «артикула в 1С
нет» и заведёт позицию, которая там есть.

**ИМЯ КОЛЛЕКЦИИ ИЩЕТСЯ И БЕЗ ПРИСТАВКИ МАРКИ** (`_collection_keys`). В прайсе Вестерхофа
коллекции зовутся «Westerhof Spark», «Westerhof Vivace», в 1С свойство «Коллекция» и
папка — просто «Spark», «Vivace». Совпадений не было ни одного: сверка отвечала
«коллекции в 1С нет», и агент предлагал завести заново три ЖИВЫЕ коллекции (8, 8 и 10
позиций). Приставка снимается ЦЕЛЫМ СЛОВОМ, с начала и только имени ЭТОЙ марки —
«Sparkling» не заденет, чужую коллекцию не притянет; двуязычное «Westerhof / Вестерхоф»
даёт оба слова.

**АРТИКУЛ БЫВАЕТ СПРЯТАН В НАЗВАНИИ** (`article_from_title`). Поставщик пишет его прямо в
имени расцветки — «Rumba (6006-4)», — и это не догадка: у коллекции Modern той же марки
артикулы В 1С уже заполнены ровно такими значениями (`6006-4`, `65-901`, `1002-32`), а
колонки артикула в прайсе нет вовсе. Поэтому `_by_title` пробует ПЕРВЫМ артикул из имени
и лишь потом само имя: артикул не зависит от написания декора. Шаблон узкий — цифры,
дефис, цифры: ни размер «1290x180x4», ни класс «33», ни «4мм» под него не попадают. **Два
кандидата в одном имени — значит ни одного**: неверный артикул хуже отсутствующего,
потому что по нему выбирается наименьшая цена между поставщиками. Коллекции с пустыми
артикулами код готовит ПАРЫ «код 1С → артикул» прямо в задаче, а занятый в базе артикул
не предлагает — записав чужой, свели бы две разные позиции в одну.

**Неоднозначное имя разбирается ЧИСЛАМИ** (`_only_one_fits`). Имя подошло к двум
карточкам — сравниваем толщину, класс и размер со строкой прайса: их пишут одинаково с
обеих сторон, а словесные значения расходятся написанием, и «совпадение» по ним было бы
выдумкой. Решает ТОЛЬКО один уцелевший кандидат: ключ создан разбирать неоднозначность, а
не заменять её другой. **Короткие названия ищутся целым словом** (`_price_line`): у Spark
декоры зовутся Ash, Fire, Glow, Star, подстрочный поиск ловил бы пол-прайса («ash» внутри
«Ashley»), а раньше такие имена не искались вовсе — семь позиций из восьми оставались без
строки прайса.

**ВТОРОЙ КЛЮЧ — название расцветки, и он строго в границах** (`_by_title`). У коллекции
«Westerhof Vivace» (лист SPC) артикулов нет ни у одной позиции, и сверка по артикулу не
отвечает вовсе. Тогда включается сопоставление по именам декоров — но ТОЛЬКО: внутри одной
коллекции, уже опознанной по имени папки (через марку целиком никогда: «Дуб Медовый» есть и
в Vivace, и в Modern); только когда по артикулу не нашлось НИЧЕГО (есть артикулы — решают
они); неоднозначное имя считается НЕ найденным, а не выбирается наугад. В сторону снятия
второй ключ не применяется — там наличие проверяется по всему тексту файла. В журнал
предложений и в выбор наименьшей цены имена НЕ попадают: артикул — единственный
межпоставщицкий ключ, а имена у разных поставщиков совпадать не обязаны.

**Позиция без артикула НЕВИДИМА для сверки** (`_nameless_twin`). Сопоставление идёт по
артикулу — имена расходятся штатно, — и карточка с пустым артикулом не совпадёт ни с чем: у
Вестерхофа папка COSMO (YO-00052996) стоит на месте с шестью живыми позициями, а агент
предложил завести коллекцию заново, то есть получить девять дублей. Поэтому при нулевом
совпадении код ищет коллекцию ПО ИМЕНИ и, найдя её с пустыми артикулами, говорит прямо:
заводить нельзя, работа тут другая — проставить артикулы. К каждой позиции прикладывается
СТРОКА ПРАЙСА, где встречается её расцветка: артикул стоит в ней же, и задача становится
механической.

**Нормализация чужой марки тоже отклоняется** — тем же признаком доли (`mark_coverage`).
Агент принял заводскую пометку «Завод AGT» за бренд и заказал нормализацию ВСЕГО каталога
AGT: марки, о которой прайс Вестерхофа говорит двумя коллекциями из семи. Наименования
чужой марки правятся по ЕЁ прайсу, а не попутно.

**Снятие предлагается только по марке, о КОТОРОЙ прайс** (`mark_coverage`). Выгрузка марки
попадает в кеш прогона от любого вызова сверки — в том числе когда код сам переставил марку,
найдя артикулы под чужой. На Вестерхофе это стоило 18 ложных задач: агент принял заводские
пометки прайса («Завод AGT», «Peli») за бренды, код нашёл под AGT коллекцию Effect — и весь
каталог AGT, Peli и Kronparket поехал в снятие. Признак «прайс про эту марку» — ДОЛЯ
закрытых живых коллекций: меньше половины — судить об остальных нечем, и об этом пишется
строка в ответе. Промпт отдельно называет ловушку: завод-изготовитель это свойство
коллекции, а марки с такими именами в 1С — совсем другие бренды.

**«Агент не сверял» — НЕ «в прайсе нет»** (`_in_price`). Кандидат в снятые проверяется по
САМОМУ ФАЙЛУ, а не по следу вызовов сверки: прайс Westerhof на три листа, агент обошёл не
все, и живые COSMO, Shine, Aristocrat поехали в снятие (бой 24.09.2026). Ищем по
нормализованному тексту всего файла — артикул в ячейке слеплен с названием и размером
(«…Альфа PELI (CO 512) 1290*190*8мм»), поэтому сравнение «ячейка = артикул» не находит
ничего. Артикулы короче трёх знаков не проверяются: «12» найдётся в любом размере. Имя
коллекции проверяется и БЕЗ размерного хвоста — в 1С папка «Aristocrat 1200х400», в прайсе
просто «Aristocrat». Та же проверка стоит и на позициях внутри сверенной коллекции.

**Коллекции, которых прайс не коснулся, находит КОД** (`untouched_collections`) и сам
заводит по ним задачу-кандидата в снятые. Агент их назвать не может: он идёт от прайса, а
такой коллекции там нет — так осталась незамеченной Brilliant у Most Flooring.

**Описание задачи пишется АБЗАЦАМИ, перечисления — списком.** Его читает человек в форме
1С, глазами; сплошной абзац на десять строк не читается вовсе, и в нём теряется
предупреждение в конце. Порядок задан промптом: суть одним предложением → откуда это →
что показала сверка числом → список позиций → свойства → цены → на что обратить внимание.
Формат держится на трёх вещах: правило в промпте с образцом, `absorb` склеивает дополненные
описания через ПУСТУЮ строку (иначе новый абзац прилипает к прежнему), и поле в форме 1С
высотой 10, а не 5.

**Задачи КОНКРЕТНЫ, потому что есть сверка** (`compare_with_1c`): она отвечает, каких
артикулов прайса нет в 1С, каких позиций 1С не стало в прайсе и какие свойства у коллекции
пусты. Без неё агент писал «проверить, все ли 8 декоров заведены» — описание, после
которого работа может оказаться пустой, и админ перестаёт такие читать. **Выгрузка в
контекст НЕ ПОПАДАЕТ**: код забирает её себе и возвращает несколько строк, иначе тысячи
токенов поехали бы в каждый следующий запрос. «Нет в прайсе» — КАНДИДАТ в снятые, а не
приговор: прайс мог быть частичным. Наименований 1С сверка не возвращает, поэтому агент
по-прежнему не судит о соответствии имён шаблону.

**Источник цены хранится В 1С** (реквизит `Поставщик` в `ЦеныНоменклатуры`, зеркало
`Справочники.ии_МодельПоставщики`, §6.4). Журнал предложений отвечает «кто что предлагает»,
регистр 1С — «чья цена СТОИТ»: разные вопросы, и второй раньше не отвечал никто. Из-за этого
пробел в журнале означал потерю выгоды — стоящая цена не могла себя представить. Зеркало
опознаётся ПО КОДУ (имя админ меняет командой, поиск по имени плодил бы дубли и растаскивал
историю цен), табличную часть «ЮрЛица» агент НЕ ТРОГАЕТ — её заполняет человек. Реквизит
ставится ТОЛЬКО в записях, которые создаёт агент: чужую цену он не атрибутирует, потому что
от какого поставщика она была, не знает никто (решение админа 23.09.2026). В контекст модели
поле не попадает — замерено, что это стоило бы +3 400 токенов на выгрузку (+22%) и ~$0,04 за
прогон, а модели оно не нужно: решение принимает код.

**Наименьшая АКТУАЛЬНАЯ цена** (`src/model/offers.py`, §6.4) — один товар возят несколько
поставщиков, и прайс подороже не должен затирать цену подешевле. Решает КОД в момент записи
(`executor._cheapest`), модель о конкурентах не знает вовсе. Ключевое — **актуальность
нельзя проверить, её можно только датировать**: единственное доказательство живой цены это
новый прайс. Поэтому свежесть считается ОТНОСИТЕЛЬНО обрабатываемого прайса (он свежий по
определению, значит двух протухших предложений в сравнении не бывает), окно —
`FRESH_WINDOW_DAYS = 180` (решение админа 22.09.2026). Ошибка намеренно сдвинута в
безопасную сторону: записать честно подорожавшую цену дешевле, чем держать в базе цифру, по
которой никто не продаёт. Протухшая выгода не выбрасывается молча — о ней пишется админу:
это повод запросить свежий прайс. РРЦ берётся У ПОБЕДИТЕЛЯ, чтобы пара была согласованной;
эксклюзивы правило НЕ обходит (оба — решения админа). Позиция, которой в свежем прайсе
победителя не стало, выбывает из журнала сама — минимум пересчитывается по оставшимся.

**Журнал встреч артикулов** (`src/storage/sightings.py`, §6.1) — отличает «нет в ЭТОМ
прайсе» от «снято с производства». Строка на пару (артикул, поставщик); новый прайс той же
пары (поставщик, СИГНАТУРА) свои строки ЗАМЕНЯЕТ — только так «есть у другого» значит «есть
в его последнем прайсе», а не «когда-то встречалось». Сигнатура в ключе обязательна:
поставщик шлёт прайс частями по типам товара, и замена по одному поставщику стёрла бы
соседний раздел. Наполняется тем, что модель и так перечислила в `compare_with_1c`, —
ЛИШНИХ ТОКЕНОВ НОЛЬ. Коллекция, чьи артикулы стоят в чужом свежем прайсе, в снятые НЕ
предлагается: это смена канала, а не конец производства; вместо задачи — строка в сводке.
Пока журнал пуст, поведение прежнее (снимаем), и это решение админа 21.09.2026, а не
недосмотр. Молчащий год поставщик перестаёт подтверждать (`SIGHTING_TTL_DAYS`).

**Возврат из снятых — не заведение заново** (`_revival_note`, `_revival_brief`). Коллекцию,
однажды унесённую в снятые, поставщик может привезти снова, а выгрузка марки её уже не
видит — снятые лежат в другой ветке. Поэтому «недостающие» артикулы проверяются `find_items`
ПАЧКОЙ по коллекции (запрос из кода, круга цикла не стоит), и найденные попадают в описание
задачи «добавление новых» С КОДАМИ 1С — текст пишет КОД, а не модель: по этим кодам задача
исполняется, а пересказ однажды разойдётся с ответом 1С.

**Марку определяет 1С, а не обложка прайса** (`_actual_mark`). Сверка шла по марке,
которую назвала модель, и для коллекции, лежащей под ДРУГОЙ маркой, отвечала «коллекция
новая»: «Классик» (A+ Floor) в прайсе Most Flooring не сверялась ни по составу, ни по ценам,
и задач по ней не возникало вообще. Теперь при нулевом совпадении артикулов код спрашивает
1С: сперва дерево папок марки, потом точный поиск по артикулам. Два подвоха, из-за которых
это не работало раньше: **`folders()` без фильтра отдаёт только верхушку** (45 узлов, ни
одной коллекции — поэтому `fix_marks` после хода молча не срабатывал НИКОГДА), и **папка
марки называется «Ламинат A+ Floor»**, а марка — «A+ Floor», так что точное сравнение имён
не совпадало; плюс имя папки коллекции несёт размер («Классик 600x238x12»). Всё три
закрыты: дерево берётся с `tm=`, марка ищется по окончанию имени, коллекция — по имени со
снятым размерным хвостом.

**`find-items` сопоставляет АРТИКУЛ ЦЕЛИКОМ** (`specs/1c/find-items.bsl`, требует выкладки).
Было `ПОДОБНО "%артикул%"`, и на коротких артикулах ламината запрос «301» возвращал обои
«101489301» сотнями, упираясь в предел выборки раньше настоящих позиций. Но и голое
равенство не годится: «А 101» из прайса обязано найти «А101» в базе. Поэтому шаблон БЕЗ
КРАЕВЫХ «%», а внутри «%» на местах разделителей и на стыке букв с цифрами (`ШаблонАртикула`);
стыки — только у артикулов от четырёх знаков, иначе «A1» снова накрыло бы пол-базы. Лишнее
шаблон поймать может — на стороне Python ответ фильтруется по `norm_article` (`_search_1c`),
и этот фильтр нужен сам по себе: со старым BSL без него в описание задачи уезжали чужие
коды 1С. Вхождение осталось только у `name`.

**Пустая цена в 1С видна без прайса.** `compare_with_1c` считает позиции без закупки и
говорит об этом, даже когда колонки цен не названы: у «Классик» цен не было ни у одной из
восьми позиций, а ответ «колонки не названы» читался как «сверить нечем».

**Приписки в скобках остаются, но причёсываются** (`naming._brackets` внутри `tidy`).
Решение админа 22.09.2026: «(английская ёлочка)» в наименовании — норма, а вот набор
правим — пробел после «(», перед «)» и прилипшая к слову скобка. Содержимое скобок не
трогается вовсе: правится НАБОР, а не текст. Живёт в `tidy`, значит применяется само и в
историю правок не попадает — как двойной пробел и CAPS LOCK.

**Размер живёт в имени ПАПКИ, и только там** (`_collection_size`). Модель видит в 1С папки
«Ле Паркет 600x600x14» и повторяет образец, передавая размер ВНУТРИ имени коллекции. Раньше
`_folder_title` снимал задвоение только для папки, а имя товара и значение свойства
«Коллекция» получали размер как есть: «Ламинат Peli Anatolia Elite 1290x157x12 Белый Дуб».
Теперь имя коллекции чистится на входе в план — точной обратной операцией к `folder_name`,
по ЕДИНОМУ размеру коллекции (разные размеры — не трогаем вовсе), — и папка по-прежнему
получает размер, а карточка и свойство нет.

**Капс в названии расцветки правится** (`naming.title_case`). Агент завёл «Ламинат
Westerhof Cosmo PERSEUS» — так свёрстана таблица поставщика, а не назван товар. Трогаются
ТОЛЬКО слова целиком из заглавных: длинные (от `CAPS_WORD_MIN` = 4) всегда, короткие — лишь
когда кричит вся строка («ДУБ МЕДОВЫЙ» → «Дуб Медовый»). «SPC», «EIR», «AC5» и «Onyx&More»
не трогаются: там регистр значащий или это не слово. Авторское «Дуб серый» остаётся как
есть — переводить его в «Дуб Серый» никто не просил, а правило по-словам сделало бы именно
это на сотнях карточек.

**Марка в НАИМЕНОВАНИИ — до косой черты** (`naming.tm_for_name`). В справочнике 1С марка
часто записана двуязычно («Westerhof / Вестерхоф»), и читать поле целиком правильно везде,
кроме имени товара: там выходило «Ламинат Westerhof / Вестерхоф Bellini Cappuccino» — обе
формы подряд вместе с разделителем. Решение админа 22.09.2026: брать первую часть. Правило
стоит внутри `build_name`, поэтому действует и на нормализацию, и на создание позиций.

**Правка справочника поставщиков будит зеркала** (`catalog_handlers._mirrors_know`).
Имя поставщика стоит в таблице прайсов формы 1С, но снимок уходит туда ТОЛЬКО когда менялось
состояние модели, а переименование живёт в справочнике и модели невидимо: админ
переименовал, нажал «Обновить» и увидел старое имя. Событие `SUPPLIER_RENAMED` идёт с ПУСТЫМ
текстом — `TelegramListener` такие пропускает, и второго сообщения о том, что админ сам
только что сделал, он не получает. Вторая половина той же поломки: провайдер кешировал имена
на весь процесс — теперь кеш живёт один снимок.

**`write_prices` принимает и РРЦ** (`rrc`, в прайсах — РРЦ или МРЦ), на коллекцию и
по-товарно. Раньше в `plan_collection` жёстко шёл `None`, и агент честно докладывал: «РРЦ
отдельным полем не записывалась — инструмент цен принимает только закупочную». Планировщик
её умел всегда. Без этого входа круг не закрывался: сверка при следующей пересборке снова
показывала расхождение по РРЦ, а починить его было нечем. Розницу по-прежнему НЕ передают —
её считают правила магазина.

**Цена бывает ОДНА НА КОЛЛЕКЦИЮ** (`price_check.flat_prices`). У Most Floor цифры стоят в
строке коллекции («301 Аристо … 1880 … 2980»), а у остальных декоров ячейки пустые —
колоночный разбор такую раскладку не берёт в принципе, строк с ценами всего одна. Поэтому
`compare_with_1c` принимает либо `price_columns` (цена у каждой позиции своя), либо `prices`
— пару чисел на коллекцию, которую модель и так видит. Артикул в ячейке часто слит с именем
(«301 Аристо»), поэтому строки индексируются и по полному ключу, и по первому слову.

**«Не с чем сравнить» — не «совпадает».** `price_check.report` различает три исхода:
расхождения, совпадение и НОЛЬ сопоставленных позиций. Последнее отвечало «цены совпадают,
задачу НЕ заводи» при том, что цен в 1С не было вовсе. Отдельно считается `без_цены_в_1С` —
позиции, у которых цены нет ни в прайсе, ни в базе: это работа, а не отсутствие данных.

**Цены сверяются КОДОМ, и задача заводится только по расхождению** (`src/model/price_check.py`).
Правило было «в прайсе есть колонки цен — заводи задачу», и на Most Flooring / Millenium Pro
это дало задачу на 8 позиций, у которых закупка и РРЦ уже совпадали с прайсом. Текущие цены
всё это время лежали в выгрузке `by-tm`, которую сборщик держит в памяти, — сравнения просто
не было. От модели нужно одно, чего код не знает: КАКИЕ КОЛОНКИ листа считать артикулом,
закупкой и РРЦ (`price_columns` в `compare_with_1c`, один раз на лист — повтор на каждой
коллекции это выходные токены на ровном месте). Порог — общий `SAME_PRICE_PCT` из
`price_tool.changes`, свой разошёлся бы с записью цен молча. Пустая цена в 1С — РАСХОЖДЕНИЕ,
а не совпадение. Совпавшие позиции отдаются ЧИСЛОМ, а не списком: агенту нужно решение, а не
перечень, который поедет в каждый следующий запрос.

**Ноль задач — это РЕЗУЛЬТАТ, а не сбой** (`service._make_tasks`). Заглушка (`stub_tasks`)
осталась ровно для сорвавшегося прогона. Пока проверок не было, пустой ответ означал только
«агент не справился»; теперь расхождения ищет код — цены сверяются с 1С, нормализация
отклоняется, когда менять нечего, недостающие позиции считает сверка, — и разобранный прайс
законно даёт ноль. 21.09.2026 повторная сборка по Most Floor выдала пять выдуманных задач,
каждая из которых при выполнении ничего бы не сделала. Поэтому `build_tasks` отдаёт ПАРУ
(задачи, что сказал агент): при нуле задач его слова единственное, чем «работы нет»
отличается от «прочитал не тот лист». Отказы `add_task` пишутся в журнал (`_refuse`) —
иначе причина нуля живёт только в истории диалога, которая никуда не сохраняется.

**Сбой прогона не трогает готовые задачи** (`_make_tasks(fallback=False)`). Пересборка
вызывает сборщик БЕЗ заглушки: список у прайса уже есть, и подменить его выдуманным из-за
того, что модель не ответила, — потеря работы. Команда в этом случае ОТКЛОНЯЕТСЯ с причиной,
задачи остаются. Причина сбоя вообще всегда едет админу текстом: 21.09.2026 прогон упал на
400 «credit balance is too low» посреди хода, и чтобы это узнать, пришлось поднимать базу
расхода токенов — сама ошибка осталась в консоли процесса, до которой из Telegram не
дотянуться.

**Задачи формирует агент** (`src/model/task_builder.py`, §6.1) — читает прайс, сопоставляет
бренды с марками 1С и заводит задачи на РЕАЛЬНЫЕ пары (марка, коллекция). **Выгрузки
номенклатуры 1С у него пока НЕТ**, и промпт обязан это называть: иначе он напишет «завести
12 недостающих позиций», которых не считал. Пустой ответ или сбой — откат на заглушку с
уведомлением: молчаливо пустой список админ прочтёт как «разбирать нечего». Уникальность
(адрес, вид) держится в самом инструменте — модель приходит к одной задаче дважды.

**Сравниваем ТО, ЧТО 1С СОХРАНИТ** (`items.STORED_DECIMALS`, `rounded`). Коэффициент
упаковки база хранит с тремя знаками после запятой, а прайс даёт 1,9608 — и правка
«1,961 → 1,9608» предлагалась КАЖДЫЙ прогон, ничего в базе не меняя и топя в себе
настоящие. Точность объявляется ПОЛЕМ и явно: молча округлять всё подряд — потеря данных.
Округлённое значение и сравнивается, и пишется, и показывается в отчёте — чтобы в 1С и в
журнале правок стояло одно число.

**Артикул нормализуется БЕЗ разделителей** (`refs.norm_article`): «LE-263», «LE 263» и
«le263» — один артикул. Общая `scope.normalize` для этого не годится, она заменяет пунктуацию
пробелом, и «le 263» не совпало бы с «le263».

**Цикл модели** (`src/bot/model_loop.py`, `src/model/service.py`, §9) — обработчики ТГ
**не действуют сами**: кладут команду в очередь и будят цикл (`loop.wake()`). Исключение
одно — приём файла: это поступление данных, а не команда, и таскать содержимое через
очередь незачем. Занятость считается ОТДЕЛЬНО ДЛЯ КАЖДОГО инициатора (`busy_for(actor)`):
свой захват админа не блокирует, общего набора «занятых» не существует. Истёкшие захваты
снимаются ПЕРВЫМ делом на обороте — иначе заброшенный прайс до конца оборота отклонял бы
чужие команды. **Выполнение задачи ПИШЕТ В 1С** (`src/model/executor.py`, §6.2): агент читает прайс и
выгрузку 1С, затем зовёт `write_items`/`write_prices` — те пишут СРАЗУ, второго
подтверждения нет, админ уже нажал «Выполнить». Без настроенной 1С (`run_task=None`)
остаётся заглушка: инструменты записи, которым некуда писать, дали бы прогон, честно
доложивший об успехе на ошибках соединения. **Право на запись проверяется ВНУТРИ прогона**
(`guard`), вплотную перед каждым вызовом 1С, и сверяется ПОКОЛЕНИЕ захвата: самый коварный
случай — захват сняли и тут же взяли заново, тогда актор и живость совпадут, а поколение
нет. Тот же `guard` продлевает аренду — это единственное место, где точно известно, что
прогон жив и дошёл до записи. Правила сборки (имена §19.5, порог 2%, категории) НЕ
переписаны заново, а вызваны из `price_tool`: второй набор разошёлся бы с первым молча.
**СНЯТОЕ АГЕНТУ НЕ ПОКАЗЫВАЕТСЯ** (решение админа 21.09.2026). Часть коллекций висит под
маркой с флагом «Не выгружать»: они УЖЕ сняты, а в папки снятых их перенесут отдельно и не
сейчас. Видя их, агент предлагал по ним работу — у Most Flooring так всплыли Quick и
Prestige в отчёте по совсем другой задаче. `get_1c_items` отдаёт только живые (57 из 100 на
Most Flooring), `compare_with_1c` и `normalize.plan` их не берут, но КЕШ остаётся полным:
сборке правок снятые нужны, иначе создание позиции не увидит, что товар уже есть, и заведёт
дубль. Искать снятые — только `find_1c_items`, он для того и сделан.

**«ЦЕЛОЙ» проверяется ПО ПРАЙСУ, а не принимается на веру** (`run_discontinue`). Задача
приходит с адресом коллекции, но описание может быть про ОДНУ позицию: у Вестерхофа агент
завёл снятие COSMO из-за единственного декора «Бета», и папка уехала в снятые вместе с
пятью живыми (бой 24.09.2026). Теперь перед переносом код читает файл: что в прайсе есть —
остаётся, чего нет — уходит ПОШТУЧНО, и только когда нет НИЧЕГО, двигается папка целиком.
Прайс не разобрался — перенос не делается вовсе: операция необратима, а гадать тут нельзя.

**Перенос ЦЕЛОЙ коллекции в снятые — тоже мимо модели** (`executor.run_discontinue`):
одна операция `update_folder` вместо N штук `update_item`. У агента переноса папки в
инструментах не было, и он двигал позиции по одной — восемь вызовов там, где хватало
одного, а пустая папка осталась в живой ветке. Папка ищется ПО КОДУ из адреса задачи
(`_add_discontinued_candidates` кладёт его, пока позиции ещё живы), иначе по имени как по
слову — имена папок разнородны, «Коллекция Brilliant - 10 декоров» рядом с «Provence».
Целевая папка снятых — из `discontinued.folder_for` по виду товара, то есть ПРОФИЛЬНАЯ, а
не общая свалка. Папка с чужими коллекциями внутри не двигается: перенос утащил бы их
следом. Задача про ОДИН товар остаётся агенту — там надо понять, что именно снимают.

**Повторяющийся ХВОСТ в названиях расцветок — шум** (`normalize.shared_tail`). Westerhof
делает часть коллекций на заводе Peli, часть на AGT, и поставщик дописал это в каждое имя:
«Альфа PELI», «Альпы AGT». Завод — свойство коллекции, а не расцветки, и в имени товара он
не различает ничего. Правило общее, а не список заводов: название расцветки внутри
коллекции УНИКАЛЬНО, значит повторяющееся слово расцветкой быть не может. Но у многих марок
первым словом идёт род («Дуб Авила», «Дуб Прато»), и он тоже повторяется — разделяет их
ПОЛОЖЕНИЕ: род спереди, маркер сзади, поэтому первое слово не трогается никогда. Достаточно
ДВУХ совпадений, а не всех: у «Effect» пометка AGT стоит лишь у семи позиций из
четырнадцати. Снятое называется в отчёте — решение принимал код, и проверить его должно
быть можно с одного взгляда.

**Нормализация наименований идёт МИМО МОДЕЛИ** (`src/model/normalize.py`): это
единственный вид задач, у которого нет ни одного входа снаружи 1С — прайс ему не нужен
вовсе, всё для имени лежит в карточке (`site_name` по §19.5 это РОВНО название расцветки).
Решать нечего, значит и платить за круги цикла незачем. Модуль не собирает имена сам: он
готовит тот же вход, что строила бы модель, и отдаёт в `items.plan_collection`. Админу
достаётся только неразрешимое кодом — пустой `site_name` и загрязнённый (внутри марка или
коллекция: такое попало бы в имя дважды). Снятые не трогаются. **Имя марки всегда из 1С**,
и переданное моделью игнорируется: `build_name` брал марку из её входа без отката к
справочнику, и «MOST FLOOR» из прайса переименовал бы сотни позиций — запретом в промпте
это не лечится, модель копирует написание из источника. Расхождение не замалчивается, а
уезжает в отчёт: переименование марки решает админ.
Состав выгрузки 1С зависит от ВИДА задачи — ценовой справочные поля не нужны ни одним
байтом, а история едет в каждый следующий запрос. Молчаливый агент не выдаётся за успех:
не вызвал `finish` — «к обработке», а если запись при этом состоялась — «частично», иначе
админ повторил бы задачу и записал второй раз.

**Захват прайса и маркер поколения** (`src/model/locks.py`, §5 модели) — захватывается прайс
ЦЕЛИКОМ, отнять чужой живой захват нельзя. **Аренда 10 минут считается от признаков жизни, а
не от старта**: работающий прогон продлевает её на каждой итерации, поэтому тяжёлая живая
задача захват не теряет, а зависшая теряет. После выполнения задачи захват держится ещё
минуту. Снятие захвата по таймеру **работу НЕ останавливает** — для этого есть отмена
прогона, а от зомби-записи защищает `valid_for`: **проверка обязана стоять непосредственно
перед записью в 1С**, а не только перед сменой статуса, потому что необратима именно запись.
`generation` при снятии захвата НЕ обнуляется — иначе следующий захват совпал бы с номером
отменённого прогона. Время в чистых функциях передаётся явно: иначе тест на истечение аренды
пришлось бы писать через `sleep`.

**Очередь команд** (`src/model/commands.py`, `src/storage/command_queue.py`, §7) — в базе, а
не в памяти: команда, присланная перед остановкой процесса, должна дождаться подъёма.
Схлопываются только присваивания (статус, описание) и только НЕ взятые: перезаписав взятую,
подменили бы то, что исполняется. **«Кто первый» действует на ВСЕ команды** (решение админа
14.09.2026) и считается по времени создания НА СТОРОНЕ ВИЗУАЛА — порядок обхода провайдеров
сделал бы один визуал главнее другого. Взятие помечает, а не удаляет; при старте
`requeue_stale` возвращает взятое (живых взятых быть не может, агент один).

**Модель работы с прайсами** (`src/model/`, `src/storage/model_store.py`,
`specs/agent-workflow-model.md`) — строится рядом с действующим прайсовым потоком и пока на
него НЕ влияет: команд, меняющих состояние, ещё нет. Домен чистый (ни базы, ни бота).
Ключевое: **пустой `Ref` не совпадает ни с чем, включая пустой** — «неизвестно» не равно
«неизвестно»; совпадение адресов идёт по ЛЮБОМУ непустому идентификатору, но марка обязана
совпасть (артикул «A001» бывает у двух поставщиков). `relink` **пересчитывает ссылки на
самый свежий прайс от нуля**, а не правит по одной: инкрементальная правка обязана угадать
все затронутые записи, пересчёт не может их пропустить. `replace_tasks` не переиспользует
старые `id` — «выполни задачу 7» после пересборки должна не найти задачу, а не выполнить
другую под тем же номером. **Уборка сирот обязана объединять пути из ВСЕХ хранилищ**
(`main.py`): забыть модель — значит стереть файл живого прайса, а прайс без файла
существовать не может.

**Справочники поставщиков** (`src/storage/suppliers.py`, `specs/agent-workflow-model.md` §2) —
три уровня: поставщик → сигнатура формата → файл прайса. **UNIQUE по ПАРЕ (поставщик,
сигнатура)**, а не по хешу: скелеты разных поставщиков могут совпасть, и тогда это две записи
у двух владельцев — поэтому `find_signatures` возвращает СПИСОК, и брать первого нельзя.
Поставщик ищется по нормализованному имени (`scope.normalize`), `add_supplier` идемпотентен.
Непустого поставщика удалять нельзя — для дублей есть `merge_suppliers`, он переносит
сигнатуры с файлами и уничтожает источник; совпавшие сигнатуры вливаются, а не дублируются.
Команды — `src/bot/catalog_handlers.py`, отдельный роутер. **Номера в командах сквозные по
полному списку**: фильтр прячет строки, но не сдвигает номера, иначе `/signature_delete 2`
удалял бы разное в разных видах. Файлы с диска справочник не трогает — это дело
`price_files.sweep`.

**Закрытие прогона — за админом** (§9.9) — `_finish_run` без `confirmed=True` НЕ закрывает
прогон: печатает сводку и спрашивает «Закончить работу с этим прайсом?» с одной кнопкой
«Да». Разобрать план и закончить работу — разные события: у админа остаются задачи по тому
же файлу, а закрытие стирает файл и историю, и текст уходит менеджерскому агенту, который
про 1С ничего не умеет. Флаг — `active_price.awaiting_close`, снимается любой новой работой
(`_run`), поэтому вопрос звучит заново. Сводка печатается ОДИН раз — с вопросом. Новый файл
вместо кнопки закрывает прогон сам (`quiet=True`); прайс В РАБОТЕ так не вытесняется.

**Поиск по всей номенклатуре** (`find_1c_items`, `specs/1c/find-items.bsl`, §19.11) —
проверка «нет ли товара в снятых» по выгрузке ТМ видит ТОЛЬКО СВОЮ МАРКУ, а дубль как раз и
возникает, когда товар заведён под другой. Эндпоинт ищет по всей базе, невыгружаемые
включены ПО УМОЛЧАНИЮ (наоборот, чем в `by-tm` — он написан ради снятых), поиск вхождением.
**Зовётся ПАЧКОЙ — `articles` списком, один раз на коллекцию.** Цену определяет число
вызовов, а не объём: круг ручного цикла несёт всю историю и стоит $0.097 (замер на прогоне
Most Floor), сам ответ — $0.0002, разница в 400 раз. Поштучная проверка 53 позиций стоила
бы $5.13 против $0.77 пачкой. **Требует выкладки BSL в 1С.**

**Непомеченные ТМ видны агенту** (§19.10) — `get_selling_tm` отдаёт все марки с признаком
`selling`. Марку заводят раньше, чем помечают к выгрузке, и в этом промежутке под неё уже
создают товары; раньше агент её не видел и писал «заведите» про заведённую. В план по
умолчанию идут только помеченные — но это решение, а не слепота.

**Справочные чтения — один раз за прогон** (`_SEEN_READS`, `_repeat_answer`, §9.6.5) —
папки марки и свойства вида товара за прогон не меняются. Две потери, закрываются порознь:
лишний круг цикла ($0.097) убирает ТОЛЬКО запрет в промпте — к ответу инструмента круг уже
оплачен; повторную выгрузку в истории убирает `_repeat_answer`, отдавая указатель вместо
данных. Второе важнее, чем кажется: `_prune_file_dumps` эти выгрузки НЕ чистит, и повтор
поедет в каждом следующем запросе (свойства вида — 6 688 токенов, дерево без фильтров —
137 063). Указатель обязан называть, что приходило, — безымянному модель не верит. Отметки
сбрасывает `clear_nomenclature_cache`, и это требование, а не побочный эффект: она зовётся
ПОСЛЕ ЗАПИСИ в 1С, а `set_items` заводит папки и значения свойств.

**ЗАПРОСЫ ТЕРЯЛ ТУННЕЛЬ VPN — ЭТО ДОКАЗАНО ЖУРНАЛОМ IIS** (25.09.2026). Запрос, который
снаружи не отдавал ни одного байта (даже заголовков) и обрывался по нашему таймауту
двенадцать раз подряд, в журнале сервера выглядит так:
`by-tm tm=000000005&include_not_exported=1&page=1&size=8 → 200 0 0 time-taken 1176`.
IIS ответил успешно за 1,2 с, ответ пропал в пути. Без VPN тот же запрос идёт так же
быстро, как на самом сервере. За сутки в журнале **13 719 ответов 200** с нулевым
`sc-win32-status`, а самый медленный `by-tm` — **6,8 с на ДВЕСТИ позиций** со снятыми.
Отсюда два следствия. Первое: ни «больных карточек», ни «предела по объёму», ни «дефекта
обработчика 1С» не было — все версии ниже описывают ОДИН и тот же туннель, и держать их
стоит как перечень тупиков, а не причин. Второе: **размер страницы теперь ПОДБИРАЕТСЯ ПОД
КАНАЛ, а не задан константой** (`_page_failed`): клиент начинает с `PAGE_SIZE` = 64 и
ужимает его вдвое, когда крупная страница не дошла ДВАЖДЫ (одиночный провал случаен, и
ужиматься из-за него — остаться на мелкой странице до конца прогона зря). Подобранный
размер живёт до перезапуска процесса и общий на все марки: канал за прогон не меняется, а
отращивать размер пробами нельзя — каждая неудачная проба стоит полного ожидания. Так
снимается выбор между «быстро» и «доедет»: 240 позиций забираются четырьмя запросами там,
где канал их несёт, и тридцатью там, где нет. Сменили канал — перезапустили бота. **Диагноз по симптому «1С не отвечает» ставить нельзя** — только по журналу
IIS (`sc-status` и `time-taken` сразу говорят, чей это провал) и по проверке с самого
сервера через `127.0.0.1`.

**Соединение при этом не переиспользуется** (`OnecClient.__init__`,
`tests/integration_onec_health.py`) — правка 24.09.2026, сделанная по замеру: тридцать ОДИНАКОВЫХ
запросов подряд по одной позиции — двенадцать отвечают за 1,3 с, тринадцатый не отвечает
вовсе; у лёгкого `selling-tm` (0,2 с) молчит КАЖДЫЙ ТРЕТИЙ, с точностью до номера (2, 5,
8, 11…). Решающий замер: у имени ОДИН адрес и один `Microsoft-IIS/10.0`, по общему
соединению гибнет каждый третий, а НОВЫМ СОЕДИНЕНИЕМ на запрос проходят 9 из 9. Сервер
закрывает keep-alive молча — наш сокет жив, запрос уходит в него, ответа не будет никогда.
(Задним числом: «сервером» тут был туннель, но вывод устоял — свежее соединение по битому
пути надёжнее долгого, и после правки провалы исчезли в обеих сериях.)
Тот же обрыв, пришедший честным `WinError 10054`, лечил повтор в `_retry` и был известен
давно; тихий вариант повтором не лечится в принципе. Лечится `max_keepalive_connections=0`:
после него 0 провалов из 30 в обеих сериях. Что НЕ подтвердилось: «больная карточка»
(опрошены по четыре раза — по 1,3 с), «тяжёлая марка» (у неё 83 позиции), «большая
страница» (25 позиций — 3,3 с, одна — 1,6 с; правка `PAGE_SIZE` 200 → 25 лечила не то),
«время жизни сеанса» (вернули 20 с и перезапустили пул — картина не изменилась ни на
запрос), «дохлый рабочий процесс IIS». Терпение в `by_tm_all` при этом ОСТАВЛЕНО: сеть
рвётся и по другим поводам, а цена его — секунды. Устроено оно так: сорвавшаяся страница
**делится ПОПОЛАМ** (`_rescue`), и спуск идёт только в ту половину, которая молчит.
**Повтора страницы НЕТ** — половины это и повторная попытка, и полезная работа сразу, а
повтор стоил второго полного ожидания: в боевом логе сорвавшаяся страница обходилась в
полторы минуты (45 + 45) при цене здоровой в полторы секунды. Разбор по одной (как было
сперва) стоил 25 запросов на страницу и этой нагрузкой сам ронял следующую. Позиция, не
ответившая в одиночку, становится ОШИБКОЙ в выгрузке, а не пропажей: молча потерянную
агент прочтёт как «товара в 1С нет» и заведёт дубль — поэтому повтор остался ровно там,
где решается судьба позиции (`_ask_item`). **Ответ здесь либо быстрый, либо никакой**
(страница из 8 — 1,4 с, из 25 — 3,3 с, позиция — 1,2 с; потерянный запрос не приходит
вовсе), поэтому пределы тесные: `PAGE_TIMEOUT` 12 с — в восемь раз больше самого
медленного виденного ответа, `ITEM_TIMEOUT` 20 с — там цена ошибки выше. **У обработчика
1С есть сочетание, которое не отвечает НИКОГДА** (12 провалов из 12 на здоровом сервисе):
`by-tm?tm=000000005&page=1&size=8&include_not_exported=1`, при том что `size=7` с тем же
флагом приходит за 1,5 с, `size=8` без флага — за 1,7 с, а те же позиции другой
группировкой — за 1,4 с. Ни объём (у другой марки доезжает 21 КБ), ни кеш по URL, ни
карточки (каждая читается по одной) этого не объясняют. **Но и обработчик 1С исправен:**
на самом сервере по `127.0.0.1` тот же запрос и даже `size=150` отдаются за 1,5 с, а
снаружи на провалившемся запросе не приходят ДАЖЕ ЗАГОЛОВКИ — ноль байт, ни строки
статуса, при том что соседний удачный запрос отдаёт 21 491 байт за 1,8 с. Ломается ПУТЬ
между рабочей станцией агента и IIS. Выгрузка исполнителя задач всегда идёт СО СНЯТЫМИ
(проверка дублей), поэтому в неё это сочетание попадает первой же страницей; `PAGE_SIZE`
держим маленьким, пока путь не починен — крупный ответ по нему не проходит. **`PAGE_SIZE` = 8, и это число из замера**: время от
размера почти не зависит (1, 5, 10 позиций — те же 1,1–1,2 с, платим за запрос по марке),
а вот надёжность зависит — на 25 ответ не пришёл дважды подряд; плюс степень двойки
обязательна, иначе половины не лягут на границы страниц. Поднимать только с цифрами от
`tests.integration_onec_health` — он меряет и лестницу размеров.

**Таймаут чтения 1С повторяется ОДИН раз, и только в выгрузке номенклатуры**
(`_page_once_more`). Общее правило ниже — не повторять вовсе — остаётся в силе: повтор
тяжёлого запроса кладёт на базу вторую такую же выгрузку. Но раз сервис теряет каждый
тринадцатый запрос, нулевой повтор терял бы каждую тринадцатую страницу на ровном месте,
а провал лечится ОДНОЙ повторной попыткой. Пять (как было) — это пять тяжёлых выгрузок в
базе и десять минут тишины у админа.

**Таймаут чтения 1С НЕ повторяется** (`client._pointless_to_repeat`). Повтор задумывался
против обрыва keep-alive (IIS рвёт простаивающее соединение — `WinError 10054`), и там он
лечит: сервер ничего не делает. Но `ReadTimeout` значит обратное — запрос ПРИНЯТ и
выполняется, а 1С не отменяет работу, когда клиент отвалился. Повторяя пять раз, мы клали
на базу пять тяжёлых выгрузок вместо одной и сами превращали медленный ответ в
неотвечающий: 24.09.2026 агент молчал десять минут (120 с × 5 + паузы), пока `by-tm` не
отвечал. `ConnectTimeout` повторяется по-прежнему — соединение не установилось, сервер о
нас не знает. Вызовы дольше `SLOW_CALL_SECONDS` пишутся в журнал: долгое ожидание должно
читаться как «идёт by-tm по марке», а не как тишина.

**Учёт расхода токенов** (`token_usage`, `src/agent/usage.py`, §9.6.4) — строка на КАЖДЫЙ
вызов API, не на ход: ход это десятки вызовов. Снимается в `_record_usage` **до ветвлений**
цикла — `pause_turn` и `refusal` тоже оплачены, и учёт только на успешном пути давал бы
тихий недосчёт. Сбой приёмника не имеет права ронять прогон (всё под `try/except`). В базе
ТОЛЬКО счётчики: доллары считаются при показе, иначе смена тарифа исказит историю задним
числом. Множитель кеш-записи здесь **×2** (часовой TTL), а не ×1.25 из умолчания SDK.
Показ — `/tokens` и строка в итоге прогона (считать до `clear_run`: граница суммирования —
`price_run.started_at`). Главное число — доля чтения из кеша: около нуля значит сломанный
префикс, и это дороже любых настроек `effort`.

**Очередь коллекций** (`price_run.stage`) — марка от `BIG_TM_ITEMS` (300) позиций
дробится: `propose_prices` отказывает, пока не вызван `start_tm_collections`. Порог считает
код, не модель. Хвосты строят модульные `queue_tail`/`next_step` в `pricing_tools.py` —
их же зовёт обработчик кнопок, поэтому они не методы класса.

**Отложенные задачи** (`deferred_tasks` + `src/storage/price_files.py`) — наполняются
кнопками «Пропустить»/«Отложить», живут отдельно от `price_run`, потому что переживают его
очистку. Прайс кладётся на диск лениво и удаляется с последней ссылающейся задачей.
Устаревание — ТОЛЬКО по более свежей `price_date`: тот же прайс, присланный заново, задачу
не роняет, иначе возврат к отложенному ломался бы сам собой.

**Итог прогона** (`_finish_run` в `pricing_handlers.py`) — единственное место, где
печатаются отложенные замечания по прайсу целиком (`price_run.notes`, инструмент
`add_final_note`) и строка «обработан полностью». Один выход на оба пути: и после кнопки
на последней марке, и когда по ней нечего было писать. Замечания уровня файла НЕ должны
попадать в предложение по марке — иначе повторяются под каждым брендом.

**Прогон прайса по маркам** (`price_run` в `src/storage/pricing.py`) — предложение
строится на ОДНУ ТМ (`propose_prices` откажет, если передали несколько), в хвосте
«Осталось обработать: …». После нажатия кнопки обработчик сам продолжает диалог следующей
маркой через `_run(..., user_id=...)` — **user_id передаётся явно**, потому что там
`message` это сообщение бота и `from_user` в нём бот, а не админ. Режим прайса и файл в
`_files` живут до конца прогона. Проверка «загружал, но не предложил» (`_unproposed`)
исключает марки ИЗ ПЛАНА — иначе ругается на каждую соседнюю; имя марки берёт из
`_TM_NAMES` (заполняется в `_selling_tm`), а не из первого слова наименования товара.

**Скачки цен** (`unit_warnings` в `src/price_tool/changes.py`) — изменение больше чем в
1.5 раза выносится наверх предупреждений. Причина определяется ПО КОЛЛЕКЦИИ, в порядке:
часть позиций уже стоит новую цену (значит в папке разные товары) → цены внутри папки
разные → и только для однородной коллекции гипотеза «цена за упаковку». Порядок важен:
на Classen отношение 2.02 совпало с упаковкой 1.974 случайно, цена была верной, а
выбивалась одна позиция. Не блокирует запись.

**История диалога по прайсу** (`_prune_file_dumps` в `pricing_handlers.py`) — в истории
остаётся ТОЛЬКО последняя выгрузка листа, прежние заменяются заглушкой. Каждая весит до
40 000 символов и едет в каждый следующий запрос; на прайсе в 12 870 строк история выросла
до 560 000 символов и модель перестала отвечать. Файл лежит в `_files`, кусок перечитывается
через `contains`/`from_row`.

**Ход очереди марок** — `_run` крутит цикл до `MAX_AUTO_STEPS`: если `PricingTools.advanced_to`
выставлен (марка закрыта без кнопки, писать было нечего), обработчик сам переходит к
следующей. Без этого прогон вставал: кнопки нет — значит нет и обработчика, который двинул
бы очередь.

**Плитка** (`plan_items` в `src/price_tool/changes.py`) — у керамики коллекция
неоднородна: настенная, напольная, декоры и бордюры лежат в одной папке с разными ценами.
`propose_prices` принимает `items[{ref, purchase, rrc}]`, тронуты только перечисленные.
`GroupResult.whole` запрещает групповую форму записи для частичной группы — иначе цена
уехала бы на соседние элементы. Разные цены внутри коллекции плитки не считаются
расхождением.

**Чтение прайса** (`render_preview` в `src/price_tool/parser.py`) — до 1500 непустых
строк на лист, дальше подсказка с `from_row`, и `read_price_file` принимает этот параметр.
Лимит в 250 строк резал боевой лист на 394 строки молча, и хвост был недостижим в
принципе. Обрезка по `MAX_TEXT_CHARS` тоже сопровождается явной пометкой.

**Маппинг колонок прайса** (`src/storage/pricing.py`) — ключ **`(signature, sheet)`**, по
строке на лист. Одна строка на файл приводила к тому, что запомненный лист сужал работу
агента до себя, а остальные листы мультилистового прайса молча выпадали. Блок «ЗАПОМНЕННЫЙ
МАППИНГ» в `read_price_file` обязан явно требовать разбора остальных листов. Старая схема
мигрирует в `init()` (лист достаётся из JSON и переезжает в ключ).

**Категории товаров** (`src/price_tool/scope.py`) — что вообще анализируем; задаётся
командами `/categories` один раз на все прайсы. Пустой список = ограничений нет, а не
наоборот. Сопоставление с `product_type` из 1С нестрогое (вхождение подстроки), поэтому
«плитка» покрывает «Керамическая плитка». `propose_prices` проверяет это независимо от
модели.

**Эксклюзивы поставщиков** (`src/price_tool/exclusive.py`) — надпись «эксклюзив» в прайсе
запоминается заявкой (`exclusive_claims`), действующая пометка **выводится** из заявок и
решений админа (`exclusive_decisions`), а не хранится. Спор двух поставщиков в окне 2 мес →
вопрос админу, пометка до ответа не показывается. Список эксклюзивов вкладывается в
системный промпт (`build_system_prompt`), потому что у менеджерского агента нет кодов 1С,
чтобы сопоставить свой ответ с БД. Функция справочная — на цены не влияет.

**Авторизация** (`src/bot/auth.py`) — middleware проверяет whitelist в SQLite (`src/storage/users.py`). `ADMIN_TELEGRAM_ID` из конфига всегда проходит; добавляет `is_admin: bool` в данные обработчика.

**Транскрипция голоса** (`src/bot/handlers.py`) — OpenAI Whisper API (`whisper-1`, `language="ru"`). Требует `OPENAI_API_KEY` в `.env`; без ключа возвращает пояснение пользователю.

**Статус действий** — при каждом вызове инструмента `on_tool` редактирует одно сообщение в чате (не создаёт новые). Маппинг `_TOOL_STATUS` в `handlers.py`.

### Конфигурация

`src/config.py` загружает `.env` через `python-dotenv`. Обязательные переменные: `TELEGRAM_BOT_TOKEN`, `ADMIN_TELEGRAM_ID`, `MAIL_USER`, `MAIL_PASSWORD`, `ANTHROPIC_API_KEY`. Опциональные: `OPENAI_API_KEY` (голос), `MAIL_HOST`, `MAIL_PORT`, `DB_PATH`.

### Системный промпт

`src/agent/prompts.py` кодирует полную логику агента: валидация запроса (бренд + коллекция обязательны, для плитки — размер) → поиск в почте → сайт → 4 формата ответа (основной / случай А / Б / В). Промпт передаётся с `cache_control: ephemeral`.
