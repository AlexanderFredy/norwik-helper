# Спецификация: Контент-менеджер (обновление цен в 1С из прайс-листов)

> **Статус:** черновик. Источник требований — `dev_tasks/content-manager.txt`.
> Базовый спек системы (поиск товаров у поставщиков) — `master-spec.md`; данная функция
> добавляется поверх него и переиспользует те же компоненты (Telegram-бот, оркестратор,
> Email Tool). Существующий функционал не меняется по поведению.
>
> **Доступ:** функция **только для админа** (`is_admin`, `src/bot/auth.py`). Обычным
> пользователям недоступна.

---

## 1. Цель

Настроен обмен «1С ↔ norwik.ru»: товары заводятся в 1С с описанием и ценами, раз в сутки
выгружаются на сайт в XML, скрипт сайта обновляет карточки. Данная функция помогает
**админу** поддерживать цены в 1С в актуальном состоянии по прайс-листам поставщиков:

1. Найти в почте новые прайс-листы поставщиков (за последний месяц, исключая уже
   обработанные).
2. По каждому прайсу узнать у 1С, какие торговые марки (ТМ) из него стоят к выгрузке
   на сайт — работать только с ними.
3. Разобрать цены из прайса (разные форматы), привести к базовой единице измерения товара.
4. Сравнить с текущими ценами в 1С, выявить изменения, оценить средний % по коллекции.
5. Сформировать админу предложение обновить цены; **после подтверждения** — записать
   новые цены в 1С через HTTP-сервис.

> Из прайса берутся **цена закупки** и **РРЦ**; **розничная цена вычисляется** от закупки
> по правилам [`retail-price-rules.md`](retail-price-rules.md) и пишется тем же вызовом
> (§6.4, §10.2).

## 2. Область охвата

### Входит в данную спецификацию
- Отбор писем-прайсов из почты за последний месяц; **ручной** запуск проверки админом.
- **Дедуп**: не обрабатывать повторно прайс, по которому уже применяли/отклоняли изменения.
- Ручной поиск конкретного прайса по поставщику и **примерной дате (±неделя)**.
- Разбор прайсов **разных форматов** (за штуку / за коллекцию / за упаковку; несколько
  колонок видов цен; скидка от РРЦ); приведение к базовой ЕИ.
- **Идентификация поставщика** (§4.5): признаки письма (домен/адрес/название/телефон) →
  поставщик; **любой незнакомый источник — через вопрос админу** «новый или один из
  известных?» со списком всех поставщиков; переименование, накопление алиасов, а также
  **слияние дублей и обратное разделение** (выделить источник в отдельного поставщика).
- **Маппинг колонок → виды цен**, запоминаемый по поставщику (поставщик + сигнатура структуры).
- Сопоставление строк прайса с номенклатурой 1С (агент по совокупности + подтверждение).
- **Выявление расхождений коэффициентов ЕИ** (`alt_units`: фасовка прайса ≠ коэффициент 1С)
  и сообщение админу (§6.3); исправление в 1С — будущий инструмент (§17).
- Проверка «ТМ к выгрузке на сайт», сравнение с текущими ценами 1С, история регистра,
  предложение админу и запись цен (закупка + РРЦ) после подтверждения.
- **Учёт нескольких поставщиков одной ТМ** (§9.4): накопление цен каждого поставщика из
  всех разобранных прайсов, предупреждение «у другого поставщика обычно дешевле» с
  подтверждением перед записью и запоминанием выбора админа.
- **Эксклюзивы поставщиков** (§9.5): надпись «эксклюзив» в прайсе запоминается и
  показывается пометкой после названия во всех отчётах; спор двух поставщиков разрешает
  админ. Справочно — на цены и выбор поставщика не влияет.
- **Режимы работы** (§5.2): «товары+цены» (умолчание), «только товары», «только цены»;
  режим задаёт и набор этапов, и состав замечаний.
- **Правка справочника номенклатуры** (§19) — контракт 1С: новые товары и папки, правка
  полей, перенос снятых с производства. Инструменты — после реализации эндпоинтов.
- Интерфейс компонента интеграции с 1С (чтение цен/истории/ТМ + запись цен).

### НЕ входит (явно отложено)
- **Частные правила розничной цены по ТМ и категориям** — базовое правило задано
  ([`retail-price-rules.md`](retail-price-rules.md) §2), частные — по мере появления (§6 там же).
- **Часть 4** источника — внесение новых товаров в 1С и заполнение описаний
  (`#будет описано позже#`).
- **Часть 5** источника — добавление фото к новым товарам (`#будет описано позже#`).
- **Автоматический суточный планировщик** — в этой итерации запуск ручной (команда админа);
  планировщик добавим позже (§5.1).
- Любые операции записи в почтовый ящик — Email Tool строго read-only (как и раньше).

## 3. Сценарий использования (полный поток)

```
Админ: «Проверь новые прайсы» (команда/сообщение в Telegram)
   │
   ▼
[Э1] Отобрать письма-прайсы за последний месяц (MailKind.PRICE),
     исключить уже обработанные (по message-id) → список прайсов
   │
   ▼
для каждого прайса:
   ├─ [Э1.5] Определить поставщика (§4.5): адрес/домен уже подтверждён → молча
   │        └─ иначе ВСЕГДА спросить: «новый или один из списка?» + весь список
   │           поставщиков (можно и переименовать) → привязать адрес,
   │           чтобы следующие прайсы с него шли без вопроса
   │
   ├─ [Э2] Спросить 1С: какие ТМ из прайса стоят к выгрузке на сайт?
   │        └─ ни одной → пропустить прайс
   │
   ├─ [Э3] Разобрать цены из прайса:
   │        - определить формат (за штуку / коллекцию / упаковку)
   │        - применить сохранённый маппинг колонок (домен+сигнатура)
   │          └─ маппинга нет / неоднозначно → уточнить у админа → сохранить
   │        - привести к базовой ЕИ товара
   │
   ├─ [Э4] Сопоставить строки прайса с номенклатурой 1С (по совокупности)
   │        └─ спорные сопоставления → подтверждение админа
   │        └─ запомнить цены поставщика (§9.4.1) — ВСЕГДА, даже если потом отклоним
   │        └─ запомнить заявки об эксклюзиве (§9.5.1) — тоже ВСЕГДА
   │           └─ спор двух поставщиков → вопрос админу, пометка пока не показывается
   │
   ├─ [Э5] Запросить текущие цены 1С, выявить изменения:
   │        - проверить историю регистра (<1 мес → предупреждение)
   │        - средний % изменения по коллекции
   │        - сравнить с другими поставщиками этой ТМ (§9.4)
   │        - сформировать предложение админу
   │
   ▼
[Э6] «Обновляем цены от [Поставщик] на: -[ТМ] *[коллекция]… ?»
     │   («…но [Поставщик Б] обычно даёт дешевле — занести цены [Поставщик А]?» — §9.4)
     ├─ да  → записать цены (закупка, РРЦ) в 1С → запомнить источник цен и выбор
     │        поставщика → отметить прайс обработанным
     └─ нет → отметить прайс обработанным (отклонено; цены поставщика остались в истории)
```

Сценарий **многошаговый**: между шагами требуется ответ админа (уточнение колонок,
подтверждение сопоставления, финальное подтверждение записи). Требуется хранение состояния
диалога — см. §8 спеки `cart-orders-1c.md` (тот же механизм истории по юзеру).

## 4. Этап 1. Отбор прайсов из почты

### 4.1. Источник писем
- Переиспользуется классификатор `src/email_tool/classifier.py`: тип `MailKind.PRICE`
  (тема → имена вложений → названия листов Excel).
- Поиск через `MailClient.search` (`src/email_tool/client.py`) с `since` = сегодня − 30 дней.
- Чтение вложений — `read_attachment` / `src/email_tool/attachments.py` (xlsx, xls, csv…).

### 4.2. Дедуп (уже обработанные прайсы)

Гарантирует, что прайс, по которому уже принято решение, повторно не обрабатывается и не
предлагается админу.

#### 4.2.1. Ключ и определение «обработан»
- **Ключ** — `message_id` (заголовок письма, §4.4); при отсутствии — `uid` (фолбэк).
- **«Обработан»** = прайс, по которому изменения цен **применены** (`applied`) или
  **отклонены** (`rejected`) админом. Просто просмотренный/разобранный — **не** обработан.
- Дедуп **по письму, не по содержимому**: тот же файл, присланный новым письмом (другой
  `message_id`), считается новым прайсом (осознанное решение, не хэш файла).

#### 4.2.2. Хранилище (SQLite, §12)
```jsonc
// processed_prices
{
  "message_id": "<a1b2@classen.ru>",  // PK; = uid, если заголовок отсутствует
  "uid": "12345",
  "sender_domain": "classen.ru",
  "sender_email": "sales@classen.ru",
  "subject": "Прайс Classen июль",
  "email_date": "2026-07-15",          // дата письма — для поиска ±неделя (§4.3) и аудита
  "status": "applied",                  // "applied" | "rejected"
  "processed_at": "2026-07-31T10:00:00+03:00",
  "summary": { "tm": ["Classen"], "collections": ["Adventure"], "updated": 12, "failed": 0 }  // опц., аудит
}
```

#### 4.2.3. Операции
- **Проверка** (используется в конвейере отбора §4.4, шаг 5): по `message_id` исключить
  записи со `status ∈ {applied, rejected}`, если не задан `include_processed`.
- `mark_price_processed(message_id, status, meta?)` — **upsert** записи. Вызывается:
  - после `set-prices` (§10.5) со `status="applied"` (частичный успех — тоже `applied`,
    детали в `summary.failed`);
  - при отказе админа на предложение (§9.3) со `status="rejected"`.

#### 4.2.4. Повторная обработка
- Обычный отбор (§4.1) обработанные исключает. Явный повтор (исправление) — через
  `include_processed=true` в `find_price_emails` (§4.4); новая отметка **перезаписывает**
  запись по тому же `message_id`.

### 4.3. Ручной поиск конкретного прайса
Админ может попросить найти конкретный прайс, а не сканировать всё:
- по **поставщику** (домен/email/имя из подписи, `parse_signature`);
- по **примерной дате ±неделя** — окно `[дата−7д; дата+7д]` для фильтра писем.

### 4.4. Контракт инструмента `find_price_emails`

Чтение почты — строго read-only (существующий `MailClient`, `BODY.PEEK`, без флагов/записи).

**Параметры (все опциональны):**
| Параметр | Назначение | По умолчанию |
|---|---|---|
| `days` | глубина сканирования (последние N дней) | 30 |
| `sender` | фильтр по отправителю (email/домен) — IMAP `FROM` | — |
| `around_date` | целевая дата для точечного поиска (±7 дней) | — |
| `text` / `subject` | подстрока в теле/теме | — |
| `include_processed` | включать уже обработанные (обычно нет) | false |

**Конвейер (переиспользует существующее):**
1. `MailClient.search(sender?, subject?, text?, since=сегодня−days)` → кандидаты
   (заголовки + текст, **без вложений**), от новых к старым. При `around_date` —
   `since = around_date−7`, верхняя граница `+7` фильтруется на нашей стороне (IMAP
   `SINCE` даёт только нижнюю).
2. Для кандидатов — `MailClient.fetch_message(uid)` (полное письмо с вложениями), чтобы
   получить имена вложений и, для xlsx, `excel_sheet_names` (§`attachments.py`).
3. `classify(subject, attachment_names, excel_sheet_names)` → оставить только
   **`MailKind.PRICE`** (тема → вложения → листы, §`classifier.py`).
4. `parse_signature(body)` → имя менеджера и телефон; из `sender_email` выделить **домен**
   (ключ маппинга, §6.5).
5. Исключить **уже обработанные** по `message_id` (таблица §12), если не `include_processed`.

**Результат (JSON агенту)** — список писем-прайсов, **без содержимого вложений**
(их читает отдельно `read_attachment(uid, filename)`):
```jsonc
[
  {
    "uid": "12345",
    "message_id": "<a1b2@classen.ru>",   // ключ дедупа (§4.2); при отсутствии — uid
    "sender_email": "sales@classen.ru",
    "sender_domain": "classen.ru",         // ключ маппинга колонок (§6.5)
    "sender_name": "Classen Sales",
    "manager_name": "Иван",                // из подписи (может быть null)
    "phone": "+7...",                       // из подписи (может быть null)
    "subject": "Прайс Classen июль",
    "date": "2026-07-15",
    "attachments": ["price_classen.xlsx"],
    "mail_kind": "price",
    "already_processed": false
  }
]
```

**Доработки существующего кода (для реализации):**
- **Добавить `message_id`** в `EmailMessage` (`src/email_tool/client.py`): в `_fetch`
  извлечь `msg.get("Message-ID")` — сейчас поле не сохраняется, а дедуп (§4.2) на него
  опирается; фолбэк на `uid`.
- `search()` — поднять/параметризовать `limit` под месячное сканирование.
- Домен отправителя — из `sender_email` (`split('@')[-1]`, нижний регистр).

### 4.5. Идентификация поставщика

Ответ на вопрос «от кого этот прайс» — предпосылка для всего остального: по поставщику
привязаны маппинг колонок (§6.5), накопленные цены и сравнение «у кого дешевле» (§9.4).

#### 4.5.1. Почему домена (или названия) недостаточно

- **Домен меняется**: переезд на другую почту, ребрендинг, переход на корпоративный домен.
- **Название меняется**: переименование компании, разные подписи у разных менеджеров.
- **Юрлицо не равно поставщику**: одна фирма работает **от нескольких ЮЛ** и периодически
  их меняет. Поэтому **ИНН в признаки не входит вовсе**: в подписях он встречается редко, а
  когда встречается — у одного поставщика их может быть несколько и они меняются, то есть
  признак и не покрывающий, и не стабильный. Поставщик определяется тем, **кем его считает
  админ**, а не юрлицом в реквизитах.
- **Домен бывает общим**: прайсы часто шлют с `mail.ru`, `yandex.ru`, `gmail.com`. Такой
  домен **нельзя** делать признаком поставщика — иначе все поставщики с публичной почты
  склеятся в одного. Для публичных доменов признаком служит **адрес целиком**.

Отсюда: **поставщик — это суррогатный `supplier_id`**, а домен, адрес, название и прочее —
его **признаки** (`supplier_identifiers`, §12.2), которых у одного поставщика может быть
много и которые накапливаются со временем.

#### 4.5.2. Признаки

| Вид (`kind`) | Источник | Роль |
|---|---|---|
| `domain` | домен отправителя (кроме публичных) | **опознающий** — по нему поставщик определяется без вопроса |
| `email` | адрес целиком (в т.ч. для публичных доменов) | **опознающий** |
| `company` | название компании из подписи, нормализованное (§4.5.3) | подсказка |
| `phone` | телефон из подписи (`parse_signature`) | подсказка |
| `signature` | сигнатура структуры прайса (§6.5.2) | подсказка |

- **Опознающий** признак попадает в базу **только после подтверждения админом** (§4.5.4).
  Совпал уже подтверждённый — поставщик определён молча, вопросов нет.
- **Подсказки** к привязке никогда не приводят: они лишь поднимают кандидата вверх списка и
  объясняют админу, почему предложены именно эти варианты.
- `signature` — самая слабая подсказка: прайсы, выгруженные из типовой 1С, у разных
  поставщиков дают одинаковый «скелет».

#### 4.5.3. Нормализация названия компании

Для сравнения (не для отображения): нижний регистр → убрать организационно-правовую форму
(`ООО`, `ОАО`, `АО`, `ИП`, `ТД`, `ТК`, `ГК`) → снять кавычки всех видов → `ё`→`е` →
схлопнуть пробелы. «ООО "Монарх-Логистик"» и «Монарх Логистик» → `монарх-логистик` /
`монарх логистик` — дальше сравнение нечёткое (как в §7.2), результат — **подсказка**, не
готовое решение.

Извлечение из подписи — расширение существующего `parse_signature`
(`src/email_tool/classifier.py`, сейчас достаёт имя менеджера и телефон): добавить
**название компании** (строка с ОПФ или перед контактами).

#### 4.5.4. Алгоритм разрешения

1. Собрать признаки письма: домен/адрес, название, телефон, сигнатура файла.
2. **Адрес или домен уже подтверждён** за поставщиком → это он, вопросов не задаём.
3. **Иначе — всегда спрашиваем админа** (§4.5.5), независимо от того, насколько уверенно
   совпали название/телефон/структура. Никакой автоматической привязки и **никакого
   автосоздания** поставщика.

**Любой новый источник проходит через админа — это правило, а не крайний случай.** Цена
ошибки несимметрична: неверная склейка двух компаний смешивает их цены, и сравнение
«у кого дешевле» (§9.4) начинает врать, причём молча и задним числом. Один вопрос на новый
адрес — приемлемая плата; тем более он задаётся **однократно**: после ответа адрес/домен
подтверждён, и все следующие прайсы с него идут без вопросов.

#### 4.5.5. Диалог с админом

Показываются: реквизиты письма, **подсказки** (кого система считает похожим и почему) и
**полный список известных поставщиков** — привязать можно к любому, не только к
предложенным.

```
Пришёл прайс с адреса sales@monarh-logistic.ru («ООО Монарх-Логистик»,
+7 495 123-45-67). Этот адрес мне не знаком.

Похожие:
  2. Монарх Логистик — совпало название и телефон
  7. ТД Паркет — совпала структура прайса

Все поставщики:
  1. А-Паркет          6. Паркет-Холл
  2. Монарх Логистик   7. ТД Паркет
  3. Мостфлор          8. Флоор Трейд
  4. Оптимум Пол       9. Хоум Флор
  5. Паркет Люкс      10. Эко Ламинат

Это новый поставщик или один из списка?
  • «новый» — заведу как «Монарх-Логистик» (имя можно задать своё)
  • номер или название — привяжу адрес к нему
  • «переименовать 7 в Паркет Трейд» — поменяю имя в списке
```

- **«Новый»** → создаётся поставщик; имя по умолчанию — из подписи, админ может задать своё.
- **Номер/название из списка** → адрес и домен привязываются к нему как подтверждённые
  признаки; следующий прайс с этого адреса определится **молча**.
- **Переименование** — прямо здесь, без отдельной команды (§4.5.6).
- Пока админ не ответил, прайс **дальше не обрабатывается**: без `supplier_id` некуда
  писать наблюдения (§9.4.1) и нечем искать маппинг колонок (§6.5). Остальные прайсы из
  пачки при этом обрабатываются — незнакомый источник не блокирует всю очередь.
- **Длинный список**: при большом числе поставщиков (> ~30) выводить постранично или
  предлагать ввести название — сообщение Telegram ограничено 4096 символами (§13.1).
- Список поставщиков доступен и отдельно, по запросу админа («покажи поставщиков») —
  инструмент `list_suppliers` (§13).

#### 4.5.6. Переименование, смена домена, слияние и разделение

- **Переименование** (`rename_supplier`) — админ может переименовать **любого** поставщика
  из списка, в любой момент: и в диалоге привязки (§4.5.5), и отдельной командой
  («переименуй Монарх Логистик в МЛ Групп»). Прежнее имя **остаётся признаком** `company`,
  чтобы письма со старой подписью по-прежнему поднимали этого поставщика в подсказках.
- **Новое название в подписи** у известного поставщика (адрес совпал, название — нет):
  привязка происходит как обычно, но админа **уведомляем** («Монарх-Логистик теперь
  подписывается как «МЛ Групп» — переименовать?»); отказ ничего не ломает, имя в подписи
  просто добавится как ещё один признак `company`.
- **Смена домена** — это новый адрес, то есть обычный случай §4.5.4: вопрос админу, ответ
  «это Монарх Логистик», новый домен подтверждён. Отдельного механизма не требуется.
- **Слияние дублей** (`merge_suppliers`) — когда выяснилось, что два `supplier_id` это одна
  компания (например, админ по ошибке завёл нового): признаки и данные переносятся на
  выбранного «выжившего», второй помечается `merged_into`. Перепривязать нужно **всё**:
  `supplier_prices`, `price_source`, `supplier_preference`, маппинги колонок. Перед слиянием
  показать админу, что именно сольётся (сколько наблюдений, по каким ТМ, за какой период).
- **Разделение** (`split_supplier`) — обратная операция: админ может **выделить любой
  источник в отдельного поставщика**, если несколько источников оказались склеены по ошибке
  (своей или админа).

##### Разделение: единица, данные, побочные эффекты

**Единица разделения — источник**, то есть опознающий признак `email`/`domain` (§4.5.2):
«выдели `sales@x.ru` в отдельного поставщика». За один вызов можно вынести несколько
источников сразу — они уйдут в одного нового поставщика.

**История переезжает вместе с источником.** Каждая строка `supplier_prices` и `price_source`
хранит `source` — адрес, с которого пришёл прайс (§12.2). Поэтому разделение
детерминировано: переносятся ровно те строки, чей `source` попал в выделяемое множество.
Без этого поля разделить историю было бы нечем — она бы целиком осталась у исходного
поставщика, и накопленные цены выделенного источника пропали бы из сравнения (§9.4).

Что происходит с остальным:
- **Подсказки** (`company`/`phone`/`signature`): переносятся, если встречались **только** у
  выделяемых источников; встречались у обоих — **копируются** обоим (подсказки не обязаны
  быть уникальными, §12.2).
- **Маппинги колонок** (`(supplier_id, signature)`, §6.5) — **копируются** новому
  поставщику, а не переносятся. Маппинг это знание о раскладке колонок; дублировать его
  безвредно, а угадывать, кому он «принадлежит», — нет.
- **Предпочтения** (`supplier_preference`, §9.4.4) по затронутым ТМ **аннулируются**:
  решение «по Classen берём у X» относилось к X, который теперь означает не то же самое.
  Агент сообщает об этом админу и задаст вопрос заново при следующем прайсе.
- Исходный поставщик, оставшийся **без единого** опознающего признака, помечается как
  пустой и в списках (§4.5.5) не показывается.

**Слияние и разделение взаимно обратимы** — именно потому, что каждая строка помнит свой
`source`: ошибочно слитых можно разделить обратно по источникам, ошибочно разделённых —
слить. Единственное, что не восстанавливается автоматически, — аннулированные предпочтения.

Перед выполнением агент показывает, **что именно уедет**: источники, число наблюдений, по
каким ТМ, за какой период, и попадает ли под перенос запись `price_source` (то есть
«цены в 1С сейчас числятся за этим источником»).

#### 4.5.7. Следствие для маппинга колонок (§6.5)

Ключ маппинга меняется с `(domain, signature)` на **`(supplier_id, signature)`**: иначе при
смене домена у поставщика теряется уже настроенный разбор колонок и админа спрашивают
заново. Домен остаётся признаком поставщика (§4.5.2), но ключом больше не является.

## 5. Запуск

### 5.1. Ручной запуск (эта итерация)
- Админ инициирует проверку командой/сообщением в Telegram (напр. `/check_prices`
  или фразой «проверь новые прайсы»).
- Автоматический суточный планировщик (описан в источнике как «раз в сутки») —
  **отложен**: в текущем боте нет планировщика (только aiogram polling). Добавляется
  позже (напр. APScheduler в процессе бота или внешний cron/Task Scheduler, вызывающий
  тот же код).

### 5.2. Режимы работы

Прайс даёт два разных повода к правкам: расхождения в самом справочнике номенклатуры
(§19) и изменения цен (§9). Делать их всегда вместе не нужно — админ переключает режим
командой `/mode`, и режим действует до следующего переключения.

| Режим | Правка справочника | Предложение по ценам | Замечания не про цены |
|---|---|---|---|
| `товары+цены` — **умолчание** | да | да | да |
| `товары` | да | нет | да |
| `цены` | нет | да | **нет** |

**Режим управляет не только этапами, но и составом замечаний.** В режиме `цены` из
предложения уходит всё, что относится к справочнику: расхождения коэффициентов ЕИ (§6.3),
несопоставленные строки прайса, коллекции 1С без строк в прайсе, расхождения названий и
размеров, бренды не в выгрузке. Предложение становится короче, а разбор — дешевле (§9.6.3).

Отсюда требование к контракту `propose_prices` (§13): **два массива замечаний вместо
одного** — `warnings` (про цены) и `item_warnings` (про справочник). Замечания, которые
формирует сам код, классифицируются в коде, а не отдаются на усмотрение модели: иначе
одно и то же наблюдение попадёт то в одну корзину, то в другую.

**Не зависят от режима** и показываются всегда — это состояние системы, а не замечания по
прайсу: «1С не отдала N поз.» (§8.2), «категория не в списке анализируемых» (§6.8),
пометки эксклюзива (§9.5).

В режиме `цены` поля, нужные только для сверки справочника, и каталог свойств (§19.2) не
запрашиваются вовсе.

## 6. Этап 3. Разбор цен из прайса

### 6.1. Форматы прайсов (учесть разнообразие)
- Цена на **конкретный товар** vs на **коллекцию целиком** (все товары коллекции по одной цене).
- Несколько **колонок видов цен** в таблице Excel.
- Поставщик даёт **скидку от РРЦ** — это наша **цена закупки** (закупка = РРЦ − скидка).
- Цена может быть **не за единицу**, а за упаковку/коллекцию → пересчёт к базовой ЕИ (§6.3).

### 6.2. Три вида цен в 1С

| Вид цены | Код 1С | Ключ в `set-prices` | Источник |
|---|---|---|---|
| Цена закупки | `00-000003` | `purchase` | прайс поставщика |
| Розничная цена | `YO-000004` | `retail` | **вычисляется** от закупки (§6.4) |
| РРЦ | `YO-000005` | `rrc` | прайс поставщика |

Из прайса заполняются **только цена закупки и РРЦ**. Розничная цена в прайсах не приходит —
она всегда результат расчёта.

### 6.3. Приведение к базовой ЕИ
- Если цена дана за упаковку/партию/коллекцию — пересчитать к базовой единице измерения
  товара **в том виде, в каком она задана в 1С**.
- **Коэффициенты ЕИ даёт 1С** — поле `alt_units` товара из `by-tm` (§8.2), напр.
  `{"упак": 2.367}` = 1 упаковка = 2.367 м². Приведение: `цена_за_базу = цена_за_упак /
  коэффициент`. Это авторитетный источник, а не только «кол-во в упаковке» из прайса.
- **Выявление расхождений коэффициентов ЕИ** (самостоятельная задача, не только для
  пересчёта): для каждой сопоставленной позиции извлечь из прайса количество базовой ЕИ в
  упаковке (напр. `10шт\2,16` → 2,16 м²/пачка) и сравнить с коэффициентом `alt_units` из 1С.
  Сама сверка — **детерминированная (в коде, с допуском)**, а не свободный текст модели:
  вход — пара `(ref, кол-во_в_упаковке)` от сопоставления, выход — вердикт совпадает/
  расходится. Матч **по размеру важен**: у одной коллекции бывают разные коэффициенты под
  разные типоразмеры (Tarkett Lounge 152×914 → 2.09, 102×914 → 2.04). Расхождение — **ошибка
  данных ЕИ**, о ней **сообщаем админу** (§9.3, отдельная таблица). В будущем — инструмент
  исправления `alt_units` в 1С (§17), сейчас только **выявление**.
- **Новые ЕИ не добавлять** — использовать существующую ЕИ товара в 1С.
- **Диапазон размера не влияет на цену за м².** У ламината, паркетной и массивной доски
  длина/ширина в `size` могут быть заданы **диапазоном** (`800-1200х200х12`,
  `1500х150-200х15`) — доски в упаковке разного размера, но **цена за м² единая**. Такой
  `size` не требует пересчёта цены и не считается расхождением.

### 6.4. Розничная цена

Правила вынесены в отдельный файл — **[`retail-price-rules.md`](retail-price-rules.md)**:
они зависят от категории товара и ТМ и будут меняться чаще остальной спеки. Здесь — только
связь с процессом.

- Розница **вычисляется от закупки** (наценка по порогам) и округляется до рубля. **РРЦ её
  не ограничивает**: если свежая РРЦ оказалась ниже закупки или ниже нашей розницы — это
  сигнал админу, а не корректировка цены.
- **Порог записи 2 %**: если новая розница отличается от текущей меньше чем на 2 %, она
  **не пишется** — чтобы копеечные пересчёты не плодили записи в регистре. На закупку и
  РРЦ порог не распространяется (это факты из прайса, пишем при любом отличии).
- Пересчитывается **только при изменении закупки** — в том же прогоне, от **новой** закупки,
  и пишется тем же вызовом `set-prices` ключом `retail` (§10.2). Обновление одной лишь РРЦ
  розницу не трогает.
- Идёт в общее предложение админу (§9.3) и пишется **только после подтверждения**.
- Правила хранятся в SQLite (`retail_rules`, §12): пустая таблица = розница не считается.

### 6.5. Маппинг колонок → виды цен (запоминаемый)

Запоминаемое описание того, **как из прайса конкретного формата извлечь** идентификацию
товара и цены (закупка/РРЦ). Хранится в SQLite (§12), переиспользуется при следующих
прайсах того же формата.

#### 6.5.1. Ключ маппинга
- **`(signature, sheet)`** — сигнатура структуры прайса (ниже) **плюс имя листа**.
  Сигнатура вычисляется из самого файла и не зависит от того, как поставщик представился в
  этот раз; вход сейчас файловый (§5.1), устойчивого `supplier_id` ещё нет.
- **Лист — часть ключа, а не поле значения.** У мультилистового прайса («Плинтус», «LA»,
  «SPC LVT») на каждом листе свои колонки, и одна строка на файл означает, что запоминается
  только последний разобранный лист. Хуже того — запомненная трактовка **сужает работу
  агента до своего листа**: остальные молча выпадают из обработки.
  > Так и произошло на бою (прайс Монарха, 4 листа, 12.08.2026): админ ответил на вопрос по
  > плинтусу, агент сохранил маппинг листа «SPC LVT» и следующим ходом обработал только его.
  > Лист ламината вместе с ТМ AGT в предложение не попал, и заметить это было нечем.
  > Отсюда же требование к тексту блока «ЗАПОМНЕННЫЙ МАППИНГ»: он обязан явно говорить, что
  > остальные листы разобрать всё равно нужно (§6.5.5).
- `supplier` хранится рядом **справочно** — чтобы показать админу, чей это формат.
- `supplier` хранится рядом **справочно** — чтобы показать админу, чей это формат.
- Когда появится справочник поставщиков (§4.5), ключ станет парой
  **`(supplier_id, signature)`**: у одного поставщика бывает несколько форматов, а один
  формат (типовая выгрузка 1С) — у нескольких поставщиков. До тех пор совпадение «скелетов»
  у двух разных поставщиков дало бы общий маппинг — риск принят осознанно: на реальных
  прайсах (Монарх / Most Floor / LINDERWOOD) сигнатуры различаются.

#### 6.5.2. Сигнатура структуры (детерминированная)
Реализация — `src/price_tool/signature.py`.

- Считается по «скелету» файла, **без числовых данных**: для каждого листа — его имя и
  верхние **текстовые** строки (заголовки, шапка, названия разделов).
- **Строка, где есть хоть одна чисто числовая ячейка, считается данными и в скелет не
  входит.** Иначе в ключ попадали бы цены и артикулы, и маппинг терялся бы с каждым новым
  прайсом — проверено тестом.
- **Цифры внутри текста заменяются на `#`**: «Прайс ОПТ с 20.07» и «Прайс ОПТ с 25.08»
  дают одну сигнатуру, иначе ежемесячная дата в шапке ломала бы запоминание.
- Нормализация ячеек: `strip` → нижний регистр → схлопывание пробелов; пустые отбрасываются.
- **PDF-прайсы** (таблиц нет) — скелет строится по верхним текстовым строкам извлечённого
  текста, теми же правилами. Без этого именно pdf-прайсы, где и встретилась неоднозначность
  колонок, не могли бы запомнить маппинг.
- `signature = sha1(json({sheets:[{name, headers:[...normalized...]}]}))` (детерминированный
  порядок). Тот же формат → та же сигнатура → маппинг подхватывается автоматически; изменили
  шапку/листы → другая сигнатура → спрашиваем заново.
- Хрупкие места (объединённые ячейки, многострочные заголовки) — §16.

#### 6.5.3. Схема записи маппинга (значение)
```jsonc
{
  "sheet": "Прайс",             // лист с таблицей цен (имя или индекс)
  "header_row": 2,               // индекс строки заголовков
  "identity": {                  // как опознать товар в строке
    "mode": "item",              // "item" (цена на товар) | "collection" (цена на коллекцию)
    "columns": { "article": "Артикул", "name": "Наименование",
                 "collection": "Коллекция", "size": "Размер" }  // ссылки по имени колонки; лишние опускаются
  },
  "prices": {                    // источник каждого вида цены (передаём только заполняемые)
    "purchase": { "source": "column", "column": "Закупка" },
    // либо закупка из скидки от РРЦ: { "source": "discount_from_rrc", "column": "Скидка %" } | { "source":"discount_from_rrc","percent":15 }
    "rrc":      { "source": "column", "column": "РРЦ" }
  },
  "unit": {                      // база цены (§6.3)
    "basis": "base_unit",        // "base_unit" | "package"
    "pack_factor_column": "Кол-во в упаковке"  // либо "pack_factor": 2.4 — для пересчёта к базовой ЕИ
  },
  "product_type_hint": "Ламинат" // опц. подсказка типа (§6.6); тип всё равно проверяется при матчинге
}
```
- Колонки ссылаются **по имени заголовка** (стабильнее индекса, согласовано с сигнатурой).
- Из прайса маппятся только `purchase`/`rrc`; `retail` в прайсе не бывает — она считается
  по [`retail-price-rules.md`](retail-price-rules.md) (§6.4).

#### 6.5.4. Инструменты (SQLite)
- `get_price_mapping(supplier_id, signature)` → запись §6.5.3 или `null`.
- `save_price_mapping(supplier_id, signature, mapping)` → upsert по `(supplier_id, signature)`.

#### 6.5.5. Поток разрешения
1. Разобрать файл → вычислить `signature` (§6.5.2); `supplier_id` уже определён на входе
   письма (§4.5) — без него разбор не начинается.
2. `get_price_mapping` → если запись есть, **применить** её к строкам прайса.
3. Если **нет** или **неоднозначно** (несколько колонок под один вид цены, неясные
   заголовки, per-упаковка/скидка) — агент предлагает трактовку, **уточняет у админа**
   (какая колонка = какой вид цены, item/collection, база ЕИ), затем `save_price_mapping`.
4. Далее сохранённый маппинг применяется автоматически к прайсам той же сигнатуры.

### 6.6. Определение `product_type` из прайса

`by-tm` по одной ТМ может вернуть товары **разных `product_type`** (напр. у бренда есть и
ламинат, и плинтус/подложка). Тип определяет, с каким подмножеством товаров сопоставлять
(§7) и по какой ЕИ пересчитывать (§6.3), поэтому его нужно определить **до** матчинга.

**Канонические значения.** `product_type` — из значений `by-tm` (§8.2) **для этой ТМ**
(набор реально присутствующих типов). Определение — это **выбор из этого набора**, не
свободный текст: нормализованное сравнение (регистр/пробелы).

**Сигналы определения** (по убыванию надёжности):
1. **Явное указание** в прайсе: имя листа / раздел-заголовок в таблице / имя файла / тема
   письма (напр. лист «Ламинат», «Плинтусы»).
2. **Состав строк**: наименования/артикулы строк совпадают с товарами конкретного типа
   из `by-tm`.
3. **Единственный тип** у ТМ в `by-tm` → тривиально он.
4. **`product_type_hint`** из сохранённого маппинга (§6.5.3) для этой сигнатуры (при
   стабильном формате поставщика).

**Несколько типов в одном прайсе.** Если файл покрывает несколько типов (разные листы/
разделы) — **разбить** прайс на части по типам; каждую обрабатывать со своим подмножеством
`by-tm` и своей ЕИ. В предложении отразить, к каким типам отнесены цены (§9.3, предупреждение).

**Неоднозначность / несоответствие.** Если тип не выбирается однозначно из набора ТМ или
строки не бьются ни с одним типом — **уточнить у админа** и сохранить выбор в маппинг
(`product_type_hint`, §6.5.3), чтобы не спрашивать снова для той же сигнатуры (при
многолистовом прайсе подсказка может быть **на лист**).

**Использование ниже по потоку.** §7 фильтрует кандидатов по выбранному `product_type`;
§6.3 пересчёт к базовой ЕИ выполняется относительно `unit` товара **этого** типа.

### 6.7. Контракт разбора файла прайса (парсинг)

Разбор — поверх существующего `src/email_tool/attachments.py`.

**Форматы:** `.xlsx` (openpyxl), `.xls` (xlrd), `.csv` — основные; `.pdf`/`.docx` (таблицы) —
частично. Легаси `.doc` не поддерживается (возвращается сообщение). Ошибки парсинга **не
бросаются** — как в `extract_text`, возвращается понятная ошибка/пометка.

**Два представления одного файла:**
1. **Текстовое** — `extract_text` (через инструмент `read_attachment`): листы
   `=== Лист: <name> ===`, строки таб-разделены, ячейки строками, до 2000 строк/лист. Для
   интерпретации агентом (какие колонки/что за прайс).
   - ⚠️ `read_attachment` **обрезает до 30000 символов** (`tools.py`) — для крупного прайса
     этого мало. Для разбора цен нужен **полный** доступ → представление (2).
2. **Структурное** — рекомендуемый хелпер `parse_price_table(content, filename)` на тех же
   движках (openpyxl `data_only=True`, xlrd), **без 30k-обрезки**:
   `{sheets:[{name, rows:[[cell,...]]}]}`. Источник для **сигнатуры** (§6.5.2) и извлечения
   значений **по маппингу** (§6.5.3).

**Правила разбора:**
- **Значения, не формулы** — `data_only=True` (openpyxl отдаёт вычисленное).
- **Обнаружение шапки** — найти строку заголовков (первая непустая «шапка» с ожидаемыми
  метками); её индекс → `header_row` (§6.5.3). Данные — строки ниже.
- **Числа** — терпимо к десятичной запятой (`1140,75`), пробелам/nbsp в разрядах
  (`1 140,75`), символам валюты; нормализовать в число. Нечисловая/пустая цена → позиция в
  отчёт админу, не молча.
- **Фильтрация строк** — пропускать пустые и разделительные/категорийные строки (без
  идентификатора/цены).
- **Несколько листов** — файл может содержать несколько листов (коллекции/типы); разбирать
  каждый, `product_type` — по §6.6.
- **Единицы/упаковка** — пересчёт к базовой ЕИ по `unit` маппинга (§6.3, §6.5.3).
- **Баннеры-картинки как разделители брендов/разделов** — поставщики часто вставляют
  название второго бренда **картинкой** (не текстом); `read_only` её не видит, и коллекции
  после баннера ошибочно попадают к предыдущему бренду. Извлекать встроенные изображения с
  позицией (openpyxl без `read_only`, `ws._images` → строка-якорь + байты) и вставлять
  нумерованный маркер «⟨ИЗОБРАЖЕНИЕ #N⟩». **Само наличие картинки НЕ означает смену бренда**
  (бывают фото товара, логотипы, декор) — нужно **проверить содержимое**: картинка
  прикладывается к запросу и мультимодальная модель определяет, есть ли на ней **название
  бренда** (альтернатива — OCR); смена бренда — только при подтверждённом баннере. Пример:
  Most Floor — баннер «A+ Floor» на строке 93, коллекции после него — A+ Floor (в 1С не
  выгружается).
- **Длинные листы** — превью листа отдаёт до 1500 непустых строк; если строк больше,
  в конце стоит подсказка с `from_row`, и агент обязан дочитать остаток тем же
  инструментом. Прежний лимит в 250 строк резал боевой лист (394 строки) молча, без
  способа добраться до хвоста: коллекции ниже среза для сопоставления не существовали.
  Обрезка общего текста по `MAX_TEXT_CHARS` тоже больше не молчаливая — к тексту
  дописывается пометка, что это не конец прайса.
- **Большие прайсы (тысячи строк)** — читать подряд нельзя: каждая выгрузка остаётся в
  истории диалога и уезжает в каждый следующий запрос к модели. На боевом файле в 12 870
  строк история за три хода выросла до 560 000 символов, после чего модель перестала
  отвечать вовсе. Поэтому: `contains` ищет НОМЕРА строк с нужным брендом, `from_row`
  читает только его раздел, а старые выгрузки вычищаются из истории (§12.1).
- **«Широкие»/битые строки** — строки с сотнями пустых или продублированных ячеек (ошибки
  экспорта Excel) обрезать (хвостовые пустые + лимит ячеек в строке), иначе раздувают вход.

**Хрупкие места (§16):** объединённые/многострочные ячейки шапки (openpyxl `read_only`
отдаёт `None` для вторичных ячеек объединения) — влияет на сигнатуру и обнаружение шапки.

### 6.9. Повторная присылка того же прайса

Два разных кеша, и путать их нельзя.

**Кеш разбора** (`_PARSED` в `parser.py`) — про время, не про токены. Файл на 12 870 строк
разбирается 0.5 c, а за один `read_price_file` это случалось дважды (в самом чтении и
внутри `price_signature`) плюс отдельное открытие книги ради картинок — около 1.7 c на
вызов и ~минута за прогон. Токенов кеш не экономит: за них платят при **передаче текста
модели**, а текст всё равно надо отправить. Отдаётся **копия**: вызывающие вставляют в
строки маркеры картинок, и общий объект поехал бы вместе с сигнатурой файла.

**Раскладка** (`price_layout`) — про токены. Ключ = сигнатура файла, поэтому ТОТ ЖЕ прайс
узнаётся при повторной присылке, и разведка «какой бренд в каких строках» не повторяется:
`read_price_file` сразу отдаёт сохранённый список разделов. Пишется из `start_price_run`
(там же агент указывает `first_row`/`last_row`), читается при чтении файла.

**Инвалидация одна на оба**: прайс **новее** от того же поставщика отменяет прежнюю
раскладку. Тот же прайс, присланный заново, её сохраняет — ровно ради этого случая всё и
заведено (это же правило, что у отложенных задач, §9.7).

### 6.10. Очень крупный прайс: спросить до того, как тратиться

Прайс Артисана (12 870 строк) обошёлся примерно в **570 тыс. входных токенов** за прогон.
Такое решение принимает админ, зная цифру, а не узнаёт о ней из счёта.

- Порог — **`BIG_PRICE_ROWS = 5000`** непустых строк по всем листам, считает код при
  первом `read_price_file`. Порог намеренно высокий: обычный прайс в него не попадает,
  вопрос должен быть редким.
- Сработал — **таблица в ответ НЕ отдаётся** (платить за неё до решения незачем), вместо
  неё блок с числом строк и оценкой стоимости. Оценка линейная от замера:
  `строки / 12 870 × 570 000`.
- Агент задаёт админу ровно один вопрос: **обработать или пропустить** — и вызывает
  `set_price_decision` (`process` | `manual`).
- **`manual` — это НЕ «Отложить» (§9.7).** Отложенное ждёт возврата и лежит в `/deferred`;
  пропущенный крупный прайс **считается обработанным**: в отложенные не идёт, бот выходит
  из режима и говорит, что цены админ обновит вручную. При повторной присылке того же
  файла разбор не начинается — бот напоминает о принятом решении.

**Ключ решения — хеш СОДЕРЖИМОГО файла, а не сигнатура формата.** Сигнатура (§6.5.2)
считается по скелету — листы плюс шапка, без данных, — поэтому прайс того же поставщика за
следующий месяц имеет ту же сигнатуру. По ней решение «обрабатываю вручную» молча
перешло бы на новый прайс, а раскладка (§6.9) отдала бы вчерашние номера строк под сегодняшние
данные. Обе таблицы (`price_layout`, `price_decisions`) ключуются хешем; старые версии
пересоздаются при `init()` — терять там нечего, кеш восстановится сам.

### 6.8. Категории товаров, которые анализируем

Прайс поставщика шире нашего ассортимента: рядом с ламинатом и плиткой в нём годами лежат
плинтус, подложка, аксессуары, стеновые панели. Разбирать их незачем — а отвечать про них
админу заново в каждом прайсе тем более.

**Список задаётся один раз и действует на все прайсы** (`product_scope`, §12.3), а не
указывается при каждом файле. Админ добавляет и убирает категории командами (§13.2).

- **Пусто = ограничений нет**, а не «не анализировать ничего». Иначе свежая установка молча
  перестала бы обрабатывать прайсы, и понять почему было бы нечем. Переход «пусто → первый
  элемент» меняет смысл на «только это», поэтому сопровождается предупреждением админу.
- **Сопоставление нестрогое**: в 1С вид товара называется «Керамическая плитка», админ
  напишет «плитка». Совпадение — вхождение одной нормализованной строки в другую
  (регистр, пунктуация, `ё`→`е` снимаются).
- **Что сравнивается** — `product_type` товара из `by-tm` (§8.2). Реальный набор значений в
  базе на 14.08.2026: Керамическая плитка, Ламинат, Обои, Двери межкомнатные, Виниловый
  ламинат, Паркетная доска, Штучный паркет, Массивная доска, Керамогранит. Плинтуса и
  подложки среди них нет — эти разделы прайса в 1С не заводятся вовсе.
- **Поведение агента**: разделы и листы вне списка не разбираются и не сопоставляются;
  в предупреждения идёт одна короткая строка «в прайсе также есть: плинтус, подложка».
  Вопрос админу по ним не задаётся — он уже ответил списком.
- **Проверка на стороне кода**: `propose_prices` независимо от модели отбрасывает группу,
  чей `product_type` вне списка, и пишет об этом в предупреждения. Модель не может обойти
  ограничение, даже если передаст такую коллекцию.

## 7. Этап 4. Сопоставление строк прайса с номенклатурой 1С

В прайсе, в отличие от заказа из корзины, **нет кода `1c`** — строки прайса сопоставляются
с товарами из `by-tm` (§8.2) по совокупности признаков.

### 7.1. Множество кандидатов
- Только товары **выбранного `product_type`** (§6.6) в рамках **ТМ** (§8.1) — фильтр до
  матчинга сужает кандидатов.
- Поля `article/size/collection` в 1С заполнены **часто, но не всегда** → усиливающие
  сигналы, не обязательные; `name` — **всегда**, но с отклонениями в написании.

### 7.2. Нормализация (обе стороны перед сравнением)
- `strip` → нижний регистр → схлопывание пробелов; единый вид латиница/кириллица-двойников;
  срез хвостовых артикул-суффиксов из `name`; для `article` — `strip` и сравнение без
  лидирующих нулей/регистра.

### 7.3. Сигналы и приоритет
1. **Точное по `article`** — если заполнен и в 1С, и в прайсе (сильнейший сигнал).
2. **`size` + `collection` + декор** — комбинация структурных полей.
3. **Fuzzy по `name`** — всегда как основа/фолбэк (сходство строк с учётом §7.2).
- **`size`** — формат `Д×Ш×Т` в мм; Д/Ш могут быть **диапазоном** (`800-1200х200х12`, §6.3);
  сравнивать с учётом диапазонов (пересечение/вхождение), диапазон ≠ расхождение.

### 7.4. Уверенность (порог «уверенно» vs «спорно»)
Для каждой строки прайса — статус матча:
- **`confident`** (авто-принять): **точное совпадение `article`**, **или** единственный
  кандидат с высоким сходством `name` **и** непротиворечивыми `size`/`collection`.
- **`disputed`** (спросить админа): несколько близких кандидатов (малый отрыв лидера),
  низкое сходство `name`, либо **противоречие** структурных полей (size/collection не бьются).
- **`unmatched`**: ни одного подходящего кандидата.
- **Порог** (стартовые значения, тюнингуются — §16): сходство `name` ≥ ~0.9 и отрыв от 2-го
  кандидата ≥ заметного зазора → `confident`; иначе `disputed`. Точные значения — §16.

### 7.5. Результат сопоставления (внутренний)
```jsonc
{
  "price_row": { /* исходная строка прайса: наименование, article, size, цена */ },
  "status": "confident",              // confident | disputed | unmatched
  "ref": "YO-00075249",               // null для unmatched
  "candidates": [ {"ref": "...", "score": 0.93}, ... ],  // для disputed — на выбор админу
  "reason": "article exact"           // краткое обоснование
}
```

### 7.6. Проверки и подтверждение
- **`parent` vs `collection`**: `parent` — имя родительской папки, обычно = коллекция; при
  **явном несоответствии** (или между прайсом и папкой) — **предупредить админа** до
  обновления (в предложении §9.3), не блокируя молча.
- **`disputed`** — показать админу кандидатов (§7.5) на выбор/подтверждение; **`unmatched`**
  — вынести в предупреждения (§9.3), в запись **не** попадают.
- В `writes` (§9.3) и запись (§10) идут **только `confident`** и **подтверждённые** админом
  `disputed`.
- Цена — относительно ЕИ (`unit`) товара 1С (§6.3).

---

### 7.7. Плитка: коллекция неоднородна

У ламината коллекция — это один декор в разных цветах, и цена на неё одна. **У
керамической плитки и керамогранита это не так.** В одной коллекции лежат элементы разного
назначения и формата: настенная, напольная, декор, панно, бордюр, вставка, ступень,
подступёнок. У каждого своя цена, свой размер и свой код в 1С.

Отсюда следствия, зафиксированные в промпте (§14), чтобы агент не спрашивал об этом на
каждом прайсе:

- **Цена задаётся поэлементно.** В `propose_prices` группа несёт `items[{ref, purchase,
  rrc}]` вместо `purchase`/`rrc` на всю коллекцию. Тронуты будут **только перечисленные**
  товары; остальные в папке остаются как есть.
- **Идентификация — по совокупности**: размер (`size`: 30x60, 60x60) + тип элемента +
  название декора и артикул. Без размера и типа элемента «Мадейра» — это сразу несколько
  разных товаров с разными ценами.
- **Разные цены внутри коллекции плитки — норма**, а не расхождение: в предупреждения они
  не выносятся, вопрос админу не задаётся.
- **Групповая форма запроса (§10.2 «а») к частичной группе не применяется.** `GroupResult`
  несёт признак `whole`; если группа покрывает не всю папку, payload собирается
  по-товарно, даже когда цена у всех перечисленных одинаковая. Иначе запись задела бы
  соседние элементы коллекции с их собственными ценами.
- Строки прайса, для которых товар в 1С не опознан однозначно, идут в `warnings` как
  несопоставленные; разбор марки на них не останавливается.

## 8. Этап 2. Чтение из 1С: ТМ к выгрузке и номенклатура с ценами

Все операции чтения — через существующий HTTP-сервис 1С, база
`/api_shop/hs/ai-tools/`. **Аутентификация — заголовок `X-API-Token: <токен>`** во всех
запросах. Обе операции ниже **уже реализованы** и проверены на боевом сервере.

### 8.1. Проверка выгрузки ТМ на сайт (`selling-tm`)
- `GET .../get-products/selling-tm` → все торговые марки, стоящие **к выгрузке на сайт**
  (каскад «Не выгружать» уже учтён на стороне 1С). Без параметров и пагинации.
- По ТМ, встретившимся в прайсе, оставляем только те, что реально выгружаются; поле `Code`
  ТМ — вход для `by-tm` (§8.2).

**Формат ответа** (реальный, проверен на бою — 168 ТМ):
```jsonc
// Ответ — JSON-массив объектов (+ UTF-8 BOM), без пагинации:
[
  {"NameTM": "Classen / Классен", "Code": "000000104"},  // NameTM — наименование ТМ (лат/кир)
  {"NameTM": "Egger / Эггер",     "Code": "000000006"}   // Code   — уникальный код ТМ (строка) → tm= в by-tm
  // ... 168 записей
]
```
- Поля именованы `NameTM` / `Code` (с заглавной); `Code` — **строка** (ведущие нули важны),
  это **Код** `Справочники.Производители` (на записи — `tm`, §10.4, `НайтиПоКоду`).
- Порядок записей не гарантирован (не алфавитный) — сортировать/индексировать на нашей стороне.
- **Аутентификация обязательна**: без валидного `X-API-Token` сервис отвечает **HTTP 500**
  (HTML-страница IIS), а не 401/403 — коннектор должен трактовать не-JSON/500 как ошибку авторизации/сервиса.

**Контракт проверки (инструмент `check_1c_trademarks_export`):**
- **Вход** — ТМ/бренды, встретившиеся в прайсе (из разбора + маппинга §6.5): обычно
  строки-наименования (напр. `"Classen"`), кода ТМ в прайсе нет.
- **Процесс**:
  1. получить список `selling-tm` (168 записей); закэшировать на время хода/прогона
     (список небольшой, тянуть один раз);
  2. **сопоставить** бренд из прайса с `NameTM` — нормализованно: `NameTM` бывает
     двуязычным (`"Classen / Классен"`), с суффиксами/регистром → сравнивать по частям
     (split по `/`), нижний регистр, латиница/кириллица, без лишних пробелов;
  3. для найденных — вернуть `Code` (для `by-tm`, §8.2).
- **Выход**: список `{brand_from_price, matched: bool, name_tm, code}`.
- **Фильтрация**: работаем **только** с ТМ, найденными в `selling-tm` (реально
  выгружаются). Бренды прайса, которых **нет** в `selling-tm`, — **пропустить** и внести в
  предупреждения предложения (§9.3), чтобы админ видел, что по ним цены не обновлялись.
- **Неоднозначность** сопоставления бренда (несколько кандидатов / нет точного) →
  уточнить у админа, как и спорные сопоставления товаров (§7).

### 8.2. Номенклатура одной ТМ с ценами (`by-tm`)
Основной источник данных для сопоставления (§7) и сравнения цен (§9).

- `GET .../get-products/by-tm?tm=<код ТМ>&page=<N>&size=<200>` — `tm` = **код ТМ** из
  `selling-tm`; пагинация — `page` (с 1) и `size` (напр. 200).
- Возвращает **только экспортируемые** товары: каскад флага **«Не выгружать»**
  разрешается **на стороне 1С** тем же механизмом, что и `selling-tm` (единый источник
  истины, дерево в Python не дублируем).
- **Цены — inline**: срез последних из регистра сведений по ВидЦен ∈ {Закупка, РРЦ}
  (**розницу `YO-000004` нужно добавить** — §16.1b);
  `date` = период активной записи = когда цена менялась в последний раз (сразу закрывает
  проверку «<1 мес» из §9.2 — отдельного запроса истории не нужно).

**Формат ответа** (реальный, проверен на ТМ Classen — 241 товар, 2 страницы):
```jsonc
// Ответ — JSON-объект «шапка + items» (+ UTF-8 BOM):
{
  "tm": "Classen / Классен",
  "total": 241,
  "offset": 1,            // = номер запрошенной страницы (page)
  "limit": 200,           // = size
  "items": [
    {
      "ref": "YO-00075249",           // Код/ссылка 1С — стабильный ключ для записи цен
      "id": "106754",                 // ID сайта — строка
      "name": "Ламинат Classen  VisioGrande WR  Мягкий Хлопок Белый",  // всегда заполнено
      "article": "56649 ",            // бывает "" или с хвостовыми пробелами (не null)
      "unit": "м2",                   // базовая ЕИ (для пересчёта цены, §6.3)
      "size": "604x280x8",            // на практике заполнен у всех
      "product_type": "Ламинат",       // вид товара
      "collection": "Visiogrande",     // очищенное имя коллекции
      "parent": {                      // папка-родитель (≈ коллекция)
        "code": "YO-00075139",         //   Код 1С → collection_ref для set-prices, форма (а)
        "name": "Classen Visiogrande"  //   сырое имя папки
      },
      "alt_units": [ {"упак": 2.367} ],// коэффициенты иных ЕИ к базовой: 1 упак = 2.367 м²
      "prices": [
        {"purchase": {"value": 960,     "date": "2026-07-14"}},
        {"rrc":      {"value": 1140.75, "date": "2026-06-07"}}
        // элемент ОТСУТСТВУЕТ, если по этому виду цены записи нет (не null)
      ]
    }
  ]
}
```
- Иерархия уже разложена в поля (`product_type/collection/parent/size/article`) — агенту
  удобно матчить строки прайса, не разбирая дерево.
- **`size`** — мм, формат `Д×Ш×Т`; у ламината/паркетной/массивной доски Д и Ш могут быть
  диапазоном (`800-1200х200х12`) — цена за м² при этом единая (§6.3).
- **`alt_units`** — массив синглтонов `[{ЕИ: коэффициент}]` (как `prices`): коэффициент иной
  ЕИ к **базовой** (`unit`). Напр. `{"упак": 2.367}` = 1 упаковка = 2.367 м². Используется
  для пересчёта цены-за-упаковку к базовой ЕИ и **сверки фасовки** с прайсом (§6.3).
- **`parent`** — объект `{code, name}` папки-родителя: `name` — сырое имя (обычно =
  коллекция), расхождение `parent.name`/`collection` → предупредить админа (§7, §9.3);
  `code` — **Код** папки в `Справочники.Номенклатура`, он же **`collection_ref`** для
  групповой записи цен по коллекции (§10.2). Группировать по имени нельзя: одинаковые
  названия коллекций встречаются под разными ТМ.
  > Ранняя версия сервиса отдавала `parent` строкой — коннектор понимает обе формы,
  > но при строке `collection_ref` пуст и форма (а) недоступна.
- **`product_type`** — в пределах одной ТМ может быть **несколько** типов; фильтровать при
  сопоставлении (§6.6, §7).
- **`ref`** (Код 1С) — ключ для последующей записи цен (§10), не зависит от наименования.
- **Нормализация на нашей стороне** (Python-коннектор): читать `items` прямо из объекта
  ответа; `article` → `strip()`; `prices` (массив синглтонов) → словарь `{purchase?, rrc?}`;
  `id` — строка; учесть BOM (`utf-8-sig`). Наблюдения по Classen: `size` и `purchase` —
  у всех 241; без `article` — 33; без `rrc` — 10.

### 8.3. Рекомендация по запросу в 1С (для разработчика HTTP-сервиса)
- `Справочник.Номенклатура`: отбор `Производитель = &ТМ`, `ЭтоГруппа = Ложь`,
  `НЕ ПометкаУдаления`.
- **Экспортируемость**: исключить элементы, у которых любой родитель имеет «Не выгружать» —
  переиспользовать функцию/признак из `selling-tm` (желательно материализованный признак,
  чтобы не обходить дерево на каждый элемент).
- **Иерархия**: подъём по `Родитель` → коллекция (непосредственная папка) и вид товара
  (папка под корнем «Товары и услуги»); ТМ — напрямую из `Производитель`.
- **Цены**: соединение с `РегистрСведений.<Цены>.СрезПоследних(, ВидЦен В (&Закупка,&РРЦ))`
  по `Номенклатура`; вернуть Цена и Период.
- **Пагинация**: по `page`/`size` (`ВЫБРАТЬ ПЕРВЫЕ size` со смещением `(page-1)*size`,
  устойчивая сортировка по Коду/Ссылке); в ответе отдавать `total` (реализовано).

### 8.4. Потребление агентом (без перегруза контекста)
- Инструмент чтения возвращает **один пакет `size`** позиций; оркестратор
  (`src/agent/orchestrator.py`, ручной loop) листает страницы (`page`) по `total`.
- Scoping: ТМ из прайса ∩ `selling-tm`. На практике ТМ ≈ до ~241 товара (Classen) → 1–2
  страницы по 200, фильтрацию по коллекции делаем **на нашей стороне** после выборки
  (параметр `collection` в эндпоинте пока не подтверждён).

## 9. Этап 5. Сравнение цен и предложение админу

### 9.1. Выявление изменений
Текущие цены (закупка, РРЦ) уже пришли **inline** в `by-tm` (§8.2) — отдельный запрос не
нужен. Сравнение — **по каждому сопоставленному товару (§7) и каждому виду цены** отдельно.

- **Вход позиции**: товар 1С (`ref`, `unit`, текущая `prices.purchase/rrc` = value+date) +
  новая цена из прайса (после пересчёта к базовой ЕИ, §6.3), по видам, которые даёт маппинг.
- **Порог значимости — 2 %, для всех видов цен** (закупка, розница, РРЦ):
  `|новая − текущая| / текущая < 2 %` → изменение **не пишется**. Копеечные колебания
  прайса (наблюдалось `1070 → 1069,93`) иначе плодили бы записи регистра за каждый новый
  день, ничего не меняя по сути.
  - Порог **не применяется**, если цены этого вида в 1С ещё нет — первая запись идёт всегда.
  - Значение порога — в конфиге (`PRICE_MIN_CHANGE_PCT`, §15).
- Классификация по виду цены:
  - `changed` — текущая цена есть и отличается **на 2 % и больше**;
  - `new` — в 1С по этому виду цены записи нет (`rrc`/`purchase` отсутствует в `by-tm`) →
    значение из прайса записывается как новое;
  - `unchanged` — равны **или отличаются меньше чем на 2 %** → **пропустить** (в запись §10
    не попадает).
- **Запись изменения** (внутренняя):
```jsonc
{
  "ref": "YO-00075249", "name": "...", "product_type": "Ламинат",
  "collection": "Visiogrande", "parent": "Classen Visiogrande",
  "price_type": "purchase",              // "purchase" | "rrc"
  "old": 960.0, "old_date": "2026-07-14",  // old=null для new
  "new": 980.0, "delta_pct": 2.08          // delta_pct=null для new
}
```
- В запись **не попадают**: unchanged; неподтверждённые/спорные сопоставления (§7) до
  подтверждения; позиции с непарсибельной ценой (§6.7) — их в отдельный список ошибок.

### 9.1.1. Подозрительные скачки цен

Изменение больше чем **в полтора раза** выносится отдельным предупреждением **в начало**
списка — обычно за таким скачком стоит не рынок, а перепутанная колонка или единица
измерения. Порог намеренно высокий: подорожание на 20–30% случается регулярно.

**Причина называется по данным самой коллекции, а не по одному отношению цен.** Проверки
идут в этом порядке:

1. **Часть позиций уже стоит новую цену** (в пределах порога значимости), а другие
   уезжают в полтора раза и больше → цена из прайса верна, выбиваются отдельные товары:
   в папке коллекции 1С лежат **разные товары**. Выбивающиеся называются поимённо.
2. **Цены внутри коллекции сильно разные** (max/min ≥ 1.5) → одной ценой её накрывать
   нельзя, показывается диапазон и сколько позиций уедет.
3. **Коллекция однородна**, а отношение совпадает с коэффициентом упаковки `alt_units` →
   гипотеза «цена ЗА УПАКОВКУ вместо цены за базовую ЕИ» (§6.3), с пересчётом за единицу.
4. Иначе — общее «проверьте колонку прайса и единицу измерения».

> **Почему порядок именно такой.** 14.08.2026 закупка Classen Euphoria «выросла» с 880 до
> 1775, отношение 2.02 почти совпало с упаковкой 1.974, и это выглядело как ошибка единицы
> измерения. На деле 1775 стояло в 1С с 15.05 у **пяти позиций из шести** — цена была
> верной. Выбивалась одна: `YO-00076843` «Euphoria WR Дуб Саттон FSC 58», другой товар в
> той же папке, со своей ценой 880. Проверь мы сначала совпадение с упаковкой — выдали бы
> уверенный, но неверный диагноз. Поэтому гипотеза про упаковку рассматривается
> **последней**, только когда коллекция однородна и объяснить скачок иначе нечем.

Настоящий риск здесь — не единица измерения, а **охват**: строка прайса относится к части
товаров папки, а цена пишется на всю папку.

Проверка **не блокирует** запись — кнопка остаётся за админом; она поднимает находку туда,
где её видно. Совпадения с коэффициентом нет — предупреждение общее («проверьте колонку и
единицу измерения»), причину не выдумываем.

### 9.2. Агрегация и защита периодического регистра

- **Агрегация** по `ТМ → коллекция`: число изменённых позиций и **средний % изменения**
  (среднее `delta_pct` по позициям коллекции, отдельно по видам цен при необходимости).

**Периодичность регистра — ДЕНЬ.** Ключ записи цены — (Номенклатура, ВидЦен, **день**).
Несколько записей за один день по одному товару/виду цены **перезаписывают** друг друга —
в регистре остаётся **последняя записанная за день** цена, новых записей истории не
добавляется. Отсюда:

- **Дата последнего изменения** (`old_date` из `by-tm`) — это **день**; сравнение «< 1
  месяца» ведём по дням (относительно сегодня, Europe/Moscow).
- **Запись всегда датируется текущим днём** (1С проставляет сам, в запросе даты нет — §10.2). Поэтому:
  - `old_date == сегодня` — цена по этому товару/виду **уже менялась сегодня**; наша запись
    **перезапишет** дневную запись (историю не засоряет). Это **не** churn — трактуем как
    коррекцию: в предложении помечаем информационно («цена уже менялась сегодня — будет
    перезаписана»), но **не** требуем отдельного подтверждения по этому признаку.
  - `old_date` — **предыдущий** день в пределах месяца → это реальная частая смена (churn):
    **предупредить** админа и писать такие позиции **только после явного подтверждения**.
  - `old_date` — старше месяца или отсутствует (`new`) → обычный случай, без предупреждения.
- Итог (средние %, флаги «недавняя смена» / «перезапись сегодня») передаётся в предложение
  (§9.3); решение — за админом.

### 9.3. Предложение админу

**Внутренний объект предложения** (несёт готовый payload для `set-prices`, §10.2):
```jsonc
{
  "supplier": "Classen",                 // из письма/ТМ
  "groups": [                            // для текста предложения
    {"tm": "Classen", "collections": [
      {"collection": "Visiogrande", "items_changed": 6, "avg_pct": 2.1, "recent_change": false}
    ]}
  ],
  "warnings": [ /* см. ниже */ ],
  "writes": [                            // ровно то, что уйдёт в set-prices при «да»
    // цена единая по коллекции → одна запись по коллекции (§10.2, форма «а»):
    {"tm": "000000104", "collection_ref": "YO-00074810", "prices": {"purchase": 980.0}},
    // неоднородная коллекция → по товару (форма «б», tm — для сверки бренда):
    {"ref": "YO-00070616", "tm": "000000104", "prices": {"rrc": 1960.0}}
  ]
}
```
`writes` содержит **только** позиции/коллекции со статусом `changed`/`new` (§9.1),
подтверждённые по сопоставлению (§7). **Группировка по коллекции** — когда цена в коллекции
единая (экономия токенов, §10.2); иначе по `ref`. При «да» → `set-prices(writes)` (§10);
при «нет» → отметить прайс `rejected` (§4.2).

**Текст предложения (из источника, воспроизводить дословно):**
```
Обновляем цены от [Поставщик] на:
-[ТМ1]
 *[коллекция1]
 *[коллекция2]
 * ...
-[ТМ2]
 *[коллекция1]
 * ...
?
```
Для затронутых коллекций показать **средний % изменения** (§9.2) и пометку о недавней смене
цены, где применимо. Если в прайсе несколько колонок под один вид цены — колонку уточнить
**заранее** (§6.5), до формирования предложения.

**Предупреждения** (`warnings`, показать админу, не блокируя молча):
- **недавняя смена цены** (предыдущий день < 1 мес, §9.2) — по каким коллекциям/позициям;
  **требует подтверждения**;
- **перезапись сегодня** (`old_date == сегодня`, §9.2) — информационно, подтверждения не требует;
- **расхождение `parent`/`collection`** у сопоставленных товаров (§7);
- прайс затронул **несколько `product_type`** — к какому типу отнесены цены (§6.6);
- **расхождение коэффициентов ЕИ** — «кол-во в упаковке» прайса ≠ коэффициент `alt_units`
  из 1С (§6.3); выводить **отдельной таблицей** (наименование, ref, ЕИ, прайс→1С,
  совпадает/расходится) — это самостоятельный результат для админа, в будущем — правка в 1С (§17);
- **бренды прайса не в `selling-tm`** (не выгружаются) — перечислить, по ним цены **не** обновлялись (§8.1);
- **позиции с непарсибельной ценой / без сопоставления** — перечислить, они **не** войдут в запись.
- **ТМ, чью номенклатуру агент загружал, но нигде не учёл** — считается по кэшу
  номенклатуры (что грузили) против переданных групп **и плана прогона** (§9.6). Ловит
  молчаливую потерю целого бренда из-за необработанного листа: именно так пропал AGT
  (§6.5.1). Не попадают в предупреждение:
  - **марки из плана** — при работе по одной ТМ в предложении всегда ровно одна, а
    остальные загруженные либо пройдены, либо ждут очереди; за них отвечает сам план,
    прогон не завершится, пока в нём есть незакрытые марки;
  - ТМ, у которой все `product_type` вне анализируемых категорий (§6.8) — пропущена
    намеренно.

  > Имя марки берётся из `selling-tm`, а не из наименования товара: у `NomItem` названия
  > марки нет, а первое слово наименования даёт «Ламинат Woodstyle Opera …» → «Ламинат».
- **замена неподтверждённого предложения** — новое предложение помечает прежнее
  `rejected`, и кнопка под ним перестаёт работать. Об этом говорится в тексте нового
  предложения: молчаливая замена выглядит для админа как поломка записи.
- **категория вне списка** (§6.8) — коллекция отброшена, цены не тронуты.

### 9.6. Прогон по маркам, а не одной простынёй

Прайс обрабатывается **по одной торговой марке**: показ изменений → вопросы по этой марке
→ подтверждение → запись → следующая марка. Не «разобрать весь прайс и выдать всё разом».

Причина — боевой прогон 14.08.2026: одно предложение на пять марок дало 62 строки запроса
и отчёт на 10 000 символов, а завышенная вдвое закупка Classen (§9.1.1) потерялась среди
трёх десятков коллекций и ушла в 1С по кнопке. Порция размером с бренд обозрима, вопросы
задаются, пока контекст этой марки ещё в работе, а ошибка стоит одной марки, а не прайса.

- **План** объявляется один раз (`start_price_run`, §13) и живёт в `price_run` (§12.4):
  список ТМ в порядке обработки и отметки о пройденных. В БД, а не в памяти — состояние
  переживает и ходы диалога, и нажатие кнопки.
- **`propose_prices` принимает ровно одну ТМ.** Несколько — отказ с указанием работать по
  одной; ограничение на стороне кода, а не только в промпте.
- **Хвост каждого предложения**: `Осталось обработать: Classen, AGT.`
- **После записи** обработчик кнопки сам продолжает диалог следующей маркой: файл и
  история остаются, админу не нужно присылать прайс заново на каждый бренд.
- **Марка без изменений** (писать нечего, кнопки не будет) закрывается сразу в
  `propose_prices`, иначе прогон встал бы на ней навсегда.
- **В конце** — отложенные замечания по прайсу целиком, затем `Прайс «Монарх-логистик»
  обработан полностью`, выход из режима, очистка файла, диалога и плана. Печатает это
  обработчик (`_finish_run`), один на оба пути завершения: и когда последнюю марку
  записали кнопкой, и когда по ней нечего было писать.

#### 9.6.1. Что показывать по марке, а что отложить в конец

Замечание про **прайс целиком** повторяется под каждым брендом и превращается в шум:
«бренды не в выгрузке: L`Quarzo, Betta, Aura…», «листы «Плинтус», «Подложка» — другие
категории», «лист «HDF Паркет» не разбирал». На шести марках админ прочитает это шесть раз.

Такие замечания агент откладывает через `add_final_note` (§13): они копятся в
`price_run.notes`, дубли отсеиваются по нормализованному тексту, и показываются **один
раз** перед итоговой строкой.

| В предложении по марке | В конец прайса |
|---|---|
| несопоставленные коллекции этой марки | бренды прайса не из выгрузки на сайт |
| коллекции 1С без строк в прайсе | листы других категорий товаров (§6.8) |
| расхождения упаковки, спорные соответствия | листы, которые не разбирались, и почему |
| скачки цен (§9.1.1), вопросы по марке | общие замечания по файлу |

Правило: относится к одной марке — в предложение; ко всему файлу — в конец.

**Список оставшихся марок добавляет код**, а не модель: иначе под предложением появляются
две строки об одном и том же («Дальше по плану: …» и «Осталось обработать: …»).

#### 9.6.3. Стоимость контекста

Оркестратор — ручной agentic-цикл (§11): **каждый** вызов инструмента это отдельный запрос
к модели со всей историей. Один шаг по коллекции с шестью инструментами отправлял историю
шесть раз. На прайсе Артисана она весила 197 тыс. токенов, то есть ~1,2 млн входных токенов
за одну коллекцию — отсюда скачок расхода, замеченный админом.

Три меры, все обязательные:

1. **Точка кеширования на последнем блоке истории** (`_cached` в `orchestrator.py`).
   Раньше кешировался только системный промпт, а сообщения уходили каждый раз заново.
   `cache_control` ставится на копии: в сохраняемую историю он попадать не должен, иначе
   копится от хода к ходу и упирается в лимит точек.
2. **Чистка тяжёлых выгрузок** (`_prune_file_dumps`). В истории остаётся по одной свежей
   выгрузке КАЖДОГО вида — лист прайса и номенклатура 1С; прежние заменяются заглушкой с
   указанием, как получить данные заново. Перечитывание бесплатно: прайс лежит в памяти
   процесса, номенклатура — в `_NOM_CACHE`.
3. **Сужение номенклатуры до коллекции** — `get_1c_nomenclature` принимает
   `collection_ref`. Выгрузка марки на 900 позиций весит ~45 000 символов на страницу, а в
   режиме коллекций нужна одна папка.

Ещё два источника, найденные при разборе счёта на 10 млн токенов за два прогона:

4. **Модель переписывала предложение дословно.** Инструмент возвращает готовый текст, и
   промпт требовал повторить его админу — это ~2 000 **выходных** токенов на шаг (у
   предложения №14 — 8 500), а выход стоит впятеро дороже входа. Заодно так терялись
   строки: однажды пропало «Осталось обработать». Теперь текст админу шлёт обработчик из
   `PricingTools.last_summary`, а модели сказано его не переписывать. В ответе инструмента
   текст **остаётся** — иначе модель не сможет ответить на уточняющий вопрос по нему, а в
   истории он кешируется и стоит копейки.
5. **Менеджерские инструменты в режиме цен.** `handle_turn` подмешивал `TOOL_DEFINITIONS`
   (почта, norwik, web_search) к режимным — 904 токена в каждом из ~72 запросов за разбор
   и лишний соблазн полезть в почту. Параметр `base_tools=False` их убирает.

Замеры: история 197 → 112 тыс. токенов (−43%), стоимость шага по коллекции ниже примерно
на 86%; инструменты 4 460 → 3 556 на запрос; выходные токены на шаг ~2 000 → ~20.

6. **Часовой TTL кеша** вместо пяти минут по умолчанию. Между предложением и нажатием
   кнопки админ читает цены и думает; за пять минут префикс протухал, и следующий шаг
   оплачивался целиком. Запись в часовой кеш дороже (×2 против ×1.25), но за прогон
   префикс читается десятки раз по ×0.1.

**Что проверено живыми запросами** (а не выведено рассуждением):

- кеш работает на нашей форме сообщений — точка на `tool_result` даёт
  `cache_read_input_tokens = 14 895` при `input_tokens = 2` на повторе;
- часовой TTL принимается и на системном блоке, и на блоке сообщений:
  `usage.cache_creation` показывает `ephemeral_1h_input_tokens`;
- **на thinking сэкономить нельзя**: Opus 5 думает и без параметра `thinking`, блок
  `thinking` присутствует в ответе в обоих случаях, разница в выходных токенах — шум;
- повторных одинаковых вызовов инструментов в боевой истории нет (68 уникальных из 68),
  то есть агент не крутится вхолостую.

Итог по прогону Артисана: входные 4,1 млн → ~570 тыс. (−86%), выходные 22 800 → ~240.

#### 9.6.2. Крупная марка дробится на коллекции

Порог — **300 позиций** в 1С по марке; проверяет **код**, а не модель. На Atlas Concorde
Rus (932 поз., прайс «Артисан-Проект») модель упёрлась в объём и вместо предложения выдала
админу три варианта на выбор — то есть переложила решение, которое принимается механически.

- `propose_prices` по крупной марке **отказывает** и требует вызвать `start_tm_collections`
  со списком коллекций, **которые есть в прайсе** (не всех из 1С — иначе очередь забьётся
  шагами, где нечего менять).
- Дальше коллекции идут той же очередью, что и марки: одна коллекция за вызов, кнопка,
  следующая. Ограничение «одна коллекция» держится кодом, симметрично правилу «одна ТМ».
- Хвост: `Сейчас Atlas Concorde Rus. Осталось в марке: Drift, Marvel.` и ниже прежнее
  `Осталось обработать: Azteca, Colorker.` Текущая марка во второй строке не дублируется.
- Очередь коллекций живёт в `price_run.stage`; когда она пустеет, марка помечается
  пройденной и внешняя очередь идёт дальше.

### 9.7. Отложенные задачи

То, к чему решили вернуться позже. Список переживает конец прогона и перезапуск бота,
поэтому лежит **отдельно** от `price_run`, который в конце очищается.

**Наполняется кнопками**, а не автоматически. Под каждым предложением второй ряд:

| Кнопка | Что делает |
|---|---|
| ⏭ Пропустить | цены не пишем, шаг закрываем, очередь идёт дальше |
| 🕐 Отложить марку целиком | закрывает марку и заводит задачу на неё; в режиме коллекций сворачивает и очередь коллекций — раз марка отложена, спрашивать её остаток незачем |
| 🕐 Отложить коллекцию | **только в режиме коллекций**: откладывается текущая коллекция, марка остаётся в работе |
| ✖️ Отмена (остаться на текущей задаче) | отклонить и **остаться** на шаге — чтобы переспросить агента |

Кнопок откладывания две только когда марка разбита на коллекции: там «Отложить» без
уточнения двусмысленна. В режиме марок откладывать можно лишь марку целиком, и вторая
кнопка не показывается. Подпись «(остаться на текущей задаче)» у «Отмены» — потому что на
вид она неотличима от «Пропустить», а ведёт себя противоположно.

Инструмент `defer_task` — для случая «админ попросил словами».

**Прайс хранится на сервере** (`data/prices/`, имя от sha1 содержимого): вернуться к задаче
через полторы недели, пересылая 12-мегабайтный файл, никто не станет. Сохраняется
**лениво** — только когда заводится первая задача этого прогона, и удаляется, когда исчезла
последняя ссылающаяся на него задача. Архива прайсов здесь нет: нет задачи — нет файла.

**Устаревание считается ТОЛЬКО по дате прайса.** Задача помечается `stale`, если у того же
поставщика (по нормализованному имени либо по совпавшей сигнатуре формата) пришёл прайс с
датой **строго новее**. Не устаревание: тот же прайс, присланный заново (это обычный способ
вернуться к отложенному); переэкспорт с той же датой; прайс без распознанной даты; задача
без даты. Проверка — в `start_price_run`, поэтому он принимает `price_date`.

**Авто-очистка**: объект, дошедший до записи, из списка убирается сам.

**Вывод краткий** — либо ТМ, либо ТМ/коллекция:

```
Отложенные задачи:
1. Atlas Concorde Rus — прайс «Price.xls» от 2026-08-26
2. Atlas Concorde Rus / Allure — прайс «Price.xls» от 2026-08-26
3. Kerama Marazzi — прайс «kerama.xlsx» от 2026-05-01  ⚠️ устарело, есть прайс новее
```

Команды: `/deferred`, `/deferred_resume <номер>` (поднимает прайс с диска),
`/deferred_forget <номер>`, `/deferred_clear`, `/deferred_clear_stale`.
Отложенное перечисляется и в итоговом блоке прогона (§9.6.1).

### 9.4. Несколько поставщиков одной ТМ

Одну и ту же ТМ возят разные поставщики по разным ценам. Перед записью агент обязан
сказать админу, если **другой поставщик обычно даёт дешевле**, и получить подтверждение:

```
Обрабатываю Classen по прайсу «Монарх Логистик» (закупка 980 ₽/м²).
Поставщик «ТД Паркет» обычно даёт дешевле — 940 ₽/м² (−4,1%) по прайсу от 15.07.2026,
сравнение по 180 из 241 позиций. Занести цены «Монарх Логистик»?
```

Ответ «да» → пишем (§10) и **запоминаем решение**, чтобы не спрашивать это же каждый месяц
(§9.4.4). Ответ «нет» → прайс помечается `rejected` (§4.2), цены не пишутся.

#### 9.4.1. Откуда берутся данные

**Наблюдения копятся при КАЖДОМ разборе прайса — независимо от того, применили его или
отклонили** (§12.2, `supplier_prices`). Иначе сравнивать не с чем: цены отклонённого прайса
в 1С не попадают и без отдельного хранения теряются, а «поставщик Б дешевле» — это факт
именно из **не применённого** прайса Б.

Момент записи наблюдений — **после сопоставления (§7) и пересчёта к базовой ЕИ (§6.3)**, до
предложения админу. Пишутся только позиции со статусом `confident` (§7.4): спорное
сопоставление даст сравнение цен разных товаров.

#### 9.4.2. Что сравнивается (и что сравнивать нельзя)

- **Только закупка.** РРЦ диктует производитель, у всех поставщиков одной ТМ она обязана
  совпадать. Расхождение РРЦ между поставщиками — **не выгода, а сигнал об ошибке** (чей-то
  прайс устарел, перепутана колонка, другой product_type): выносится отдельным
  предупреждением, а не как «у Б дешевле».
  > **Проверка РРЦ независима от сравнения закупки.** Она выполняется всегда, когда есть
  > наблюдения других поставщиков по этой ТМ, — в том числе когда вопрос о закупке не
  > задаётся (действует предпочтение §9.4.4, пересечение мало, разница ниже порога).
  > Это проверка **качества данных**, а не выбор поставщика, и пороги §9.4.5 к ней не
  > применяются.
- **Только по пересечению `ref`.** Средние по разным корзинам несопоставимы: если у Б в
  прайсе только дешёвая половина коллекции, его «средняя» будет ниже при поштучно одинаковых
  ценах. Считаем на множестве товаров, которые есть у **обоих**, и показываем его размер
  (`comparable_items` из `coverage`).
- **Условия поставки — часть цены.** «Закупочная с доставкой от 20 упак.» (реальная колонка
  прайса LINDERWOOD) и самовывозная цена — разные вещи. Заголовок колонки-источника
  сохраняется в `terms` и **показывается админу** рядом с ценой; автоматически цены с разными
  `terms` не приводятся друг к другу.
- **Свежесть.** У наблюдения есть `observed_at` = дата письма с прайсом (не дата разбора).
  Наблюдение старше **60 дней** помечается `stale` и в вопросе админу подаётся с оговоркой
  («по прайсу от 15.05, возможно устарел»), а не как актуальная альтернатива.
- **«Обычно дешевле»** — не одно наблюдение: доля позиций пересечения, где Б дешевле A,
  по **последним** прайсам каждого (`cheaper_share`). Порог для вопроса — §9.4.5.

#### 9.4.3. Кто источник цен, лежащих в 1С

`by-tm` отдаёт цену и дату, но **не поставщика** — а без него «980 против 940» не читается
(это подорожание у того же поставщика или другой поставщик дороже?). Поэтому каждая наша
запись фиксируется в `price_source` (§12.2): `ref` + вид цены → поставщик, значение, день,
`message_id` прайса. Заполняется из ответа `set-prices` (§10.3) — в нём есть и `refs` групп
формы «а», и `ref` формы «б», т.е. точный список фактически записанных товаров.

Цены, попавшие в 1С **до** внедрения фичи (или руками), источника не имеют — тогда
сравнение подаётся без «сейчас у нас цены поставщика X», просто как факт.

#### 9.4.4. Решение админа запоминается

Без этого агент будет задавать один и тот же вопрос при каждом прайсе. Ответ пишется в
`supplier_preference` (§12.2): ТМ (опц. коллекция) → выбранный поставщик, дата, причина
(если админ её назвал: «у Б нет наличия», «минимальная партия»).

- Пока предпочтение действует, вопрос **не задаётся**; в предложении остаётся одна
  информационная строка: «цены Classen берём у «Монарх Логистик» (решение от 01.06.2026)».
- Предпочтение **не вечно**: если разрыв вырос существенно (по умолчанию — вдвое против
  зафиксированного при решении) или решению больше **180 дней**, вопрос задаётся заново.
- Админ может переназначить явной командой («по Classen теперь берём у ТД Паркет»).

#### 9.4.5. Когда спрашивать

Вопрос задаётся, если **все** условия выполнены:
1. по этой ТМ есть наблюдение другого поставщика не старше 60 дней;
2. пересечение — не меньше 5 позиций **и** ≥ 20% позиций текущего прайса;
3. другой поставщик дешевле в среднем по пересечению **и** `cheaper_share` ≥ 60%;
4. разница средних **> 3%** (ниже — шум округлений и логистики);
5. по этой ТМ нет действующего предпочтения (§9.4.4).

Иначе — молча пишем; расхождение ниже порога уходит в `warnings` информационно.
Все пороги — в конфиге (§15), значения выше — умолчания.

Пороги относятся **только к вопросу о закупке**. Расхождение РРЦ (§9.4.2) проверяется и
попадает в `warnings` **независимо** от них и от наличия предпочтения.

```jsonc
              "terms": "закупка с доставкой", "observed_at": "2026-08-10"},
  "current_in_1c": {"supplier": "Монарх Логистик", "written_at": "2026-05-11"},  // из price_source; null если неизвестно
  "alternatives": [
    {"supplier": "ТД Паркет", "avg_purchase": 940.0, "delta_pct": -4.1,
     "comparable_items": 180, "coverage_pct": 74.7, "cheaper_share": 0.92,
     "observed_at": "2026-07-15", "stale": false,
     "terms": "закупочная с доставкой от 20 упак."}
  ],
  "rrc_conflict": [                          // РРЦ разошлась между поставщиками — ошибка, не выгода
    {"supplier": "ТД Паркет", "rrc": 1500.0, "ours": 1400.0, "items": 12}
  ],
  "requires_confirmation": true              // по §9.4.5
}
```
При `requires_confirmation: true` запись **не выполняется** до явного «да» — это
дополнительное подтверждение **поверх** обычного подтверждения предложения (§9.3), а не
вместо него.

### 9.5. Эксклюзивы поставщиков

Поставщики пишут в прайсах «эксклюзив» — на отдельные товары и на целые коллекции. Это
знание полезно менеджеру («у кого ещё брать» — ни у кого), и агент должен его показывать.

**Пометка чисто информативная.** Она не участвует в выборе поставщика (§9.4), не влияет на
цены и не блокирует запись. Единственное действие, которое она порождает, — вопрос админу,
когда двое заявили эксклюзив на одно и то же.

Формат: пометка добавляется **после названия** объекта — `Adventure (эксклюзив: Монарх
Логистик)`. Именительный падеж намеренно: родительный от произвольного названия компании
кодом не построить («ТД Паркет» → «ТД Паркета»). Модель в свободном ответе склоняет сама.

#### 9.5.1. Что считается заявкой

Слова-признаки: `эксклюзив`, `эксклюзивно`, `эксклюзивный дистрибьютор`, `экскл.`,
`только у нас`, `exclusive`, `exclusively`, `exclusive distributor`.

**Слово внутри наименования заявкой НЕ является.** Существуют коллекции, которые так и
называются — Exclusive, Эксклюзив, Exclusive Line; «Kronotex Exclusive» это имя товара, а
не заявление о правах. Засчитывается только надпись, стоящая **отдельно**: колонка-
примечание, строка-заголовок раздела, имя листа, имя файла. Код проверяет это независимо
от модели и такие позиции отбрасывает — иначе одна коллекция с неудачным названием
навесила бы ложный эксклюзив на целый бренд.

Определение того, на что распространяется надпись, — задача того же рода, что и баннер-
разделитель брендов (§6.7): позиционная, одной регуляркой не решается. Поэтому **модель
извлекает, код проверяет и хранит** — словарь слов идёт в промпт подсказкой, а не
детектором.

Заявки копятся при **каждом** разборе прайса, включая отклонённый: «эксклюзив» — факт из
прайса, а не следствие решения о записи цен.

#### 9.5.2. Разрешение

Действующая пометка не хранится, а **выводится** из заявок и решений админа — иначе её
пришлось бы пересчитывать при каждой новой заявке и держать в согласованном состоянии.

1. Есть решение админа → берём его; `supplier IS NULL` снимает пометку насовсем.
2. Иначе отбрасываем заявки старше **365 дней** (§9.5.3).
3. Из оставшихся берём самую свежую по `price_date` и все заявки в пределах **62 дней**
   от неё (диапазон «2 месяца» с запасом на разную длину месяцев).
4. Разных поставщиков в окне больше одного → **спор**: пометка не показывается, админу
   задаётся вопрос.
5. Иначе → пометка с этим поставщиком.

**Заявки вне окна — не спор, а смена эксклюзива**: побеждает свежая. Это тот же случай,
что и «перешёл к другому дистрибьютору», и требовать на него решение админа незачем.

**Наследование при показе:** товар → его коллекция → вся ТМ. Эксклюзив на коллекцию
распространяется на её товары, если у товара нет собственной заявки.

#### 9.5.3. Срок жизни

Заявка, не подтверждённая новым прайсом **365 дней**, перестаёт действовать. Прайсы
приходят примерно ежемесячно, поэтому живой эксклюзив подтверждается многократно; молчание
длиной в год означает, что договорённость истекла. Без срока мы бы годами показывали
неправду — эксклюзивы отмирают тихо, никто не присылает уведомление об их прекращении.

#### 9.5.4. Спор

```
⚠️ На «Classen / Adventure» эксклюзив заявили двое:
   Монарх Логистик: «эксклюзивный дистрибьютор в РФ» (прайс от 01.07.2026)
   ТД Паркет: «эксклюзив» (прайс от 01.08.2026)
Пометку не показываю, пока не решим. За кем эксклюзив?
```

Формулировки цитируются дословно — по ним админ и судит: «эксклюзивный дистрибьютор в РФ»
в шапке листа и «экскл.» в колонке-примечании это заявки разной силы, и без исходного
текста вопрос беспредметен.

До ответа пометка **не показывается**. Утверждать «эксклюзив Монарха», когда с равным
основанием это может быть эксклюзив другого, хуже, чем не показать ничего: информационная
подпись не должна утверждать то, в чём мы не уверены.

#### 9.5.5. Где появляется пометка

| Где | Кому | Механизм |
|---|---|---|
| Предложение по ценам (§9.3) | админ | код, `_render` |
| Рассылка менеджерам (§12.2 п.6) | менеджеры | код, `build_broadcast` |
| «Когда меняли цены» | оба | код, `describe_product`/`describe_group` |
| Ответы про товар (§13 master-spec) | менеджер | **список в системном промпте** |

Последняя строка — не код: основной агент ищет по почте и norwik.ru, кодов 1С у него нет, и
сопоставить его ответ с записью в БД постфактум нечем. Поэтому компактный список
эксклюзивов (`ТМ / коллекция — поставщик`) **вкладывается в системный промпт**, и модель
сама соотносит его с тем, о чём спросили.

Список, а не инструмент: инструмент модель может не позвать, и справочная пометка молча
исчезнет — для такой функции это худший режим отказа. Список маленький (эксклюзив пишут на
коллекции, это десятки строк), кеш промпта инвалидируется только при его изменении.

#### 9.5.6. Хранилище

```sql
-- Заявки: что поставщик написал. Не перезаписываются никогда.
CREATE TABLE exclusive_claims (
    id             INTEGER PRIMARY KEY AUTOINCREMENT,
    supplier       TEXT NOT NULL,       -- текстом; supplier_id — когда появится §4.5
    tm_code        TEXT NOT NULL,
    tm_name        TEXT NOT NULL DEFAULT '',
    collection_ref TEXT NOT NULL DEFAULT '',   -- '' = заявка на всю ТМ
    collection     TEXT NOT NULL DEFAULT '',
    item_ref       TEXT NOT NULL DEFAULT '',   -- '' = заявка на коллекцию целиком
    item_name      TEXT NOT NULL DEFAULT '',
    phrase         TEXT NOT NULL DEFAULT '',   -- дословно — по нему админ судит спор
    where_found    TEXT NOT NULL DEFAULT '',   -- column | header | sheet | filename | admin
    price_date     TEXT NOT NULL,              -- дата прайса: по ней считается окно спора
    price_doc      TEXT,
    recorded_at    TEXT NOT NULL,
    UNIQUE (supplier, tm_code, collection_ref, item_ref, price_date)
);
-- Решение админа. supplier IS NULL = «эксклюзива нет».
CREATE TABLE exclusive_decisions (
    tm_code        TEXT NOT NULL,
    collection_ref TEXT NOT NULL DEFAULT '',
    item_ref       TEXT NOT NULL DEFAULT '',
    supplier       TEXT,
    decided_at     TEXT NOT NULL,
    note           TEXT,
    PRIMARY KEY (tm_code, collection_ref, item_ref)
);
```

**`price_date` в UNIQUE** — повторный разбор того же прайса не плодит заявки, а два прайса
одного поставщика за разные даты не схлопываются: история нужна, чтобы отличить смену
эксклюзива от спора.

**Снятие пометки — это решение, а не удаление заявок.** `/exclusive_forget` пишет
`supplier = NULL`; удали мы заявки, следующий прайс с той же надписью вернул бы пометку
обратно, и админ снимал бы её каждый месяц.

**Поставщик — текстом**, как уже сделано в `price_writes.supplier`. Поэтому функция **не
блокирована** справочником поставщиков (§4.5) и IMAP (§16 п.7): имя поставщика в потоке
обновления цен уже известно. Переход на `supplier_id` — вместе с §4.5.

#### 9.5.7. Команды админа

- `/exclusives` — что помечено и что ждёт решения (споры показываются с формулировками).
- `/exclusive_forget <номер>` — снять пометку.
- Назначение и разрешение спора — словами в диалоге при разборе прайса (`set_exclusive`).

## 10. Этап 6. Запись цен в 1С — `set-prices` (ОПЕРАЦИЯ ЗАПИСИ)

Единственная операция записи. Выполняется **только после явного подтверждения** админа
(§9.3). Пишет **цену закупки и/или РРЦ** в периодический регистр сведений.

### 10.1. Эндпоинт и аутентификация
- **`POST .../get-products/set-prices`** (та же база `/api_shop/hs/ai-tools/`). Путь именно
  такой: POST-обработчик висит на том же ресурсе с шаблоном `get-products/{query-type}`,
  что и чтение; `POST .../set-prices` отдаёт 404.
- Заголовки: `X-API-Token: <токен>`, `Content-Type: application/json; charset=utf-8`.
- Идентификация товара — по **`ref`** (Код 1С из `by-tm`, §8.2), не по наименованию.

### 10.2. Тело запроса
Передаются **только изменяемые** виды цен (отсутствующий вид — не трогаем). **Дата не
передаётся** — 1С записывает цену **текущим днём** сам (см. ниже). Запись всегда **одним
батчем** (число round-trip'ов к 1С не зависит от гранулярности). Поддерживаются **две формы
записи** в общем списке `items`:

**(а) По коллекции (предпочтительно, когда цена единая по коллекции — экономия токенов):**
```jsonc
{
  "items": [
    { "tm": "000000104", "collection_ref": "YO-00074810",   // папка-коллекция (§8.2)
      "prices": { "purchase": 980.0, "retail": 1127.0, "rrc": 1200.0 } }
    // 1С разворачивает запросом `ГДЕ Родитель = &Родитель И Производитель = &Производитель`
    // и пишет по одной записи регистра на найденный товар. Принадлежность коллекции к ТМ
    // проверяется самим фильтром: несогласованная пара → 0 строк → ничего не пишется
    // (в ответе count=0, отдельная проверка не нужна).
  ]
}
```
**(б) По товару (fallback — когда цена внутри коллекции неоднородна):**
```jsonc
{ "items": [ { "ref": "YO-00075249", "tm": "000000104",   // tm — защитная сверка бренда
               "prices": { "purchase": 980.0, "retail": 1127.0, "rrc": 1200.0 } } ] }
```
`ref` адресует товар точно, но получен из **нечёткого сопоставления** (§7) — поэтому в
форме «б» передаём и `tm`: 1С сверяет `Производитель` товара с ним и при несовпадении не
пишет (§10.4). Ловит редкий случай, когда матчинг дал `ref` **другой** ТМ.
- **Почему по коллекции:** цена в регистре хранится **по-товарно** (коллекция — папка, цены
  не имеет), поэтому 1С в любом случае пишет N записей. Но перечисление SKU лучше делать
  **на стороне 1С** (форма «а»): агент/`writes` (§9.3) выдают ~1 строку на коллекцию вместо
  8–20 (Classen ≈ 30 вместо 241) — кратно меньше токенов в предложении и запросе; фильтр
  «Не выгружать» и разворачивание — в одной транзакции 1С.
- **Когда форму «б»:** цена в коллекции неоднородна (различается по размеру/декору) — тогда
  по `ref` (или под-группами). Определение однородности — при сравнении (§9.1).
- **Дата не передаётся.** Периодичность регистра — день; запись всегда актуальна на
  **текущий день** (устанавливает 1С своей датой, Москва). Это убирает дубли даты и риск
  рассинхрона часов клиент/сервер. На **чтении** `by-tm` дата остаётся (`prices.*.date` =
  когда цена менялась) — она нужна для проверки «<1 мес» (§9.2).
- `value` — просто число, цена за **базовую ЕИ** товара (та же `unit`, что в `by-tm`; новые
  ЕИ не создаются, §6.3). Пересчёт из прайса делаем **до** записи.
- Виды цен: `purchase` = `00-000003`, `retail` = `YO-000004`, `rrc` = `YO-000005` (§6.2).
  `retail` — **вычисленная** розница ([`retail-price-rules.md`](retail-price-rules.md)), а не
  значение из прайса; форма «а» для неё применима, только если и закупка, и розница в
  коллекции единые.
- Ответ на форму «а» **обязан вернуть список затронутых `ref`** (§10.3) — для аудита и учёта
  «сколько обновлено».

### 10.3. Ответ
Частичный успех: 1С обрабатывает позиции в цикле, **пропуская** проблемные и накапливая
объекты-ошибки в `errors`. Успешные — в `results`.

**Ответ самодостаточен для отчёта админу в Telegram (§13.1): агент строит сообщение, не
делая повторных запросов в 1С.** Поэтому в каждой записи есть `name`, `collection`, `tm_name`
и **старое** значение цены с датой, а ошибки — объекты с машинным `code`, номером позиции
запроса (`index`) и `ref`.

```jsonc
{
  "date": "2026-08-10",     // день, которым проставлены цены (ставит 1С)
  "updated": 21,            // товаров, где записана хотя бы одна цена
  "unchanged": 1,           // товаров, где все переданные цены уже равны текущим
  "failed": 2,              // позиций запроса, отвергнутых с ошибкой
  "results": [
    // форма «по коллекции» → изменения СГРУППИРОВАНЫ по одинаковому переходу цены:
    { "index": 0, "collection_ref": "YO-00075139", "collection": "Excellent",
      "tm": "000000311", "tm_name": "Most Flooring",
      "count": 8, "updated": 8, "unchanged": 0,
      "changes": [
        { "price_type": "rrc", "old": 2270, "old_date": "2025-10-20", "new": 2070,
          "count": 7, "refs": ["YO-00075141", "…"] },
        { "price_type": "rrc", "old": null, "old_date": "", "new": 2070,
          "count": 1, "refs": ["YO-00077618"] }        // РРЦ проставлена впервые
      ] },
    // форма «по товару»:
    { "index": 1, "ref": "YO-00068864", "name": "Ламинат Peli  Vintage Ван Браун VN-511",
      "collection": "Vintage", "collection_ref": "YO-00068859",
      "tm": "000000298", "tm_name": "Peli",
      "written": { "purchase": { "old": 949, "old_date": "2026-07-20", "new": 999 } } }
  ],
  "errors": [
    { "index": 2, "ref": "YO-99999999", "code": "product_not_found",
      "message": "product YO-99999999 not found" }
  ]
}
```
- **`old: null`** — цены этого вида раньше не было, проставляется впервые (`old_date: ""`).
- **Форма «а» отдаёт `changes` — группы по одинаковому переходу цены** (ключ: вид цены +
  старое + новое), а не строку на товар. Цена по коллекции обычно единая, поэтому поштучный
  список с наименованиями на 200 SKU раздувал бы ответ в десятки раз, повторяя те же
  `old`/`new` (≈35 КБ против ≈0,5 КБ). Аудит сохраняется — все коды перечислены в `refs`;
  наименования агент берёт из `by-tm`, который у него уже загружен. Товары-исключения
  («цена впервые», «уже актуальна») выделяются в отдельную группу **автоматически** — их
  не нужно искать, они видны как отдельная строка `changes` с малым `count`.
- **Цена равна текущей → запись НЕ делается**, позиция считается в `unchanged`: в форме «б»
  уходит в `skipped` (`{"value": 2070, "date": "2025-10-20", "reason": "same"}`), в форме
  «а» — в группу с `"skipped": true`. Так дата последнего изменения в регистре остаётся
  правдивой, а админ видит «уже актуально» вместо ложного «обновлено».
- **`collection`** — очищенное имя папки (как в `by-tm`): «Коллекция Brilliant - 10 декоров»
  → «Brilliant». Сырое имя папки для сообщения админу шумное.
- **`index`** — порядковый номер позиции в присланном `items` (с 0); связывает ошибку со
  строкой предложения (§9.3) без разбора текста `message`.
- **`code`** — машинно-читаемый: `items_missing`, `prices_missing`, `price_types_missing`,
  `tm_missing`, `tm_not_found`, `tm_deleted`, `target_missing`, `collection_not_found`,
  `collection_not_a_folder`, `collection_deleted`, `collection_not_exported`,
  `collection_empty`, `product_not_found`, `product_is_folder`, `product_deleted`,
  `product_not_exported`, `product_without_tm`, `product_tm_mismatch`, `price_invalid`,
  `write_failed`. Агент группирует по `code` («3 позиции помечены на удаление») вместо
  пересказа текстов.
- **Реализация 1С** — `specs/1c/set-prices.bsl` (готовый к вставке модуль).

### 10.4. Валидация на стороне 1С (обязательна; ошибка → в `errors`, позиция пропускается)
Идентификаторы: **`collection_ref`** = Код папки в `Справочники.Номенклатура`
(`НайтиПоКоду`); **`tm`** = Код в `Справочники.Производители` (тот же `Code`, что в
`selling-tm`, §8.1).
- Нет свойства **`prices`** у позиции → `prices_missing`; нет `tm` → `tm_missing`; нет ни
  `ref`, ни `collection_ref` → `target_missing` (все — с `index` позиции).
- **`tm`** проверяется до разбора формы: не найден → `tm_not_found`, помечен на удаление →
  `tm_deleted`.
- Форма «по коллекции»: `collection_ref` не найден → `collection_not_found`; это не папка →
  `collection_not_a_folder`; помечена на удаление → `collection_deleted`; «Не выгружать» →
  `collection_not_exported`. Развёртка отбирает **только конечные выгружаемые** товары
  (`И НЕ ЭтоГруппа И НЕ ПометкаУдаления И ЕСТЬNULL(НеВыгружать, ЛОЖЬ) = ЛОЖЬ`), симметрично
  чтению `by-tm` (§8.2/§8.3). Принадлежность папки к ТМ обеспечивает сам фильтр
  `Производитель = &Производитель`; **пустая выборка — не «тихий успех», а ошибка**
  `collection_empty` (иначе админ увидит «обновлено 0» без причины).
- Форма «по товару»: `product_not_found` / `product_is_folder` / `product_deleted` /
  `product_not_exported` / `product_without_tm`. **Сверка бренда**: код `Производитель`
  товара должен совпасть с переданным `tm`, иначе → `product_tm_mismatch`
  (`"product {ref} belongs to tm {код}, not {переданный}"`) — защита от ошибочного
  сопоставления §7, давшего `ref` чужой ТМ.
- `purchase`/`rrc` — **число > 0**, иначе `price_invalid` (строка `"980,0"` из прайса тоже
  сюда). Виды цен ищутся по коду один раз на запрос; не найдены → `price_types_missing` и
  запрос отвергается целиком.
- Ошибка записи менеджера записи → `write_failed` **с текстом исключения**
  (`КраткоеПредставлениеОшибки`), а не обезличенным «ошибка записи».
- **Реквизиты справочника читать запросом, а не через точку от ссылки.** У реквизита с
  «Использование = Для группы» (так может быть настроен `НеВыгружать`) обращение
  `Товар.НеВыгружать` бросает «Поле объекта не обнаружено» и роняет весь запрос в HTML-500;
  в запросе то же поле вернёт `NULL` → `ЕСТЬNULL(..., ЛОЖЬ)`.
- Сериализация ответа тоже под `Попытка` — иначе сбой `ЗаписьJSON` возвращает HTML-страницу
  IIS вместо JSON, и клиент не может разобрать ошибку.
- Запись только в регистр цен; **никаких других записей/удалений**.

### 10.5. Поведение на нашей стороне
- **Периодичность регистра — ДЕНЬ.** Ключ — (Номенклатура, ВидЦен, **день**). Любая
  запись за сегодня по товару/виду цены **перезаписывает** дневную запись — остаётся
  **последняя** записанная за день цена, **новых записей истории не создаётся**. Отсюда
  запись **идемпотентна в пределах дня**: повтор `set-prices` (тот же прайс/те же значения)
  за тот же день безопасен и не плодит историю; повтор с новым значением — просто заменяет
  цену дня на последнюю.
- Перед записью повторно учесть предупреждения §9.2 (churn — предыдущий день < 1 мес) —
  подтверждено (§9.3); «перезапись сегодня» подтверждения не требует.
- Логировать записанное (`ref` → значения/дата) для аудита.
- После применения/отклонения — пометить прайс **обработанным** (§4.2).
- **Требования безопасности** (как в `cart-orders-1c.md`, §7.3): изменения в 1С — только
  с разрешения админа; запись цен — единственная разрешённая операция изменения.

### 12.1. Контракт хранения истории диалога

Сценарий многошаговый (список → выбор → уточнение колонок → подтверждение записи), поэтому
контекст диалога сохраняется **между сообщениями Telegram**. Общий механизм с
`cart-orders-1c.md` §8; здесь — конкретный контракт.

**Ключ и значение:**
- Ключ — **Telegram `user_id`** (история по юзеру).
- Значение — сериализованный список **`messages`** Anthropic (роли `user`/`assistant`/
  `tool_result` вместе с блоками `tool_use`), как его накапливает цикл оркестратора, плюс
  метаданные.

```jsonc
// dialog_state
{
  "user_id": 12345,
  "messages": [ /* Anthropic messages: user / assistant(content с tool_use) / user(tool_result) ... */ ],
  "updated_at": "2026-07-31T10:00:00+03:00",
  "turns": 3
}
```
- **Сериализация**: блоки ответа модели приводить к JSON-совместимому виду
  (`block.model_dump()` / `response.model_dump()`) — сейчас цикл кладёт в `messages`
  SDK-объекты (`orchestrator.py:60`), для персистентности их нужно сериализовать.

**Изменение оркестратора** (`src/agent/orchestrator.py` — сейчас stateless,
`handle_query` создаёт новый `messages`):
- Ввести stateful-вход, напр. `handle_turn(user_id, query, on_tool)`:
  1. загрузить `messages` по `user_id` (пусто/просрочено → начать новый);
  2. добавить `{"role":"user","content": query}` (текущая дата Europe/Moscow передаётся
     в контекст хода — §4.3 спеки заказов);
  3. отработать существующий цикл до `end_turn`;
  4. **сохранить** обновлённый `messages` + `updated_at`/`turns` по `user_id`;
  5. вернуть текст ответа.
- **Обратная совместимость**: одношаговый поиск поставщика продолжает работать в рамках той
  же истории (каждый ход просто дополняет `messages`).

**TTL, сброс, ограничение размера:**
- **TTL** бездействия (рекоменд. 30–60 мин): при просрочке `updated_at` история считается
  устаревшей → новый диалог.
- **Явный сброс**: команда/фраза «новый запрос» (или `/reset`) очищает `dialog_state` по
  `user_id`.
- **Ограничение размера**: кап по числу ходов/токенов; при превышении обрезать **целыми
  ходами с начала**, не разрывая пары `tool_use`↔`tool_result` (иначе Anthropic отклонит
  запрос). `tool_result` от `by-tm` могут быть крупными (до 200 позиций) — учитывать в капе.

**Хранение и конкурентность:**
- **SQLite** (`src/storage/`) — переживает рестарт и общий для нескольких воркеров;
  для одного инстанса допустим in-memory-кэш поверх.
- Сообщения одного `user_id` обрабатывать **последовательно** (блокировка на юзера), чтобы
  параллельные сообщения не переплели `messages`.

### 12.2. Хранение цен по поставщикам (§9.4)

```sql
-- Справочник поставщиков. Ключ СУРРОГАТНЫЙ: ни домен, ни название не годятся — оба
-- меняются (§4.5.1). Имя нужно, чтобы агент говорил «ТД Паркет», а не «tdparket.ru».
CREATE TABLE suppliers (
    id          INTEGER PRIMARY KEY,
    name        TEXT NOT NULL,             -- текущее отображаемое имя (прежние — в identifiers)
    merged_into INTEGER REFERENCES suppliers(id),  -- NULL у живого; заполнен у слитого (§4.5.6)
    created_at  TEXT NOT NULL,
    updated_at  TEXT NOT NULL
);

-- Признаки, по которым письмо привязывается к поставщику (§4.5.2). Много к одному:
-- у поставщика накапливаются домены, адреса, прежние названия, телефоны, сигнатуры.
CREATE TABLE supplier_identifiers (
    kind        TEXT NOT NULL,             -- domain | email | company | phone | signature
    value       TEXT NOT NULL,             -- нормализованное значение (§4.5.3 для company)
    supplier_id INTEGER NOT NULL REFERENCES suppliers(id),
    confirmed   INTEGER NOT NULL DEFAULT 0,-- 1 = подтверждено админом; domain/email опознают
                                           --     только при confirmed = 1 (§4.5.2/§4.5.4)
    first_seen  TEXT NOT NULL,
    last_seen   TEXT NOT NULL,
    message_id  TEXT,                      -- письмо, из которого признак впервые взят
    PRIMARY KEY (kind, value, supplier_id)
);
CREATE INDEX ix_supplier_identifiers_supplier ON supplier_identifiers (supplier_id);
-- Опознающий признак принадлежит РОВНО ОДНОМУ поставщику; подсказки (company/phone/
-- signature) могут совпадать у разных (общий менеджер, похожие названия, типовая 1С).
CREATE UNIQUE INDEX ux_supplier_identity ON supplier_identifiers (kind, value)
    WHERE kind IN ('domain', 'email');

-- Наблюдения: что поставщик давал по конкретному товару. Пишется при КАЖДОМ разборе
-- прайса, в т.ч. отклонённого (§9.4.1). Цена — за базовую ЕИ 1С (§6.3), после пересчёта.
CREATE TABLE supplier_prices (
    supplier_id    INTEGER NOT NULL REFERENCES suppliers(id),
    ref            TEXT NOT NULL,          -- Код 1С сопоставленного товара (только confident, §7.4)
    tm_code        TEXT NOT NULL,
    collection_ref TEXT,
    price_type     TEXT NOT NULL,          -- purchase | rrc
    value          REAL NOT NULL,          -- за базовую ЕИ
    unit           TEXT NOT NULL,
    terms          TEXT,                   -- заголовок колонки-источника: «с доставкой от 20 упак.»
    observed_at    TEXT NOT NULL,          -- ДЕНЬ письма с прайсом, не дата разбора
    message_id     TEXT NOT NULL,          -- → processed_prices (§4.2)
    source         TEXT NOT NULL,          -- адрес отправителя (нижний регистр) — ИСТОЧНИК строки;
                                           -- по нему разделяют поставщика (§4.5.6)
    PRIMARY KEY (supplier_id, ref, price_type, observed_at)
);
CREATE INDEX ix_supplier_prices_tm ON supplier_prices (tm_code, price_type, observed_at DESC);
CREATE INDEX ix_supplier_prices_ref ON supplier_prices (ref, price_type, observed_at DESC);

-- Чьи цены реально лежат в 1С (§9.4.3). Заполняется из ответа set-prices (§10.3):
-- changes[].refs формы «а» + ref формы «б» = точный список записанного.
CREATE TABLE price_source (
    ref         TEXT NOT NULL,
    price_type  TEXT NOT NULL,
    supplier_id INTEGER NOT NULL REFERENCES suppliers(id),
    value       REAL NOT NULL,
    written_at  TEXT NOT NULL,             -- день записи (= date из ответа set-prices)
    message_id  TEXT NOT NULL,
    source      TEXT NOT NULL,             -- адрес отправителя прайса (см. supplier_prices.source)
    PRIMARY KEY (ref, price_type)
);

-- Решение админа «по этой ТМ берём у X» (§9.4.4), чтобы не спрашивать каждый месяц.
-- collection_ref = '' — решение на всю ТМ (пустая строка, а не NULL: NULL ломает PK).
CREATE TABLE supplier_preference (
    tm_code        TEXT NOT NULL,
    collection_ref TEXT NOT NULL DEFAULT '',
    supplier_id    INTEGER NOT NULL REFERENCES suppliers(id),
    decided_at     TEXT NOT NULL,
    delta_pct      REAL,                   -- разрыв на момент решения — для пересмотра (§9.4.4)
    note           TEXT,                   -- «у Б нет наличия», «минимальная партия 40 упак.»
    PRIMARY KEY (tm_code, collection_ref)
);
```

**Почему в наблюдениях есть `source`.** Он делает связь «строка → откуда пришла» явной, а не
выводимой из `supplier_id` (который может измениться при слиянии/разделении) или из джойна с
`processed_prices`. Благодаря ему **разделение поставщика (§4.5.6) детерминировано**:
переносятся ровно строки выделяемых источников. Без него ошибочно склеенных поставщиков
можно было бы разъединить только по признакам, а вся накопленная история осталась бы у
исходного — то есть сравнение цен (§9.4) для выделенного источника обнулилось бы.

**Почему `observed_at` в первичном ключе `supplier_prices`.** Иначе повторная обработка того
же прайса затирала бы историю, а два прайса одного поставщика за разные даты — схлопывались
бы в одну строку, и «обычно дешевле» стало бы «дешевле в последний раз». История нужна и для
пересмотра предпочтения (§9.4.4).

**Объём.** ~250 позиций × 2 вида цены × ~10 поставщиков × 12 прайсов в год ≈ 60 тыс. строк в
год — для SQLite незначительно. Чистка: наблюдения старше 2 лет удалять (кроме последнего по
каждой паре `supplier_id, ref`, чтобы не потерять «единственное известное»).

**Уникальность — только у опознающих признаков.** `domain`/`email` принадлежат ровно одному
поставщику (частичный уникальный индекс): попытка привязать занятый адрес к другому
`supplier_id` — это сигнал «похоже, дубликат», он выносится админу (слияние, §4.5.6), а не
разрешается молча. `company`/`phone`/`signature` — подсказки, у разных поставщиков они
законно совпадают (общий менеджер, похожие названия, типовая выгрузка 1С), поэтому под
уникальность не попадают.

Публичные почтовые домены (`mail.ru`, `yandex.ru`, `gmail.com`, …) в признаки **не пишутся
вовсе** (§4.5.1) — вместо них `email` целиком. **ИНН не используется** (§4.5.1).

**Связь с существующими таблицами.** `sender_domain` из `processed_prices` (§4.2) → признак
`domain` → `supplier_id`; `message_id` — общий ключ, по нему из наблюдения всегда виден
исходный прайс. Отдельной сущности «поставщик» в 1С нет — она живёт только у нас.

**Слитые поставщики.** Все выборки идут по «живым» (`merged_into IS NULL`); слитая запись
остаётся ради ссылочной целостности старых логов, но данные при слиянии переносятся на
выжившего (§4.5.6).

**Порядок вызова в потоке** (§3): отбор писем (§4.4) → `resolve_supplier` → при

## 16. Открытые вопросы (закрыть до реализации)

1. **`set-prices` — уточнения к контракту (§10 определён, проверен на бою)** — осталось
   подтвердить максимальный **размер пакета** `items`. Коды ВидЦен известны (§6.2),
   периодичность регистра — **ДЕНЬ**, дата в запросе **не передаётся** (§9.2/§10.2/§10.5),
   форма ошибок — объекты с `code` (§10.3). Контракт **чтения** — в §8.
1b. ~~`by-tm` не отдаёт розницу~~ — **закрыто 11.08.2026**: сервис отдаёт `retail`
    (`YO-000004`) в `prices` тем же форматом, `set-prices` её принимает; проверено чтением
    и записью ([`retail-price-rules.md`](retail-price-rules.md) §14.2).
1a. **Групповая запись по коллекции** (§10.2, экономия токенов) — 1С должен поддержать запись

    §8.2). До этого — запись по-товарно (форма «б»).
2. **Порог сопоставления (тюнинг)** — контракт матчинга определён в §7 (`confident`/
   `disputed`/`unmatched`), заданы **стартовые** значения (сходство `name` ≥ ~0.9 + зазор до
   2-го кандидата); осталось откалибровать пороги на реальных прайсах.

4. **Стабильность структуры прайсов** — насколько устойчива «сигнатура шапки» у поставщиков

## 19. Правка справочника номенклатуры (`dev_tasks/content-manager.txt` п.4)

Прайс расходится с 1С не только ценами. Агент должен заводить новые товары, править поля
существующих и убирать снятые с производства. **Удаление не предусмотрено вовсе**: на товар
остаются ссылки в других объектах, да и снятая позиция через время возвращается в
ассортимент.

Раздел — **контракт для разработчика 1С**. Инструменты агента пишутся после того, как
эндпоинты появятся: сейчас в сервисе нет ни одного из них, а `by-tm` не отдаёт полей,
которые нужно сверять.

### 19.1. Устройство справочника

Иерархия: корень «Товары и услуги» → папка **вида товара** (Ламинат, Керамическая плитка,
Обои…) → папка **ТМ** → папка **коллекции** → товар. У любой папки есть флаг «Не выгружать»,
который каскадом гасит выгрузку всего вложенного.

Внутри каждого вида товара лежит папка вида `*Номенклатура снятая с производства (Паркетная
доска)`. Товары и целые коллекции, ушедшие из ассортимента, **переносятся** туда сменой
родителя.

**Коллекция живёт в 1С дважды** — папкой иерархии и значением свойства «коллекция». Это не
дублирование контракта, а факт базы: `by-tm` уже отдаёт и `parent`, и `collection`, а §8.2
требует предупреждать админа при их расхождении. Поэтому заведение новой коллекции — это
**две операции**: создать папку и добавить значение свойства.

### 19.2. Эндпоинты: три чтения и одна запись

| Метод | Назначение | Пункт ТЗ |
|---|---|---|
| `GET get-products/folders` | Дерево папок с фильтрами `product_type` / `tm`. Узлы `{ref, name, parent_ref, kind, not_exported}`, где `kind` = `type` \| `discontinued` \| `tm` \| `collection` | нужен для п.2 и п.5 |
| `GET get-products/properties?product_type=<код>` | Доп. свойства вида товара со значениями **и их кодами** — из чего агенту выбирать. Фильтры `tm` и `property` (§19.2.1) | п.1, чтение |
| `GET get-products/by-tm` | Существующий, **расширить** (§19.3) | п.3 |
| `POST get-products/set-items` | **Единственная запись в справочник.** Батч операций `create_folder`, `create_item`, `update_item`, `add_property_value` | п.1 запись, п.2, п.4, п.5 |

Набор выведен из пяти запросов ТЗ после проверки на полноту и избыточность:

- **`move_item` не нужен.** Перенос — это правка поля `parent_ref`, частный случай
  `update_item`. Само ТЗ так и формулирует: «редактирование нужного поля… здесь же
  перемещение из каталога в каталог».
- **`add_property_value` — операция, а не эндпоинт.** Новая коллекция требует и папки, и
  значения свойства, а подтверждается одной кнопкой (§19.6): значит и уходить должна одним
  запросом.
- **`folders` шире, чем «дерево видов товара».** Чтобы создать папку коллекции, нужен ref
  **папки ТМ внутри вида товара**. `selling-tm` отдаёт код Производителя — это реквизит, а
  не папка иерархии; `by-tm` показывает только папки существующих коллекций и не покажет
  пустую, из-за чего можно завести дубль.

Похожие на первый взгляд вещи, которые **не** дублируют друг друга: `properties` даёт
**допустимые** значения, а `properties` в ответе `by-tm` — уже проставленные у товара;
`set-items` и `set-prices` — разные предметы (справочник и регистр цен), у каждого своя
кнопка и свой контракт.

#### 19.2.1. Свойства: объём, частота, коллекции

Проверено на боевом ответе по «Виниловому ламинату»: 8 свойств, 123 значения (из них 75 —
одна «Порода дерева»), 1 554 символа ≈ 620 токенов. С кодами значений (§19.2.2) ответ
растёт примерно до **2 100 токенов** на вид товара.

**Частота.** Один раз на вид товара за прогон прайса, кеш в памяти процесса. Прайс задевает
один-три вида → до ~6 тыс. токенов на весь разбор, около 1% от него (§9.6.3). **При создании и
правке каждого товара запрос не нужен.** В режиме «только цены» (§5.2) не вызывается вовсе.

Кеш именно в памяти, а не в БД: справочник свойств правят руками в 1С, и залежавшийся кеш
начнёт молча предлагать значения, которых там уже нет. Время жизни — один прогон, как у
`_NOM_CACHE`.

#### Коллекции: справочник ни к виду товара, ни к ТМ не привязан

Значения свойства «коллекция» лежат отдельным иерархическим справочником (вид товара → ТМ →
коллекции), но **ссылочной связи с видом товара и Производителем у него нет** — иерархия
держится только на именах папок. Сопоставлять по именам рискованно: имена ТМ бывают
двуязычными («Atlas Concorde / Атлас конкорд»), и молчаливое ложное совпадение обнаружится
нескоро.

**Основной путь обходит справочник вообще.** `by-tm` уже отдаёт у каждого товара поле
`collection` — это и есть значение свойства. Значит набор коллекций марки виден из её же
товаров, без обращения к справочнику и без сопоставления по именам. Не хватает только кода,
поэтому **`by-tm` должен отдавать `collection_code`** (§19.3). Тогда:

- **коллекция существует** → код берём из товаров этой ТМ: ноль запросов, ноль сопоставления
  по названиям, риска нет;
- **коллекция новая** → в 1С её нет по определению, сопоставлять не с чем: создаём через
  `add_property_value` и ссылаемся `$id` (§19.2.3).

Запрос к справочнику коллекций остаётся **страховкой от дубля** — на случай, когда значение
в справочнике есть, но ни одним товаром этой марки не используется. Это узкий остаток, а не
основной путь.

**Отбор в этом запросе.** По **виду товара** — жёсткое соответствие на стороне 1С (девять
типов, они стабильны, это одна таблица в модуле). По **ТМ** — только сопоставление по имени
папки, и тогда 1С обязана вернуть `matched_folder` — какую папку она сопоставила. Без этого
поля риск молчаливый; с ним агент сверит имя с ТМ и предупредит админа при расхождении.
Жёсткого соответствия по ТМ быть не должно: марок 165 и их число растёт, поддержка такой
таблицы нереальна.

**Нужен ли отдельный фильтр по свойству.** Два варианта, разница измерена на плане прайса
Артисана (7 марок, свойства с кодами ≈ 2 100 токенов на вид товара, коллекции одной ТМ ≈ 250):

| Вариант | Запросы | Токенов за прогон |
|---|---|---|
| `properties?product_type=X` + `…&tm=Y&property=Коллекция` | раз на вид + раз на марку | ~3 850 |
| `properties?product_type=X&tm=Y` без фильтра | раз на марку | ~16 450 |

Без фильтра общие свойства вида товара повторяются на каждой марке — лишние ~12 600 токенов,
около 2% разбора. **Рекомендация — оставить фильтр**: на стороне 1С это одно условие. Но
если разработчику так удобнее, вариант без фильтра приемлем: два процента не блокер.

#### 19.2.2. Значения свойств адресуются КОДОМ

Свойства и их значения — справочник 1С, у них есть коды (подтверждено разработчиком).
Поэтому `properties` отдаёт `{"property": …, "code": …, "values": [{"value": …, "code": …}]}`,
а `set-items` принимает **коды**, не строки.

Имена были бы дешевле — с кодами ответ растёт с 620 до ~2 100 токенов на вид товара, то
есть ~6 300 за прогон при трёх типах (≈1% разбора, §9.6.3). Но на этих данных имя не
является надёжным ключом:

- переименование значения в 1С молча разорвало бы сопоставление;
- в самом справочнике соседствуют «Гикори» и «Хикори», есть «Клён» и «Ёлочка» с «ё» —
  строковое совпадение здесь слишком легко испортить регистром, пробелом или заменой «ё».

**Новая коллекция.** У созданного значения кода заранее нет, поэтому `add_property_value`
получает `id`, а ссылка на него идёт как `"$id"` — тем же механизмом, что и для папок
(§19.2.3). Это единообразно: всё адресуется кодом, а ещё не существующее — временной
ссылкой.

#### 19.2.3. Ссылка на объект, созданный в этом же батче

Главный сценарий — в прайсе новая коллекция, надо создать папку **и** товары в ней.
**Подтверждено разработчиком 1С:** папка и товары передаются одним батчем, 1С создаёт
сначала папку, затем кладёт в неё товары.

Контракт: у операции есть необязательный `id`, а любое поле `*_ref` принимает `"$<id>"` —
ссылку на объект, созданный ранее в этом же батче.

**Ошибка родителя отменяет зависимые операции.** Если папка не создалась, товары в неё не
создаются. Это не «частичный успех», а каскад — и он обязан быть виден в ответе (§19.8),
иначе админ увидит одну ошибку про папку и решит, что товары записались.

```jsonc
{ "items": [
  { "op": "create_folder", "id": "coll", "parent_ref": "YO-TM-CLASSEN",
    "name": "Adventure 1286x192x8" },
  { "op": "add_property_value", "product_type": "000000012",
    "property": "collection", "value": "Adventure" },
  { "op": "create_item", "parent_ref": "$coll", "product_type": "000000012",
    "name": "Ламинат Classen Adventure Дуб Авола 1286x192x8", "article": "62593" }
] }
```

### 19.3. Расширение `by-tm` (п.3 ТЗ)

Без этого сверка «правильности заполнения всех полей» невозможна: сегодня из размеров виден
только `size` строкой, а вида товара — только имя.

- Фильтр `product_type`; флаг **`include_not_exported=1`**.
- Поля: `product_type_ref`, `length_from`/`length_to`, `width_from`/`width_to`, `thickness`,
  `full_name`, `site_name`, `properties`, `not_exported`, **`collection_code`** — код
  значения свойства «коллекция». Он закрывает основной сценарий работы с коллекциями без
  обращения к их справочнику (§19.2.1).

> **Почему нужен `include_not_exported`.** Сейчас `by-tm` отдаёт только выгружаемые товары
> (§8.2), а папка снятых помечена «Не выгружать». Значит проверить «нет ли товара среди
> снятых» через неё нельзя — и агент завёл бы дубль вместо возврата позиции в ассортимент,
> ровно вопреки ТЗ.

### 19.4. Поля товара при создании и правке

`parent_ref`, `product_type`, `article`, `name`, `full_name`, `site_name`, `manufacturer`
(код ТМ), `unit`, `length_from`/`length_to`, `width_from`/`width_to`, `thickness`,
`pack_coefficient`, `properties`.

- **Длина и ширина** — целое число мм. У части паркетной доски длина в упаковке плавает:
  тогда `*_from` — минимум, `*_to` — максимум. По умолчанию размер фиксированный, и оба
  поля равны.
- **Толщина** — мм, допускается один знак после запятой.
- **Коэффициент** количества базовой ЕИ в упаковке — до трёх знаков после запятой.
- **Свойства** — коды значений из `properties`. Агент **создаёт** только значения свойства
  «коллекция»; остальные выбирает из существующих.

### 19.5. Правила имён и единиц — считает код, не модель

Правила из ТЗ детерминированы, поэтому живут в коде (`src/price_tool/naming.py`) и
покрываются тестами — как расчёт розницы в `src/price_tool/retail.py`. Модель отдаёт
**части**, строку собирает код.

- `Наименование` = `Полное наименование` = `[тип] [ТМ] [коллекция] [название] [размер]`;
  `Наименование для сайта` = `[название]`.
- **Тип для керамики**: «Керамическая плитка» для напольной и настенной, «Керамогранит» при
  явном указании, а для декоративных элементов — сам тип декора: бордюр, вставка, панно,
  декор, мозаика.
- **Латиница в приоритете**, кириллица — если латинского названия нет. Смешивать латиницу и
  кириллицу в одном имени **нельзя**; проверяет код.
- **Размер**: у дверей не заполняется вовсе; толщина не заполняется у обоев, а у керамики —
  только если явно указана в прайсе; длина и ширина обязательны везде, кроме дверей.
- **Базовая ЕИ** выводится из вида товара: ламинат и паркет — м², двери — шт., керамика —
  м² для фоновой плитки и шт. для декоративных элементов, обои — рулон.
- **Имя папки коллекции**: у ламината и паркетной доски дописывается размер `ДxШxТ` в мм,
  если он единый для всей коллекции.

### 19.6. Что проверяем при разборе прайса

1. **Товара нет в 1С, но он есть в прайсе** — сначала искать в папке снятых (§19.3) и
   **возвращать оттуда** сменой родителя, а не заводить дубль.
2. **Поля в 1С не совпадают с прайсом** — правка через `update_item`.
3. **Товар есть в 1С, но его нет в прайсе** — кандидат на перенос в снятые.

Перенос выполняется **только после вопроса админу** «перенести или оставить» — кроме
случая, когда агент точно знает, что это товар другого поставщика.

> Сегодня «точно знает» = есть действующая пометка эксклюзива другого поставщика (§9.5).
> Наблюдения цен других поставщиков (§9.4) не реализованы и упираются в IMAP (§16 п.7).
> **Значит в первой версии вопрос будет задаваться почти всегда** — это ожидаемое поведение,
> а не дефект.

### 19.7. Диалог с админом

Порядок по каждой коллекции: перечислить найденные несоответствия → **«применить правки или
пропустить»** → затем предложение по ценам (только в режиме `товары+цены`, §5.2) → следующая
коллекция. В конце — итог по всему прайсу.

Правки подтверждаются **одной кнопкой на коллекцию**: показанный список уходит одним батчем
`set-items`. Гейт тот же, что у цен (§10): модель готовит payload, сохраняет его, а
отправляет в 1С обработчик кнопки — инструмента записи у модели нет.

**Следствие для очереди.** В режимах с правкой товаров прогон идёт **по коллекциям всегда**,
а не только у марок крупнее `BIG_TM_ITEMS`, как сейчас (§9.6.2). Второй уровень очереди
(`price_run.stage`) для этого уже готов — менять его не нужно, достаточно всегда открывать.

### 19.8. Ответ `set-items`

По образцу §10.3: `{date, created, updated, results, errors}`. В `results` — `index`, тип
операции и **ref созданного объекта** (нужен и для журнала, и для разрешения `$id`); в
`errors` — `{index, ref, code, message}` с машинным `code`.

**Батч не откатывается целиком** — как в `set-prices`: ошибка одной операции не отменяет
независимые от неё. Но **зависимые пропускаются**: не создалась папка — не создаются и
товары в ней (§19.2.3). Такие операции обязаны попадать в ответ отдельным статусом
`skipped_dependency` с индексом провалившейся операции-родителя. Без этого админ увидит
одну ошибку и решит, что остальное записалось, — а на деле не записалось ничего.
