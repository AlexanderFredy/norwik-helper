# Спецификация: Контент-менеджер (обновление цен в 1С из прайс-листов)

> **Статус:** черновик. Источник требований — `dev_tasks/content-manager.txt`.
> Базовый спек системы (поиск товаров у поставщиков) — `master-spec.md`; данная функция
> добавляется поверх него и переиспользует те же компоненты (Telegram-бот, оркестратор,
> Email Tool). Существующий функционал не меняется по поведению.
>
> **Доступ:** функция **только для админа** (`is_admin`, `src/bot/auth.py`). Обычным
> пользователям недоступна.

---

## 1. Цель

Настроен обмен «1С ↔ norwik.ru»: товары заводятся в 1С с описанием и ценами, раз в сутки
выгружаются на сайт в XML, скрипт сайта обновляет карточки. Данная функция помогает
**админу** поддерживать цены в 1С в актуальном состоянии по прайс-листам поставщиков:

1. Найти в почте новые прайс-листы поставщиков (за последний месяц, исключая уже
   обработанные).
2. По каждому прайсу узнать у 1С, какие торговые марки (ТМ) из него стоят к выгрузке
   на сайт — работать только с ними.
3. Разобрать цены из прайса (разные форматы), привести к базовой единице измерения товара.
4. Сравнить с текущими ценами в 1С, выявить изменения, оценить средний % по коллекции.
5. Сформировать админу предложение обновить цены; **после подтверждения** — записать
   новые цены в 1С через HTTP-сервис.

> Обновляются **цена закупки** и **РРЦ**. Розничная цена в этой итерации **не пишется**
> (см. §6.4 и §11) — задел на будущее.

## 2. Область охвата

### Входит в данную спецификацию
- Отбор писем-прайсов из почты за последний месяц; **ручной** запуск проверки админом.
- **Дедуп**: не обрабатывать повторно прайс, по которому уже применяли/отклоняли изменения.
- Ручной поиск конкретного прайса по поставщику и **примерной дате (±неделя)**.
- Разбор прайсов **разных форматов** (за штуку / за коллекцию / за упаковку; несколько
  колонок видов цен; скидка от РРЦ); приведение к базовой ЕИ.
- **Маппинг колонок → виды цен**, запоминаемый по поставщику (домен + сигнатура структуры).
- Сопоставление строк прайса с номенклатурой 1С (агент по совокупности + подтверждение).
- Проверка «ТМ к выгрузке на сайт», сравнение с текущими ценами 1С, история регистра,
  предложение админу и запись цен (закупка + РРЦ) после подтверждения.
- Интерфейс компонента интеграции с 1С (чтение цен/истории/ТМ + запись цен).

### НЕ входит (явно отложено)
- **Розничная цена** — правила расчёта по отдельной инструкции; в этой итерации в 1С
  не пишется. Механизм хранения/применения правил закладывается (§11), правила — позже.
- **Часть 4** источника — внесение новых товаров в 1С и заполнение описаний
  (`#будет описано позже#`).
- **Часть 5** источника — добавление фото к новым товарам (`#будет описано позже#`).
- **Автоматический суточный планировщик** — в этой итерации запуск ручной (команда админа);
  планировщик добавим позже (§5.1).
- Любые операции записи в почтовый ящик — Email Tool строго read-only (как и раньше).

## 3. Сценарий использования (полный поток)

```
Админ: «Проверь новые прайсы» (команда/сообщение в Telegram)
   │
   ▼
[Э1] Отобрать письма-прайсы за последний месяц (MailKind.PRICE),
     исключить уже обработанные (по message-id) → список прайсов
   │
   ▼
для каждого прайса:
   ├─ [Э2] Спросить 1С: какие ТМ из прайса стоят к выгрузке на сайт?
   │        └─ ни одной → пропустить прайс
   │
   ├─ [Э3] Разобрать цены из прайса:
   │        - определить формат (за штуку / коллекцию / упаковку)
   │        - применить сохранённый маппинг колонок (домен+сигнатура)
   │          └─ маппинга нет / неоднозначно → уточнить у админа → сохранить
   │        - привести к базовой ЕИ товара
   │
   ├─ [Э4] Сопоставить строки прайса с номенклатурой 1С (по совокупности)
   │        └─ спорные сопоставления → подтверждение админа
   │
   ├─ [Э5] Запросить текущие цены 1С, выявить изменения:
   │        - проверить историю регистра (<1 мес → предупреждение)
   │        - средний % изменения по коллекции
   │        - сформировать предложение админу
   │
   ▼
[Э6] «Обновляем цены от [Поставщик] на: -[ТМ] *[коллекция]… ?»
     ├─ да  → записать цены (закупка, РРЦ) в 1С → отметить прайс обработанным
     └─ нет → отметить прайс обработанным (отклонено)
```

Сценарий **многошаговый**: между шагами требуется ответ админа (уточнение колонок,
подтверждение сопоставления, финальное подтверждение записи). Требуется хранение состояния
диалога — см. §8 спеки `cart-orders-1c.md` (тот же механизм истории по юзеру).

## 4. Этап 1. Отбор прайсов из почты

### 4.1. Источник писем
- Переиспользуется классификатор `src/email_tool/classifier.py`: тип `MailKind.PRICE`
  (тема → имена вложений → названия листов Excel).
- Поиск через `MailClient.search` (`src/email_tool/client.py`) с `since` = сегодня − 30 дней.
- Чтение вложений — `read_attachment` / `src/email_tool/attachments.py` (xlsx, xls, csv…).

### 4.2. Дедуп (уже обработанные прайсы)
- Ключ письма — `message-id` (при отсутствии — `uid`).
- Отметка хранится в SQLite (`src/storage/`, новая таблица — §11).
- «Обработан» = прайс, по которому изменения цен уже **применены или отклонены**
  (просто просмотренный — не считается обработанным).
- При отборе (§4.1) уже обработанные письма исключаются.

### 4.3. Ручной поиск конкретного прайса
Админ может попросить найти конкретный прайс, а не сканировать всё:
- по **поставщику** (домен/email/имя из подписи, `parse_signature`);
- по **примерной дате ±неделя** — окно `[дата−7д; дата+7д]` для фильтра писем.

### 4.4. Контракт инструмента `find_price_emails`

Чтение почты — строго read-only (существующий `MailClient`, `BODY.PEEK`, без флагов/записи).

**Параметры (все опциональны):**
| Параметр | Назначение | По умолчанию |
|---|---|---|
| `days` | глубина сканирования (последние N дней) | 30 |
| `sender` | фильтр по отправителю (email/домен) — IMAP `FROM` | — |
| `around_date` | целевая дата для точечного поиска (±7 дней) | — |
| `text` / `subject` | подстрока в теле/теме | — |
| `include_processed` | включать уже обработанные (обычно нет) | false |

**Конвейер (переиспользует существующее):**
1. `MailClient.search(sender?, subject?, text?, since=сегодня−days)` → кандидаты
   (заголовки + текст, **без вложений**), от новых к старым. При `around_date` —
   `since = around_date−7`, верхняя граница `+7` фильтруется на нашей стороне (IMAP
   `SINCE` даёт только нижнюю).
2. Для кандидатов — `MailClient.fetch_message(uid)` (полное письмо с вложениями), чтобы
   получить имена вложений и, для xlsx, `excel_sheet_names` (§`attachments.py`).
3. `classify(subject, attachment_names, excel_sheet_names)` → оставить только
   **`MailKind.PRICE`** (тема → вложения → листы, §`classifier.py`).
4. `parse_signature(body)` → имя менеджера и телефон; из `sender_email` выделить **домен**
   (ключ маппинга, §6.5).
5. Исключить **уже обработанные** по `message_id` (таблица §12), если не `include_processed`.

**Результат (JSON агенту)** — список писем-прайсов, **без содержимого вложений**
(их читает отдельно `read_attachment(uid, filename)`):
```jsonc
[
  {
    "uid": "12345",
    "message_id": "<a1b2@classen.ru>",   // ключ дедупа (§4.2); при отсутствии — uid
    "sender_email": "sales@classen.ru",
    "sender_domain": "classen.ru",         // ключ маппинга колонок (§6.5)
    "sender_name": "Classen Sales",
    "manager_name": "Иван",                // из подписи (может быть null)
    "phone": "+7...",                       // из подписи (может быть null)
    "subject": "Прайс Classen июль",
    "date": "2026-07-15",
    "attachments": ["price_classen.xlsx"],
    "mail_kind": "price",
    "already_processed": false
  }
]
```

**Доработки существующего кода (для реализации):**
- **Добавить `message_id`** в `EmailMessage` (`src/email_tool/client.py`): в `_fetch`
  извлечь `msg.get("Message-ID")` — сейчас поле не сохраняется, а дедуп (§4.2) на него
  опирается; фолбэк на `uid`.
- `search()` — поднять/параметризовать `limit` под месячное сканирование.
- Домен отправителя — из `sender_email` (`split('@')[-1]`, нижний регистр).

## 6. Этап 3. Разбор цен из прайса

### 6.1. Форматы прайсов (учесть разнообразие)
- Цена на **конкретный товар** vs на **коллекцию целиком** (все товары коллекции по одной цене).
- Несколько **колонок видов цен** в таблице Excel.
- Поставщик даёт **скидку от РРЦ** — это наша **цена закупки** (закупка = РРЦ − скидка).
- Цена может быть **не за единицу**, а за упаковку/коллекцию → пересчёт к базовой ЕИ (§6.3).

### 6.2. Три вида цен в 1С
- **Цена закупки** — по которой поставщик продаёт единицу продукции.
- **Розничная цена** — по которой мы продаём (в этой итерации **не пишется**, см. §6.4).
- **РРЦ** — рекомендованная поставщиком розничная цена.

Из прайса заполняются **только цена закупки и РРЦ**.

### 6.3. Приведение к базовой ЕИ
- Если цена дана за упаковку/партию/коллекцию — пересчитать к базовой единице измерения
  товара **в том виде, в каком она задана в 1С**.
- **Новые ЕИ не добавлять** — использовать существующую ЕИ товара в 1С.
- **Диапазон размера не влияет на цену за м².** У ламината, паркетной и массивной доски
  длина/ширина в `size` могут быть заданы **диапазоном** (`800-1200х200х12`,
  `1500х150-200х15`) — доски в упаковке разного размера, но **цена за м² единая**. Такой
  `size` не требует пересчёта цены и не считается расхождением.

### 6.4. Розничная цена (отложено, но с заделом)
- Розничная цена заполняется по отдельной инструкции (правила будут описаны позже).
- В этой итерации **не пишется** в 1С.
- В коде закладывается механизм: таблица правил розничной цены (§11) + точка их применения,
  чтобы включить розницу позже без переделки.

### 6.5. Маппинг колонок → виды цен (запоминаемый)
- Прайсы одного поставщика приходят с **разных ящиков одной компании** → ключ маппинга =
  **домен email отправителя** + **сигнатура структуры** прайса.
- **Сигнатура структуры** — хэш «скелета» файла: имена листов + строка(и) заголовков
  колонок, **без числовых данных**. Новый прайс того же формата → та же сигнатура →
  маппинг подхватывается автоматически; поставщик сменил формат → другая сигнатура →
  спрашиваем колонки заново.
- При **отсутствии маппинга** или **неоднозначности** (несколько колонок могут
  соответствовать одному виду цены) — уточнить у админа, из какой колонки заполнять
  какой вид цены, затем **сохранить** маппинг (§11).

### 6.6. Несколько типов товара (`product_type`) в одной ТМ
- `by-tm` по одной ТМ может вернуть товары **разных `product_type`** (напр. у бренда есть
  и ламинат, и плинтус/подложка). Прайс обычно относится к **конкретному типу**.
- При разборе прайса нужно **определить, к какому `product_type`** относятся его цены
  (по заголовкам/листам/содержимому), и сопоставлять строки только с товарами **этого
  типа** (§7). Если прайс покрывает несколько типов — разбить по типам.
- Размерность/ЕИ зависит от типа (ламинат — м², плинтус — пог. м и т.п.) → пересчёт (§6.3)
  выполнять относительно `unit` товара соответствующего типа.

## 7. Этап 4. Сопоставление строк прайса с номенклатурой 1С

- В прайсе, в отличие от заказа из корзины, **нет кода `1c`**. Сопоставляем строки прайса
  с товарами из `by-tm` (§8.2). Поля `article/size/collection` в 1С заполнены **часто, но
  не всегда** → это усиливающие сигналы, не обязательные; `name` заполнено **всегда**, но
  с отклонениями в написании.
- **Сначала фильтр по `product_type`** — сопоставлять строки прайса только с товарами того
  типа, к которому относится прайс (§6.6); в одной ТМ типов может быть несколько.
- **Приоритет матчинга** строки прайса к товару 1С:
  1. **Точное по `article`** — если заполнен и в 1С, и в прайсе.
  2. **`size` + `collection` + декор** — комбинация структурных полей.
  3. **Fuzzy по `name`** — всегда как основа/фолбэк, с учётом отклонений написания
     (регистр, пробелы, латиница/кириллица, синонимы, суффикс-артикул).
- **`size` — формат `Д×Ш×Т` в мм**; Д и Ш могут быть **диапазоном** (`800-1200х200х12`,
  `1500х150-200х15`, §6.3). Сравнивать размеры с учётом диапазонов (пересечение/вхождение),
  не считать диапазон расхождением.
- **Проверка `parent` vs `collection`.** `parent` — имя родительской папки, обычно
  отражает коллекцию. Если агент видит **явное несоответствие** `parent` и `collection`
  у товаров (или между тем, что в прайсе, и папкой) — **предупредить админа до обновления
  цен** (вывести в предложении §9.3), не блокируя молча.
- Сопоставление выполняет **агент**; **спорные** (низкая уверенность / несколько
  кандидатов) показываются админу на **подтверждение** перед записью.
- Цена указывается относительно той ЕИ (`unit`), которая используется у данного товара
  в 1С (§6.3).

## 8. Этап 2. Чтение из 1С: ТМ к выгрузке и номенклатура с ценами

Все операции чтения — через существующий HTTP-сервис 1С, база
`/api_shop/hs/ai-tools/`. **Аутентификация — заголовок `X-API-Token: <токен>`** во всех
запросах. Обе операции ниже **уже реализованы** и проверены на боевом сервере.

### 8.1. Проверка выгрузки ТМ на сайт (`selling-tm`)
- `GET .../get-products/selling-tm` → все торговые марки, стоящие **к выгрузке на сайт**
  (каскад «Не выгружать» уже учтён на стороне 1С). Без параметров и пагинации.
- По ТМ, встретившимся в прайсе, оставляем только те, что реально выгружаются; поле `Code`
  ТМ — вход для `by-tm` (§8.2).

**Формат ответа** (реальный, проверен на бою — 168 ТМ):
```jsonc
// Ответ — JSON-массив объектов (+ UTF-8 BOM), без пагинации:
[
  {"NameTM": "Classen / Классен", "Code": "000000104"},  // NameTM — наименование ТМ (лат/кир)
  {"NameTM": "Egger / Эггер",     "Code": "000000006"}   // Code   — уникальный код ТМ (строка) → tm= в by-tm
  // ... 168 записей
]
```
- Поля именованы `NameTM` / `Code` (с заглавной); `Code` — **строка** (ведущие нули важны).
- Порядок записей не гарантирован (не алфавитный) — сортировать/индексировать на нашей стороне.
- **Аутентификация обязательна**: без валидного `X-API-Token` сервис отвечает **HTTP 500**
  (HTML-страница IIS), а не 401/403 — коннектор должен трактовать не-JSON/500 как ошибку авторизации/сервиса.

### 8.2. Номенклатура одной ТМ с ценами (`by-tm`)
Основной источник данных для сопоставления (§7) и сравнения цен (§9).

- `GET .../get-products/by-tm?tm=<код ТМ>&page=<N>&size=<200>` — `tm` = **код ТМ** из
  `selling-tm`; пагинация — `page` (с 1) и `size` (напр. 200).
- Возвращает **только экспортируемые** товары: каскад флага **«Не выгружать»**
  разрешается **на стороне 1С** тем же механизмом, что и `selling-tm` (единый источник
  истины, дерево в Python не дублируем).
- **Цены — inline**: срез последних из регистра сведений по ВидЦен ∈ {Закупка, РРЦ};
  `date` = период активной записи = когда цена менялась в последний раз (сразу закрывает
  проверку «<1 мес» из §9.2 — отдельного запроса истории не нужно).

**Формат ответа** (реальный, проверен на ТМ Classen — 241 товар, 2 страницы):
```jsonc
// Ответ — JSON-объект «шапка + items» (+ UTF-8 BOM):
{
  "tm": "Classen / Классен",
  "total": 241,
  "offset": 1,            // = номер запрошенной страницы (page)
  "limit": 200,           // = size
  "items": [
    {
      "ref": "YO-00075249",           // Код/ссылка 1С — стабильный ключ для записи цен
      "id": "106754",                 // ID сайта — строка
      "name": "Ламинат Classen  VisioGrande WR  Мягкий Хлопок Белый",  // всегда заполнено
      "article": "56649 ",            // бывает "" или с хвостовыми пробелами (не null)
      "unit": "м2",                   // базовая ЕИ (для пересчёта цены, §6.3)
      "size": "604x280x8",            // на практике заполнен у всех
      "product_type": "Ламинат",       // вид товара
      "collection": "Visiogrande",     // очищенное имя коллекции
      "parent": "Classen Visiogrande", // сырое имя родительской папки
      "prices": [
        {"purchase": {"value": 960,     "date": "2026-07-14"}},
        {"rrc":      {"value": 1140.75, "date": "2026-06-07"}}
        // элемент ОТСУТСТВУЕТ, если по этому виду цены записи нет (не null)
      ]
    }
  ]
}
```
- Иерархия уже разложена в поля (`product_type/collection/parent/size/article`) — агенту
  удобно матчить строки прайса, не разбирая дерево.
- **`size`** — мм, формат `Д×Ш×Т`; у ламината/паркетной/массивной доски Д и Ш могут быть
  диапазоном (`800-1200х200х12`) — цена за м² при этом единая (§6.3).
- **`parent`** — сырое имя родительской папки, обычно = коллекция; расхождение
  `parent`/`collection` → предупредить админа (§7, §9.3).
- **`product_type`** — в пределах одной ТМ может быть **несколько** типов; фильтровать при
  сопоставлении (§6.6, §7).
- **`ref`** (Код 1С) — ключ для последующей записи цен (§10), не зависит от наименования.
- **Нормализация на нашей стороне** (Python-коннектор): читать `items` прямо из объекта
  ответа; `article` → `strip()`; `prices` (массив синглтонов) → словарь `{purchase?, rrc?}`;
  `id` — строка; учесть BOM (`utf-8-sig`). Наблюдения по Classen: `size` и `purchase` —
  у всех 241; без `article` — 33; без `rrc` — 10.

### 8.3. Рекомендация по запросу в 1С (для разработчика HTTP-сервиса)
- `Справочник.Номенклатура`: отбор `Производитель = &ТМ`, `ЭтоГруппа = Ложь`,
  `НЕ ПометкаУдаления`.
- **Экспортируемость**: исключить элементы, у которых любой родитель имеет «Не выгружать» —
  переиспользовать функцию/признак из `selling-tm` (желательно материализованный признак,
  чтобы не обходить дерево на каждый элемент).
- **Иерархия**: подъём по `Родитель` → коллекция (непосредственная папка) и вид товара
  (папка под корнем «Товары и услуги»); ТМ — напрямую из `Производитель`.
- **Цены**: соединение с `РегистрСведений.<Цены>.СрезПоследних(, ВидЦен В (&Закупка,&РРЦ))`
  по `Номенклатура`; вернуть Цена и Период.
- **Пагинация**: по `page`/`size` (`ВЫБРАТЬ ПЕРВЫЕ size` со смещением `(page-1)*size`,
  устойчивая сортировка по Коду/Ссылке); в ответе отдавать `total` (реализовано).

### 8.4. Потребление агентом (без перегруза контекста)
- Инструмент чтения возвращает **один пакет `size`** позиций; оркестратор
  (`src/agent/orchestrator.py`, ручной loop) листает страницы (`page`) по `total`.
- Scoping: ТМ из прайса ∩ `selling-tm`. На практике ТМ ≈ до ~241 товара (Classen) → 1–2
  страницы по 200, фильтрацию по коллекции делаем **на нашей стороне** после выборки
  (параметр `collection` в эндпоинте пока не подтверждён).

## 9. Этап 5. Сравнение цен и предложение админу

### 9.1. Выявление изменений
- Текущие цены (закупка, РРЦ) уже пришли **inline** в `by-tm` (§8.2) — отдельный запрос
  не нужен.
- Сравнить с ценами из прайса (после пересчёта к базовой ЕИ) → список изменившихся.

### 9.2. Защита периодического регистра
- Цены в 1С — **периодический регистр сведений**. Дата последнего изменения приходит в
  `by-tm` как `prices.*.date`: если цена менялась **меньше месяца назад** — предупредить
  админа и запросить подтверждение до записи.
- Оценить, на сколько процентов меняется цена **в среднем по каждой коллекции**, и дать
  админу принять окончательное решение.

### 9.3. Формат предложения (из источника)
```
Обновляем цены от [Поставщик] на:
-[ТМ1]
 *[коллекция1]
 *[коллекция2]
 * ...
-[ТМ2]
 *[коллекция1]
 * ...
?
```
Если в прайсе несколько колонок под один вид цены — предварительно уточнить, из какой
колонки заполнять (§6.5). Для затронутых коллекций показать средний % изменения (§9.2)
и предупреждение о недавней смене цены, если применимо.

**Предупреждения перед обновлением** (показать админу, не блокируя молча):
- **расхождение `parent`/`collection`** у сопоставленных товаров (§7);
- прайс затронул **несколько `product_type`** — перечислить, к какому типу отнесены цены (§6.6).

## 10. Этап 6. Запись цен в 1С — `set-prices` (ОПЕРАЦИЯ ЗАПИСИ)

Единственная операция записи. Выполняется **только после явного подтверждения** админа
(§9.3). Пишет **цену закупки и/или РРЦ** в периодический регистр сведений.

### 10.1. Эндпоинт и аутентификация
- `POST .../set-prices` (та же база `/api_shop/hs/ai-tools/`).
- Заголовки: `X-API-Token: <токен>`, `Content-Type: application/json; charset=utf-8`.
- Идентификация товара — по **`ref`** (Код 1С из `by-tm`, §8.2), не по наименованию.

### 10.2. Тело запроса
Симметрично формату цен в `by-tm`: значение + опц. дата актуальности. Передаются **только
изменяемые** виды цен (отсутствующий вид — не трогаем).
```jsonc
{
  "date": "2026-07-29",          // дата актуальности по умолчанию (Europe/Moscow, день)
  "items": [
    {
      "ref": "YO-00075249",
      "prices": {
        "purchase": {"value": 980.0},                    // date опускается → берётся общий "date"
        "rrc":      {"value": 1200.0, "date": "2026-07-29"}
      }
    }
    // ... пакетно, все подтверждённые позиции одного предложения
  ]
}
```
- `value` — цена за **базовую ЕИ** товара в 1С (та же `unit`, что в `by-tm`; новые ЕИ не
  создаются, §6.3). Пересчёт из прайса делаем **до** записи.
- `date` — день актуальности в периодическом регистре; общий на уровне запроса, с опц.
  переопределением на позицию/вид цены. По умолчанию — сегодня (Москва).
- Виды цен: `purchase` = «Закупка», `rrc` = «РРЦ» (точные представления ВидЦен в 1С — §16).

### 10.3. Ответ
Пер-позиционный результат (частичный успех допустим):
```jsonc
{
  "updated": 1,
  "failed": 0,
  "results": [
    {
      "ref": "YO-00075249",
      "status": "ok",                                   // "ok" | "error"
      "written": {
        "purchase": {"value": 980.0, "date": "2026-07-29"},
        "rrc":      {"value": 1200.0, "date": "2026-07-29"}
      }
    }
    // при ошибке: {"ref": "...", "status": "error", "message": "не найдено / не выгружается / неверная цена"}
  ]
}
```

### 10.4. Валидация на стороне 1С (обязательна)
- `ref` существует, это **конечный элемент** (не группа), **не** помечен на удаление и
  **экспортируемый** (не под «Не выгружать»); иначе — `error` по позиции.
- ВидЦен из запроса существует; `value` > 0 (число). Иначе — `error`.
- Запись только в регистр цен; **никаких других записей/удалений**.

### 10.5. Поведение на нашей стороне
- Идемпотентность: ключ регистра — (Номенклатура, ВидЦен, Период=день). Повтор той же
  записи за тот же день перезаписывает то же значение (без дублей истории).
- Перед записью повторно учесть предупреждения §9.2 (изменение <1 мес) — подтверждено (§9.3).
- Логировать записанное (`ref` → значения/дата) для аудита.
- После применения/отклонения — пометить прайс **обработанным** (§4.2).
- **Требования безопасности** (как в `cart-orders-1c.md`, §7.3): изменения в 1С — только
  с разрешения админа; запись цен — единственная разрешённая операция изменения.

## 16. Открытые вопросы (закрыть до реализации)

1. **`set-prices` — уточнения к контракту (§10 определён)** — на стороне 1С подтвердить:
   точные представления **ВидЦен** «Закупка»/«РРЦ» (наименование vs код) в теле запроса;
   гранулярность **Периода** (день ок? принимает ли `date` без времени); максимальный
   **размер пакета** `items`; форма ошибок по позиции. Контракт **чтения** — в §8.
2. **Порог сопоставления** — что считать «уверенным» vs «спорным» матчем строки прайса
   к товару (§7), при котором требуется подтверждение админа.
3. **Правила розничной цены** — будут описаны отдельной инструкцией (позже); тогда
   заполнить таблицу правил (§12) и точку применения (§6.4).
4. **Стабильность структуры прайсов** — насколько устойчива «сигнатура шапки» у поставщиков
   (объединённые ячейки, многострочные заголовки) для надёжного переиспользования маппинга.
5. **Формат «скидки от РРЦ»** — как в прайсе выражается скидка (процент/колонка/письмо) для
   вычисления закупки = РРЦ − скидка.
