# Спецификация: Поиск заказов из корзины и работа с заказами в 1С

> **Статус:** черновик. Источник требований — `create-orders-into-1C.txt`.
> Базовый спек системы (поиск товаров у поставщиков) — `master-spec.md`; данная функция
> добавляется поверх него и переиспользует те же компоненты (Telegram-бот, оркестратор,
> Email Tool). Существующий функционал не меняется по поведению.

---

## 1. Цель

Дать менеджеру возможность через Telegram-бот (текстом или голосом):

1. Найти в почте письмо-заказ, сформированное **корзиной сайта norwik.ru**, по нечёткому
   описанию («заказ из корзины за прошлую пятницу», название товара, адрес, имя клиента).
2. Сопоставить найденный заказ с заказами в **1С** (по дате, контакту, адресу, составу).
3. Если в 1С такого заказа нет — предложить **создать новый заказ в 1С**.
4. *(Будущий этап)* Выполнять действия с найденным/созданным заказом в 1С — см. §13.

---

## 2. Область охвата

### Входит в данную спецификацию
- Распознавание запроса о заказе из корзины (отличие от запроса о поиске поставщика).
- Разбор естественно-языковой даты («сегодня», «вчера», «в прошлую пятницу»).
- Поиск и разбор письма-заказа из корзины (новый тип письма).
- Сопоставление письма с заказами в 1С и форматы ответов из источника.
- Интерфейс компонента интеграции с 1С (чтение + создание заказа).
- Управление состоянием диалога в оркестраторе (многошаговый сценарий с уточнениями).

### НЕ входит (явно отложено)
- Детальный функционал **работы с заказом** в 1С после его нахождения/создания
  (источник обрывается на строке `##Далее будет описание функционала работы с заказом##`).
  В данной спецификации описано только доведение до точки «заказ найден / предложено создать».
- Редактирование/удаление писем и любые операции записи в почтовый ящик (как и раньше —
  Email Tool строго read-only).

## 3. Сценарий использования (полный поток)

```
Менеджер: «Посмотри заказ из корзины за прошлую пятницу, плитка Equipe, доставка в Балашиху»
   │
   ▼
[Э1] Распознать намерение = «заказ из корзины/1С» и извлечь параметры:
     дата/период, тип+бренд товара, адрес (возможно неполный), имя клиента
   │
   ▼
[Э2] Поиск письма-заказа из корзины в почте (частичное совпадение)
   ├─ найдено 0      → «нет подходящего заказа, дайте детальнее» → ждём новые данные → [Э2]
   ├─ найдено >1     → показать список → менеджер выбирает один → [Э3]
   └─ найдено 1      → [Э3]
   │
   ▼
[Э3] Поиск соответствующих заказов в 1С (дата ≥ даты письма, контакт, адрес, состав)
     ├─ найдено >1   → показать список заказов 1С → менеджер выбирает → [Э4]
     ├─ найдено 1    → показать заказ 1С → [Э4]
     └─ найдено 0    → «Похожих заказов в 1С не нашёл. Создать новый заказ в 1С?»
                        ├─ да  → создать заказ из данных письма → [Э4]
                        └─ нет → завершение
   │
   ▼
[Э4] Работа с заказом  →  TBD (см. §13)
```

Сценарий **многошаговый**: между шагами требуется ответ менеджера (выбор из списка,
уточнение данных, подтверждение создания). Это требует хранения состояния диалога —
см. §8.

## 4. Этап 1. Распознавание запроса и параметров

### 4.1. Маршрутизация намерения
Оба сценария (существующий «поиск поставщика» и новый «заказ из корзины/1С») проходят
через один оркестратор и один системный промпт. Промпт должен сначала классифицировать
намерение:

| Признаки запроса | Намерение |
|---|---|
| Упоминание «заказ», «корзина», «клиент», «доставка», период/дата, адрес | Заказ из корзины / 1С |
| Название товара + количество для закупки, без признаков клиента/заказа | Поиск поставщика (существующий) |

При неоднозначности — задать уточняющий вопрос, а не угадывать.

### 4.2. Извлекаемые параметры запроса
Все поля **необязательны и могут быть неполными** — менеджер задаёт ровно столько,
сколько помнит:

| Параметр | Примеры | Назначение |
|---|---|---|
| Дата / период | «сегодня», «вчера», «в прошлую пятницу», «на той неделе» | Фильтр писем по дате |
| Товар | «плитка», «ламинат Kronospan», «Equipe Palais» | Совпадение по строке товара письма |
| Адрес доставки | «Балашиха», «ул. Загородная», только город | Совпадение по блоку «Адрес» письма |
| Имя клиента | «Владимир» | Совпадение по блоку «Контактная информация» |

### 4.3. Разбор естественно-языковой даты
- Опорная дата — **текущая дата в часовом поясе Europe/Moscow**.
- Текущую дату необходимо передавать модели (сейчас оркестратор её не сообщает) —
  добавить в системный промпт или в начало пользовательского сообщения.
- Относительные выражения переводятся в диапазон дат для фильтра `since`/диапазона:
  - «сегодня» → текущий день;
  - «вчера» → предыдущий день;
  - «в прошлую пятницу» → ближайшая пятница до текущего дня;
  - «на той/прошлой неделе» → диапазон Пн–Вс предыдущей недели.
- Если дата не указана — поиск без жёсткого ограничения по дате (с разумным лимитом,
  например последние 30 дней), полагаясь на остальные параметры.

## 5. Этап 2. Поиск письма-заказа из корзины

### 5.1. Шаблон письма (как генерирует корзина сайта)

Письмо имеет устойчивую структуру. Пример (из источника):

```
Керамическая Плитка Equipe Palais blue 20x20x0,9
1c: 71954 ///// Норвик: 124383 ///// У производителя: КА-00018921
14 м2 * 4800 = 67200 руб.
http://www.norwik.ru/item/124383

Итого: 67200 руб.

Вариант доставки: По Москве (2 500 руб.)

Дата доставки: 20.06.2026

Если доставка выпадает на выходной или праздничный день, то она будет перенесена на ближайший рабочий

Вариант оплаты: Наличными (при получении)

---------- Контактная информация ----------
Владимир
+7 (965) 177-83-89
nsonnov@yandex.ru

---------- Адрес ----------
Балашиха ул. Загородная 48
```

### 5.2. Разбираемые поля

| Поле | Источник в письме | Примечание |
|---|---|---|
| Позиции заказа | Блоки до строки «Итого» | Письмо может содержать несколько позиций |
| → Название товара | Первая строка позиции | `Керамическая Плитка Equipe Palais blue 20x20x0,9` |
| → Коды товара | Строка `1c: … ///// Норвик: … ///// У производителя: …` | `1c` — код номенклатуры в 1С (ключ для §6) |
| → Кол-во, ед., цена, сумма | Строка вида `14 м2 * 4800 = 67200 руб.` | Парсить: кол-во, ед.изм, цена за ед., сумма |
| → Ссылка | URL `norwik.ru/item/{id}` | ID совпадает с «Норвик» |
| Итого | `Итого: … руб.` | Сумма заказа (для списка совпадений) |
| Вариант доставки | `Вариант доставки: …` | Включая стоимость доставки в скобках |
| Дата доставки | `Дата доставки: ДД.ММ.ГГГГ` | |
| Вариант оплаты | `Вариант оплаты: …` | |
| Контакт клиента | Блок `Контактная информация` | Имя, телефон, email (по строкам) |
| Адрес | Блок `Адрес` | Свободная строка |
| Дата создания заказа | Заголовок письма `Date` | Нижняя граница даты поиска в 1С (§6) |

> Парсер должен быть устойчив к отсутствию отдельных полей и к нескольким позициям.
> Разделители блоков (`---------- … ----------`) — якоря для контактов и адреса.

### 5.3. Классификация письма как «заказ из корзины»
Письмо-заказ нужно отличать от прайсов/остатков поставщиков. Признаки (по совокупности):
- тема письма вида `Заказ #18062026-1347`;
- приходит с почты `sale@norwik.ru`;
- наличие маркеров `Вариант доставки:`, `Дата доставки:`, `Вариант оплаты:`;
- наличие блоков `Контактная информация` и `Адрес`;
- строка кодов `1c: … ///// Норвик: … ///// У производителя: …`.

Рекомендуется ввести отдельный тип письма (например `CART_ORDER`) в существующем
классификаторе (`src/email_tool/classifier.py`), не ломая текущую логику прайс/остатки.
Также возможна фильтрация по отправителю (адрес, с которого корзина шлёт заказы) —
**уточнить при реализации**.

### 5.4. Логика сопоставления (частичное совпадение)
- Совпадение **нечёткое и по совокупности** параметров: совпало больше критериев —
  выше релевантность.
- Адрес сопоставляется по подстроке (город / улица), имя клиента — по подстроке,
  товар — по бренду/типу/коллекции.
- Финальный матч выполняет модель (как и в существующем поиске поставщиков).

### 5.5. Форматы ответа

**Найдено несколько подходящих писем:**
```
Нашёл несколько похожих заказов:
1. {Адрес} {Имя_клиента} {Сумма заказа, руб.}
2. ...

Какой именно заказ интересует?
```
Менеджер выбирает один из списка (номером).

**Не найдено ни одного:**
```
По вашему запросу нет ни одного подходящего заказа на почте. Дайте более детальную информацию
```
Если менеджер присылает новые данные — поиск повторяется (§5).

**Найдено ровно одно** — переход к Этапу 3 без дополнительного вопроса.

## 6. Этап 3. Поиск соответствующих заказов в 1С

После того как нужное письмо найдено, агент ищет в 1С заказы, которые могут ему
соответствовать.

### 6.1. Критерии сопоставления (по совокупности, не строго)
- **Дата создания** заказа в 1С — не раньше даты письма (`Date` письма или позже).
- **Контакт клиента** — имя / телефон / email из блока «Контактная информация».
- **Адрес доставки** — из блока «Адрес».
- **Состав товара** — позиции (по коду `1c`, названию, количеству, сумме);
  допускается неточное совпадение, оценивается совокупность.

### 6.2. Формат ответа (найдены заказы в 1С)
```
Заказ {Номер} от {Дата_создания}
1. {Название_товара} {Количество_товара} {Единица_измерения} {Цена} {Сумма}
2. ...

Следующий заказ {Номер} от {Дата_создания}
1. {Название_товара} {Количество_товара} {Единица_измерения} {Цена} {Сумма}
2. ...
```
Если похожих заказов **больше одного** — уточнить у менеджера, с каким работаем дальше.

### 6.3. Заказов в 1С не найдено
```
Похожих заказов в 1С не нашёл. Создать новый заказ в 1С?
```
- «Да» → создать новый заказ в 1С на основании данных письма (см. §7.3), затем Этап 4 (TBD).
- «Нет» → завершить диалог.

## 7. Компонент: Интеграция с 1С (новый)

> Это новый внешний компонент. В источнике **не указаны** ни конкретная конфигурация 1С,
> ни способ подключения. Ниже — требуемый интерфейс и открытые вопросы (§12), которые
> нужно закрыть до реализации.

### 7.1. Предполагаемый способ подключения
Наиболее вероятные варианты для 1С (выбрать один на этапе уточнения):
- **Стандартный OData-интерфейс** публикации 1С (HTTP, `/odata/standard.odata/…`).
- **Custom HTTP-сервис** (HTTP-сервисы 1С) с прикладными методами поиска/создания.
- Промежуточный обмен (выгрузка/COM/файловый) — наименее желательно.

Доступ должен быть **сетевым и аутентифицированным** (логин/пароль или токен), с учётом
того, что бот работает в облаке/Docker (см. `master-spec.md`, §7).

### 7.2. Чтение заказов — операция `search_orders`
Вход: дата «от», контакт клиента, адрес, позиции (коды/названия) — все опциональны.
Выход: список заказов с полями: номер, дата создания, контакт, адрес, позиции
(название, количество, ед.изм, цена, сумма), сумма заказа.

### 7.3. Создание заказа — операция `create_order` (ОПЕРАЦИЯ ЗАПИСИ)
Вход: позиции (код `1c`, количество, цена), контакт клиента, адрес, вариант доставки,
дата доставки, вариант оплаты — из разобранного письма (§5.2).
Выход: номер созданного заказа.

**Требования безопасности к записи:**
- Создание выполняется **только после явного подтверждения** менеджера («Создать новый
  заказ в 1С?» → «Да»).
- В отличие от Email Tool (read-only), 1С-компонент имеет операцию записи — она должна
  быть единственной и строго ограниченной (создание заказа); никаких других операций
  записи/удаления.
- Идемпотентность/защита от дублей: перед созданием повторно убедиться, что заказ
  действительно не найден (§6).

## 8. Управление состоянием диалога (изменение оркестратора)

Текущий оркестратор (`src/agent/orchestrator.py`) **stateless**: `handle_query(query)`
создаёт новый список `messages` на каждый запрос. Новый сценарий — многошаговый
(список → выбор → список → выбор → подтверждение), поэтому требуется сохранять контекст
диалога **между сообщениями одного чата**.

Требования:
- Хранить историю `messages` по ключу `chat_id` (или `telegram user_id`) между ходами.
- Ограничить время жизни диалога (TTL) и/или длину истории; предусмотреть сброс
  (например команда/фраза «новый запрос» или таймаут).
- Передавать в модель текущую дату (Europe/Moscow) — см. §4.3.
- Сохранить обратную совместимость: существующий одношаговый сценарий поиска поставщика
  продолжает работать в рамках той же истории.

Точное место хранения (память процесса vs SQLite) — решение реализации; для одного
инстанса достаточно in-memory с TTL, но при нескольких воркерах нужна общая БД.

Добавляются в `TOOL_DEFINITIONS` (`src/agent/tools.py`) и в `ToolExecutor`; статусные

## 12. Открытые вопросы (закрыть до реализации)

1. **1С: какая конфигурация и способ доступа?** (HTTP-сервис; адрес задам позже, вынести в .env. аутентификация через токен, права на создание заказа и контрагента будут в в аккаунте 1С под которым работает HTTP-сервис.)
2. **Структура заказа в 1С** для создания: обязательные реквизиты, контрагент/клиент - один, прописан на стороне 1С, номенклатура по коду `1c` - в письме из корзины это "1c: 71954", где цифры - это уникальный код товара, склад - один, прописан на стороне 1С, организация - один, прописана на стороне 1С.
3. **Формат письма** — гарантирована ли стабильность шаблона §5.1; шаблон стандартный,
   может быть несколько позиций, разные варианты доставки/оплаты.
5. **Сопоставление с 1С** — какие поля считать ключевыми и каков порог «похожести». Все вышепереисленные поля являются равнозначными. Если есть совпадение по двум и более полям, то выводим в ответ, если совпадение по одному полю или нет вообще - то не выводим
6. **Хранение состояния диалога** — один инстанс (in-memory) или несколько (общая БД). Для каждого юзера нужно хранить историю диалога
7. **Часовой пояс и формат дат** в 1С и в письмах. Часовой пояс у них один - Москва
