# Модель работы с прайсами — спека реализации

Рабочий документ для написания кода. Обсуждение, из которого он вырос (46 вопросов с
обоснованиями решений), — в `specs/agent-workflow-model-qa.md`; обращаться туда стоит, когда
непонятно, **почему** правило именно такое. Исходное ТЗ — `dev_tasks/agent-workfloow-model.txt`.

> **Ждут подтверждения два пункта** (В45, В46 в qa-файле). Здесь записан рекомендованный
> вариант: статус задачи `отклонена` существует (§3.4), а при пересборке описание админа
> сохраняется над свежим текстом LLM (§6.3). Если решение будет иным, правится по одному
> месту в каждом случае.

Соглашение о словах: **модель** — программная модель состояния; **LLM** — языковая модель;
**агент** — процесс бота целиком. В исходном ТЗ всё это называлось «агентом».

---

## 1. Назначение и границы

Модель хранит состояние всех полученных прайсов и задач по ним. Она **не зависит от
визуала** и не знает о существовании Telegram и 1С.

- Модель **не** разбирает файлы, **не** ходит в 1С, **не** формирует сообщения.
- Модель — **синглтон**: сколько бы ни было админов, список прайсов и задач один.
- Визуалы **только шлют команды** и **получают уведомления**.
- Уведомления формирует код, **без участия LLM**.

Агент один на всех админов: команды от разных админов обслуживает один цикл.

## 2. Справочники

Три уровня, иерархия строгая:

```
supplier              поставщик
 └── signature        сигнатура формата (у поставщика их несколько)
      └── price_file  файл прайса на сервере
```

### 2.1. Поля

**`supplier`**: `id`, имя (отображаемое), имя нормализованное, дата создания.

**`signature`**: `id`, `supplier_id`, хеш сигнатуры (`price_signature`), имя-образец файла,
назначение («ламинат», «плитка»), дата первой встречи, дата последней встречи.

**`price_file`**: `id`, `signature_id`, имя файла, путь на сервере, дата получения, дата
добавления.

Нормализация имён везде — существующая `scope.normalize` (регистр, пунктуация, двойные
пробелы, ё→е).

### 2.2. Опознание поставщика

1. Админ прислал файл и **назвал поставщика** — берём его имя. Нет такого — заводим.
2. Имя не названо — **опознаёт LLM** по сигнатуре, содержимому и имени файла; привязывает к
   существующему поставщику либо заводит нового, назвав на своё усмотрение.
3. Вывод **закрепляется**: под поставщиком заводится (или находится) сигнатура, под
   сигнатурой — запись о файле.

Одинаковая сигнатура **может** принадлежать разным поставщикам: это разные записи, и любое
обращение к сигнатуре учитывает владельца. Несколько кандидатов — выбирает LLM по остальным
признакам; ошибку админ правит командами справочника.

Опознание по признакам письма (домен, адрес отправителя) — **за рамками**, до появления
приёма из почты.

### 2.3. Операции над справочниками

Показать список, добавить, удалить, переименовать поставщика, перепривязать сигнатуру к
другому поставщику, **слить двух поставщиков**.

Списки **сортируются по дате добавления**, дата показывается в формате `дд.мм.гг чч.мм`.

**Слияние.** Сигнатуры вместе с подчинёнными файлами переезжают к поставщику-получателю.
Поставщик-источник **уничтожается**: все ссылки на него (включая эксклюзивы и прочие
атрибуты) заменяются на получателя.

Исторические строковые `supplier` из старых таблиц **не мигрируются** — справочники
заводятся с нуля.

## 3. Сущности модели

```
PriceList (синглтон)
 └── Price
      ├── SupplierPrice
      └── PriceTask[]
```

### 3.1. `SupplierPrice`

Поля: ссылка на `supplier`, список ТМ, дата получения (когда прайс пришёл агенту — **не**
дата внутри файла), ссылка на `price_file`.

**Без ссылки на файл объект существовать не может.**

Элемент списка ТМ: `{код 1С, имя, есть_в_1С: bool}`. ТМ, которой в 1С нет или которую LLM не
смогла сопоставить, в список всё равно попадает — с признаком «нет в 1С».

Список ТМ заполняется **после** разбора файла; объект создаётся сразу с пустым списком.

Источник прайса (Telegram, почта) в модели **не фиксируется**.

### 3.2. `Price`

Поля: `SupplierPrice`, дата создания объекта, статус, ссылка на более свежий прайс, список
задач, состояние захвата (§5.1).

**Дата создания** может не совпадать с датой получения: письмо пришло вчера, объект завели
сегодня.

**Статус:** `к обработке` | `частично обработан` | `выполнен`.

- Статус **ставит админ** командой; модель его не выставляет сама.
- Модель вычисляет **готовность**: прайс готов к закрытию, когда все задачи в состоянии
  `выполнена`, `частично обработана` или `отклонена`. Готовность — подсказка визуалу, не
  переход.

**Признак «есть более свежий»** — производная от ссылки: ссылка есть → `true`.

- Ссылка указывает **всегда на самый новый** прайс, не на непосредственно следующий.
- При появлении более нового модель **проходит все устаревшие и переписывает им ссылку**.
- При уничтожении самого свежего ссылки переставляются на **следующий по свежести из
  оставшихся**; очищаются, только когда более новых не осталось.
- Есть операция снятия ссылки (привязали ошибочно).

**Устаревание работу не блокирует.** Модель выполняет команды по устаревшему прайсу как
обычные; предупреждать — дело визуала.

«Тот же прайс» — пара **(поставщик, сигнатура)**, не поставщик: он дробит прайс по типам
товаров, и иначе «плитка» была бы новее «ламината».

### 3.3. `PriceTask`

Поля: `id`, дата создания, вид, предмет, адрес, статус, описание, результат, дата выполнения.

**Виды** (и порядок сортировки):

1. `нормализация наименований`
2. `изменение свойств`
3. `перенос в снятые`
4. `добавление новых`
5. `изменение цен`

Порядок — **подсказка админу, не запрет**: выполнять можно в любом.

**`перенос в снятые`**: в 1С ничего не удаляется, товар переносится в папку снятых **по виду
товара** сменой `parent_ref`, по жёсткой таблице `src/price_tool/discontinued.py`. Папку
выбирает код, не LLM; отсутствия вида товара в таблице — отказ, а не повод взять глобальную
папку. Задача заводится только по коллекциям, реально разобранным в этом файле: отсутствие
товара в ОДНОМ файле не значит, что он снят.

**Предмет:** `коллекция` | `товар`.

**Адрес:** `{марка, коллекция}` либо `{марка, товар}`. Задача хранит **все** идентификаторы,
какие знала о себе (см. §6.4) — не один.

- товар: код 1С, если есть; иначе артикул (если есть) плюс наименование из прайса.

**Уникальность:** пара (адрес, вид) уникальна **в пределах одного `Price`**. Повторное
создание такой задачи — не вторая задача, а **дополнение описания существующей**.

**Описание** пишет LLM при создании; админ может его править.

**Результат** и перевод статуса — за LLM. Дата выполнения обновляется при каждом переводе в
`выполнена` или `частично обработана`.

**Уничтожить задачу может только админ.** LLM создаёт задачи при создании `Price` и при
пересборке (§6.3), но не удаляет.

### 3.4. Статусы задачи

| статус | смысл |
|---|---|
| `к обработке` | не начата либо не удалось ничего |
| `выполнена` | сделано |
| `частично обработана` | часть задуманного не удалась; в результате обязательны причина и что сделано |
| `отклонена` | админ решил не делать |

`частично обработана` — **информационный** статус и штатный исход. Если не получилось
**ничего**, задача остаётся `к обработке`.

`отклонена` ставит только админ. Он же может вернуть задачу в `к обработке`.

## 4. Приём прайса

Метод модели один, **провайдеронезависимый**, с параметром «принудительно»:
`submit(file, supplier_hint=None, force=False)`.

**Обычный приём:**

1. Прочитать файл, посчитать сигнатуру.
2. Опознать поставщика (§2.2), завести/найти сигнатуру и запись о файле.
3. Проверить свежесть по паре (поставщик, сигнатура).
4. Устарел → **отказ**: `Price` не создаётся, **файл и запись о нём удаляются**. Поставщик и
   сигнатура сохраняются — они про опознание, а не про прайс.
5. Не устарел → создаётся `Price` со статусом `к обработке` и пустым списком ТМ.

**Принудительный приём:** шаги 1–2 те же, шаг 3 **пропускается**. `Price` создаётся, файл
остаётся, признак устаревания и ссылка проставляются сразу.

«Принудительно» — признак **поступления**, известный до проверки свежести. Спасать уже
отклонённый файл нельзя: его нет.

**Удаление файла блокируется**, пока на него ссылается хоть один объект модели. Механизм
есть: `price_file_in_use`, `known_price_paths` (`src/storage/pricing.py`), `sweep`
(`src/storage/price_files.py`, чистит только сирот и только при старте).

## 5. Блокировки

Два независимых механизма.

### 5.1. Захват прайса — координация между админами

Захватывается **прайс целиком**, не отдельная задача: задачи одного прайса конфликтуют между
собой (правка справочника и цены по одной коллекции).

- **Жёсткий запрет:** команды других админов по захваченному прайсу **отклоняются** с ответом
  «прайс занят».
- Отнять захват нельзя — второй админ ждёт.
- **Аренда 10 минут, с продлением на каждой итерации цикла.** То есть 10 минут означает «10
  минут без признаков жизни», а не от старта: живая тяжёлая задача захват не теряет.
- **После выполнения задачи захват держится ещё 1 минуту**, потом снимается: тот же админ
  скорее всего продолжит, и за это время визуалы успевают обновиться.
- **Досрочное снятие** — команда админа.
- **Истечение аренды**: прогон отменяется, захват снимается, **все визуалы уведомляются**.

**Маркер поколения.** Каждому прогону выдаётся возрастающий номер; изменение состояния несёт
свой номер, модель отвергает изменения с устаревшим. **Проверка обязана стоять
непосредственно перед записью в 1С** (`set_items` / `set_prices`), а не только перед сменой
статуса: необратима именно запись.

Три слоя вместе: продление аренды не даёт отобрать захват у живого прогона; отмена прогона
реально прекращает работу и расход токенов; маркер поколения закрывает промежуток между
отменой и записью.

### 5.2. Задача в работе — защита от повторного запуска

Если задача уже выполняется, повторная команда — **даже от того же админа** — её не
перезапускает. Все визуалы уведомляются, что задача в работе.

**Задачу закрывает модель независимо от того, жив ли визуал.** Если приславший команду
«отвалился», выполнение доводится до конца и статус записывается.

**Повторная команда по уже выполненной задаче** → ответ «задача уже выполнена»; визуал обязан
перечитать состояние и привести интерфейс в соответствие. Факт доставки уведомлений нигде не
фиксируется (гарантий доставки нет, §8), а состояние задачи модель знает точно.

## 6. Задачи: жизненный цикл

### 6.1. Создание

Задачи заводит **LLM через инструмент** — при создании `Price` и при пересборке.

Три из пяти видов уже вычисляет существующий код: `CollectionPlan.created` ↔ «добавление
новых», `.updated` ↔ «изменение свойств», `.normalized` ↔ «нормализация наименований»
(`src/price_tool/items.py`).

### 6.2. Выполнение

Команда несёт `id` задачи. Агент получает: **идентификатор, актуальное описание** (уже с
правками админа), **прошлый результат и текущий статус**.

Последние два обязательны: у задачи `частично обработана` без них LLM не знает, что уже
сделано, и повторит удавшуюся часть — запишет цены дважды или создаст созданное.

**Проверку записи делает сама LLM:** прежде чем поставить `выполнена`, она обязана убедиться
своими инструментами, что изменения в 1С записаны. Вето со стороны кода нет.

### 6.3. Пересборка списка

Команда «собери задачи по этому прайсу заново». LLM заново анализирует, обращаясь к 1С, и
строит актуальный список. Уже сделанная работа в него не попадёт — расхождений по ней нет.

- **Статусы совпавших задач переносятся** (§6.4). «Собери заново» — пересборка состава, а не
  сброс решений админа.
- Переносится **только `отклонена`**. `выполнена` и `частично обработана` **не переносятся**:
  раз задача создалась заново, расхождение сегодня есть, и работа снова актуальна.
- **Описание:** правка админа сохраняется **над** свежим текстом LLM. Терять молча нельзя ни
  анализ, ни решение админа; противоречие между ними админ увидит и разрешит.
- **Если по прайсу выполняется задача — команда отклоняется** с перечнем незавершённых
  задач. Ни прерывания, ни очереди: прерывание может застать запись в 1С на середине.

### 6.4. Сопоставление задач при пересборке

Совпадение = **тот же вид** И **та же марка** И **совпадение предмета хотя бы по одному
непустому идентификатору**.

Поэтому задача хранит все идентификаторы, какие знала о себе:

| предмет | идентификаторы |
|---|---|
| марка | код 1С, нормализованное имя |
| коллекция | код папки 1С, нормализованные имена (все, под которыми встречалась) |
| товар | код 1С, нормализованный артикул, нормализованное имя из прайса |

Один идентификатор недостаточен, потому что адрес меняется от нашей же работы: «QUARTZ»
после нормализации становится «Quartz»; товар без кода 1С после создания код получает; папка
коллекции появляется там, где было только имя.

Приём и его обоснование — из существующего `_collection_keys`
(`src/agent/pricing_tools.py:703`): **лишний ключ безвреден, недостающий запер бы работу
намертво.**

**Неоднозначность — повод не переносить:** если на одну новую задачу претендуют две старые
(или наоборот), статус не переносится, задача остаётся `к обработке`, админу сообщается.

## 7. Команды визуалов

Визуал кладёт команду в очередь; агент забирает её своим циклом (§9) и применяет.

| команда | параметры |
|---|---|
| принять прайс | файл, подсказка о поставщике, признак «принудительно» |
| выполнить задачу | `task_id` |
| сменить статус задачи | `task_id`, статус |
| сменить статус прайса | `price_id`, статус |
| изменить описание задачи | `task_id`, текст |
| удалить задачу | `task_id` |
| пересобрать задачи | `price_id` |
| уничтожить прайс | `price_id` |
| снять захват досрочно | `price_id` |
| операции справочников | §2.3 |

**Каждая команда несёт отметку времени своего создания на стороне визуала.**

**Схлопывание.** Повторная смена статуса того же объекта **перезаписывает** лежащую в
очереди команду, а не добавляет вторую: в модель приезжает последнее решение, а не цепочка
промежуточных.

**Кто первый, тот и работает.** Если за цикл пришло несколько команд по одному прайсу,
выполняется первая — **по времени создания на стороне визуала**, а не по порядку обхода
провайдеров; остальным отвечаем «прайс занят».

---

## 8. Уведомления

Модель объявляет протокол слушателя; провайдеры подписываются.

События: прайс добавлен, статус прайса изменён, прайс уничтожен, задача добавлена, статус
задачи изменён, **задача взята в работу**, прайс захвачен, **захват снят** (в том числе по
таймауту), справочники изменены.

**Гарантии доставки нет.** Недоставленные уведомления не копятся: визуал при подключении
перечитывает состояние.

---

## 9. Опрос визуалов

Агент забирает команды сам. Слушатель на VPS не поднимается: это открытая наружу точка входа
с портом и аутентификацией, и он всё равно не избавляет от очереди на стороне 1С (иначе
команда теряется при перезапуске агента).

**Интерфейс провайдера единый**: «отдай накопившиеся команды». Для 1С — запрос к её очереди.
Для Telegram транспортом остаётся `aiogram`, но обработчики **не действуют сами**: кладут
команду в очередь, которую забирает тот же цикл.

### 9.1. Период

| состояние | период | когда |
|---|---:|---|
| активное | **5 с** | команда от любого визуала или выполнение задачи в последние 5 минут |
| простой | **30 с** | активности не было дольше 5 минут |

Любая активность **мгновенно** возвращает к 5 секундам. Около 4 100 запросов в сутки вместо
17 280 при постоянных пяти секундах.

**Telegram цикла не ждёт:** `aiogram` доставляет событие сразу, провайдер **будит цикл**.
Адаптивный период управляет только частотой похода в 1С. Худший случай — первая команда из
1С после простоя, до 30 секунд.

**Требование к эндпоинту очереди команд в 1С: он читает маленькую таблицу и НЕ трогает
Номенклатуру.** Замеры на боевой базе: чистые накладные HTTP-сервиса — **231 мс**, тривиальный
запрос с обращением к Номенклатуре — **1 263 мс**. При лёгком эндпоинте пятисекундный опрос
стоит 4,6 % занятости 1С, при тяжёлом — 25,3 %.

Числа подобраны, а не выведены: меняются константами.

## 10. Хранение

Состояние пишется в БД **при каждом изменении**: остановка VPS или сбой визуала не должны
терять данные и рассинхронизировать модель с визуалом.

Таблицы **нормализованные**, не сериализованный граф: под команду «выполни задачу N» нужен
адресуемый идентификатор, а не переписывание блоба.

Новые таблицы: `supplier`, `supplier_signature`, `supplier_price_file`, `price`, `price_task`,
`command_queue`. Состояние захвата — поля на строке `price`.

**Агент на VPS один**, и только он работает с БД и с визуалами. Визуалы к БД напрямую не
обращаются, поэтому синглтон в памяти процесса остаётся настоящим синглтоном и блокировка на
уровне БД не нужна.

**Истечение и чистка не делаются** — прайсы копятся; механизм чистки появится позже.

## 11. Что меняется в существующем коде

**Снимается гейт `propose_prices`** — сейчас цены по коллекции не принимаются, пока по ней не
вызван `propose_items`. При свободном порядке задач (§3.3) он бы ломал работу. Вместе с ним
снимаются покрывающие его тесты. Причина, по которой гейт появился: цены уезжали по
несверенному справочнику.

**Становится «на прайс» то, что сейчас «на пользователя»:**

| сейчас | ключ | станет |
|---|---|---|
| `dialog_state` | `user_id` | история на каждый прайс |
| `active_price` | `user_id` | указатель «какой прайс открыт» |
| `price_run` | `user_id` | план и очередь марок внутри `Price` |
| `items_checked` | `user_id` + ключ | внутри `Price` |
| `pending_proposal` | `user_id` | несёт `task_id` |
| `_files` (память) | `user_id` | ссылка на файл в `SupplierPrice` |
| `_SEEN_READS` (память) | глобально «за прогон» | на прайс |

`_SEEN_READS` отдельно: он означает «эти данные уже приходили, возьми выше по переписке». При
переключении между прайсами переписка другая, и глобальная отметка подавила бы выгрузку,
которой в текущей истории нет.

**Переиспользуется без переписывания:**

- `src/price_tool/items.py` — `CollectionPlan.created/updated/normalized` → три вида задач;
- `src/price_tool/freshness.py` — `is_newer` для признака «есть более свежий»;
- `src/price_tool/signature.py` — сигнатура для справочника;
- `src/price_tool/discontinued.py` — папки снятых;
- `src/price_tool/scope.py` — `normalize` для всех ключей сопоставления;
- `src/storage/price_files.py` — блокировка удаления файла.
