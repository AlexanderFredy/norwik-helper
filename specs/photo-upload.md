# Фото товаров с сайтов производителей → на сайт norwik.ru

**Статус: план, не реализован** (записан 25.10.2026). Ждём от админа: FTP-доступ к каталогу
фото хостинга и id товара без фото для пробы (см. «Порядок работы», шаг 0).

## Зачем

На сайте norwik.ru у части товаров нет фото; находить такие товары агент уже умеет
(`find_items_without_photo`, журнал `photo_watch`, ежедневная проверка). Теперь нужно
закрывать дыры: брать фото с официальных сайтов производителя/дистрибьютора и загружать на
сайт.

## Решения админа (25.10.2026)

- **Откуда брать — только со страниц, которые админ прописал для марки.** Это не обязательно
  корень сайта: чаще прямо страница каталога марки, где лежат ссылки на коллекции, или
  сразу страница товаров с фото — чтобы не обходить весь сайт. Хранится в базе агента,
  искать вне этого нельзя.
- **Что обрабатывать — решает админ**: марка обязательна, список коллекций по желанию (не
  задан — вся марка). Автоматического сбора «всех товаров без фото» нет. Берутся только
  товары, которые выгружаются на сайт (без «Не выгружать», с id сайта) и у которых фото нет.
- **Человек утверждает**: агент собирает список «товар → страница-источник → фото», и
  только утверждённое уходит на сайт.
- **Все доступные фото** товара, а не одно.
- **Загрузка — по FTP прямо в каталог фото хостинга** (`/images/products/<id сайта>/`).
  ZIP для ручной загрузки — НЕ делаем. Довод, что сайт покажет файл из папки сам: при сверке
  30.09.2026 наличие фото на карточке совпало с наличием папки на 25 из 25 товаров. Но это
  наблюдение, а не доказательство (через админку имя файла генерируется: `5xe4gtu.jpg`, у
  карточки сейчас одна картинка), поэтому первым делом — проверка на одном товаре.
- Формат: JPG, хотя бы одна сторона не меньше 200 px.

## Что переиспользуем

- Отбор товаров без фото: `photo_scan.scan_category` / `photo_scan.scan`
  (`src/website_tool/photo_scan.py`), журнал `src/storage/photo_watch.py`, `NomItem.id` —
  id сайта = имя папки.
- Проверка «фото появилось»: `PhotoChecker` (`src/website_tool/photos.py`) — после загрузки
  ежедневная проверка сама отметит закрытие в журнале.
- Кнопки и отправка мимо модели: `ToolExecutor.pending_*`, `handlers._keyboard`,
  `_send_pending` (`src/agent/tools.py`, `src/bot/handlers.py`).
- Серверные инструменты Anthropic: `web_search_20260209` уже подключён в оркестраторе;
  добавить `web_fetch` с `allowed_domains` = домены страниц марки — модель физически не
  выйдет за разрешённый список.
- Pillow уже в зависимостях.
- Хранилище по образцу `photo_subscribers` / `signature_note` (`src/storage/`).

## Устройство

### 0. Проверка на одном товаре — ДО всей разработки
С разрешения админа, на товаре без фото, который он назовёт:
1. По FTP создать `/images/products/<id>/` и положить два JPG с именами в стиле сайта (7
   случайных строчных букв/цифр).
2. Проверить: карточка показывает фото? оба или одно, какое главное (по имени, по времени)?
   есть ли миниатюры/кеш, которые сайт строит сам?
3. Показалось — путь подтверждён, дальше как ниже. Нет — значит сайт ведёт список в своей
   базе, и тогда загрузка только через админку (нужен разбор её формы); пробную папку
   удалить.

### 1. Страницы-источники по марке (база агента)
- Таблица `photo_source(tm_code, tm_name, url, note, added_by, added_at)`, несколько адресов
  на марку; адрес — любая страница: каталог марки, страница коллекции, список товаров. Новый
  модуль `src/storage/photo_sources.py`.
- Команды в Telegram (только админ), как у `/photo_subs`: `/photo_sources [марка]`,
  `/photo_source_add <марка> <url> [пометка]`, `/photo_source_delete <номер>`. Марка
  сопоставляется с `selling_tm` тем же `photo_scan.match_marks`.
- Нет адресов у марки — запуск по ней отказывает с текстом «для марки X не задано, откуда
  брать фото: /photo_source_add …».

### 2. Отбор товаров (код, по указанию админа)
- Запуск: `/photo_find <марка> [; коллекция, коллекция…]` (и тот же вопрос агенту). Марка
  обязательна; без коллекций — вся марка.
- Код берёт выгрузку марки (`onec.by_tm_all`), оставляет: выгружаемые (без «Не выгружать»,
  непустой id сайта), нужных коллекций (сопоставление имён — общее
  `normalize.collection_keys`: размерный хвост и приставка марки снимаются), без фото
  (`PhotoChecker`; исходы «карточки нет» и «сайт не ответил» — не берём, называем числом).
  Не найденная коллекция называется в ответе.

### 3. Поиск кандидатов (модель, по коллекции)
- Новый модуль `src/website_tool/photo_finder.py`. **Прогон на КОЛЛЕКЦИЮ, а не на товар**:
  страница коллекции у производителя обычно одна на все декоры, и открывать её заново ради
  каждого — платить за одно и то же.
- Модели даются: страницы-источники марки (с них и начинать), список товаров коллекции (id
  сайта, название расцветки, артикул, размер). Инструменты: `web_fetch` с `allowed_domains`
  = домены этих страниц; `web_search` с теми же доменами — только запасной путь, если от
  страниц не дойти. Ответ — инструментом `propose_photos`: по каждому товару
  страница-источник, URL картинок и причина совпадения (артикул / название декора +
  размер). Неуверенно — пусто, а не догадка.
- Код скачивает картинки, проверяет (Pillow открывает; это не иконка/логотип: обе стороны ≥
  200 px — меньше отбрасывается, НЕ растягивается), приводит к JPG (RGB, качество 90, без
  EXIF), убирает дубли по хешу. Хранит в `data/photo_candidates/<id>/`.
- Таблица `photo_candidate(item_ref, site_id, tm, name, source_url, images json, reason,
  status: найдено/утверждено/отклонено/загружено, found_at, decided_by)`.

### 4. Утверждение человеком
- Итог — список «товар → страница-источник → N фото» в Telegram (длинный — Excel с
  гиперссылками, как сейчас) и по каждому товару карточка: альбом из найденных фото +
  кнопки «Утвердить / Отклонить». Утверждает админ (и, по решению админа, подписчики фото).

### 5. Загрузка по FTP
- Доступ в `.env` (не в коде, не в базе): `PHOTO_FTP_HOST`, `PHOTO_FTP_USER`,
  `PHOTO_FTP_PASSWORD`, `PHOTO_FTP_ROOT` (путь к `images/products`). По возможности FTPS
  (`ftplib.FTP_TLS`, стандартная библиотека), без него — обычный FTP; SFTP — если хостинг
  даёт его (`paramiko`).
- Модуль `src/website_tool/photo_upload.py`: по утверждённому товару — создать папку `<id
  сайта>` и залить все его JPG; имена в стиле сайта (7 случайных строчных букв/цифр),
  порядок/главное фото — как покажет проверка на шаге 0.
- **Только дописываем, ничего не перезаписываем и не удаляем.** Перед загрузкой папка
  проверяется: уже есть файлы (кто-то успел загрузить вручную) — товар пропускается и
  называется в отчёте. Права на каталог фото — всего сайта, поэтому ошибка здесь видна
  покупателям сразу.
- После загрузки — `PhotoChecker` по id: увидел фото → статус «загружено», журнал фото
  отметит закрытие сам. Не увидел — «загружено, на сайте не видно» и строка админу.
- Загрузку запускает кнопка «Утвердить» (или «Утвердить все» по списку).

## Стоимость (оценка)

На коллекцию: несколько `web_fetch` страниц производителя (+ изредка `web_search`, $10 за
1000) и ~20–60 тыс. токенов Haiku 5.5 ≈ $0.01–0.05; с прямой страницей коллекции в
источниках — нижняя граница. Скачивание и конвертация — код, токенов не стоят.

## Порядок работы

0. От админа: FTP-доступ (в `.env` на сервере и локально; узнать, есть ли FTPS/SFTP) и id
   товара без фото для пробы → проверка шага 0.
1. Страницы-источники: таблица, команды, тесты.
2. Отбор товаров по марке/коллекциям + поиск кандидатов + обработка картинок, на одной
   коллекции живьём.
3. Утверждение в Telegram + загрузка по FTP + проверка на сайте.

## Проверка

- Юнит-тесты: хранилище источников; отбор (только выгружаемые без фото, фильтр коллекций,
  без коллекций — вся марка, ненайденная коллекция называется, марка без источников —
  отказ); обработка картинок (PNG/WebP → JPG, отказ при <200 px, дубли по хешу);
  `allowed_domains` строятся из страниц марки; кнопки утверждения меняют статус.
- Загрузка — на тестовом FTP-сервере в юнит-тестах (`pyftpdlib` во временной папке): папка
  создаётся, существующие файлы не трогаются, занятая папка пропускается.
- Живой прогон на 3–5 товарах одной марки с заданными страницами: найденные страницы
  открываются, фото — того самого декора.
- Живьём: после загрузки `PhotoChecker` по id видит фото, журнал отмечает закрытие.
