# content-manager: схемы процессов

Блок-схемы к спеке [`content-manager.md`](content-manager.md) — для проверки логики целиком,
без чтения всего текста. Ссылки вида «§9.4» ведут на разделы спеки.

Формат — **Mermaid**: обычный текст, правится руками, рендерится в GitHub, VS Code
(расширение Markdown Preview Mermaid) и JetBrains. Ромб — решение, прямоугольник — действие,
скруглённый — вопрос админу (диалог останавливается до ответа).

**Легенда цветов**

```mermaid
flowchart LR
    A["действие агента"]:::act
    B{"решение"}:::dec
    C(["вопрос админу — ждём ответ"]):::ask
    D[("запись в SQLite")]:::db
    E["ЗАПИСЬ В 1С"]:::write

    classDef act fill:#eef4ff,stroke:#4a76c7,color:#123
    classDef dec fill:#fff8e6,stroke:#c79a29,color:#123
    classDef ask fill:#eafaf1,stroke:#2f9e6b,color:#123
    classDef db fill:#f3eeff,stroke:#7a5cc7,color:#123
    classDef write fill:#ffecec,stroke:#c74a4a,color:#123
```

## 5. Сравнение цен и защита регистра (§9.1–9.2)

```mermaid
    UNCH["unchanged: пропустить,<br/>в запись не идёт"]:::act
    CHG["changed: старая → новая, дельта %"]:::act

    DATE{"дата последнего<br/>изменения цены"}:::dec
    TODAY["Перезапись сегодня:<br/>информационно, подтверждения не требует"]:::act
    CHURN["Смена < 1 месяца назад:<br/>предупредить, требует подтверждения"]:::act

    RET["Посчитать розницу от НОВОЙ закупки:<br/>наценка по порогам → округление;<br/>РРЦ только сигнал — retail-price-rules.md"]:::act

    FORMB["writes: форма «б» — по товарам"]:::act
    NEXT["К сравнению поставщиков — схема 6"]:::act

    PAIR --> HAS
    HAS -- "нет" --> NEW --> DATE
    HAS -- "да" --> EQ
    EQ -- "да" --> UNCH
    EQ -- "нет" --> CHG --> DATE
    DATE -- "сегодня" --> TODAY --> RET
    DATE -- "меньше месяца" --> CHURN --> RET
    DATE -- "давно или не было" --> NORMAL --> RET
    RET --> AGG --> HOMO
```

> **Проверить при ревью:** периодичность регистра — ДЕНЬ, поэтому «перезапись сегодня» это
> не порча истории, а замена дневной записи; отдельного подтверждения не требует. А вот смена
> цены в предыдущий день в пределах месяца — требует.

## 5а. Расчёт розничной цены

Правила — [`retail-price-rules.md`](retail-price-rules.md). Считается для каждого
сопоставленного товара внутри шага «Посчитать розницу» схемы 5.

```mermaid
flowchart TD
    IN["Товар из прайса"]:::act
    CHG{"закупка<br/>меняется?"}:::dec
    HASP{"новая закупка<br/>известна?"}:::dec
    NONE["Розница не пересчитывается,<br/>остаётся как есть — §8, §9"]:::act

    TIER{"размер закупки"}:::dec
    M20["× 1.20"]:::act
    M15["× 1.15"]:::act
    M12["× 1.12"]:::act

    ROUND["Округлить до рубля — §4<br/>ЭТО ИТОГ: РРЦ цену не меняет"]:::act

    RRC{"РРЦ задана<br/>и свежая?<br/>не старше 1 мес."}:::dec
    LOW{"РРЦ ≤ закупки?"}:::dec
    BELOW{"РРЦ < розницы?"}:::dec
    W1["warnings: rrc_below_purchase<br/>«РРЦ ниже закупки — проверьте прайс»"]:::act
    W2["warnings: rrc_below_retail<br/>«наша цена выше РРЦ»"]:::act

    KNOWN{"текущая розница есть?<br/>by-tm отдаёт retail"}:::dec

    HASP -- "да" --> TIER
    TIER -- "< 1000" --> M20 --> ROUND
    TIER -- "1000…2000" --> M15 --> ROUND
    TIER -- "> 2000" --> M12 --> ROUND

    ROUND --> RRC
    ROUND --> KNOWN
    RRC -- "нет: не рассматриваем" --> KNOWN
    RRC -- "да" --> LOW
    LOW -- "да" --> W1
    LOW -- "нет" --> BELOW
    BELOW -- "да" --> W2
```

> **Проверить при ревью:** ветка РРЦ идёт **параллельно** записи и на величину цены не
> влияет — обрезки нет, РРЦ только даёт сигнал админу, и только пока она свежая. Триггер
> пересчёта — **только изменение закупки**; обновление одной РРЦ розницу не трогает. Порог
> 2 % — **только для розницы**: закупку и РРЦ пишем при любом отличии, это факты из прайса.

## 6. Сравнение поставщиков одной ТМ (§9.4)

Две **независимые** ветки: проверка качества данных по РРЦ и выбор поставщика по закупке.
Пороги §9.4.5 действуют только на вторую.

```mermaid
flowchart TD

    RRC{"РРЦ разошлась<br/>между поставщиками?"}:::dec
    RRCW["warnings: «ошибка в данных» —<br/>РРЦ диктует производитель — §9.4.2"]:::act

    PREF{"есть действующее<br/>предпочтение по ТМ?"}:::dec
    PREFOK{"разрыв вырос вдвое<br/>или решению > 180 дней?"}:::dec

    ANY -- "да" --> PREF
```

> **Проверить при ревью:** сравнивается только **закупка** и только по **пересечению
> позиций**. Проверка РРЦ идёт **своей веткой** и срабатывает даже когда вопрос о закупке не
> задаётся — иначе при действующем предпочтении ошибка в данных осталась бы незамеченной.
> База наблюдений пуста на старте, поэтому первые месяцы ветка «нет наблюдений» — норма.

## 7. Запись цен в 1С (§10)

Левая часть — наша сторона, правая — что делает обработчик 1С
(`specs/1c/set-prices.bsl`).

```mermaid
flowchart TD
    subgraph BOT["Агент"]
        W1["writes из предложения: формы «а» и «б»"]:::act
        W2["POST get-products/set-prices<br/>X-API-Token, одним батчем"]:::write
        W3["Разобрать ответ: updated, unchanged,<br/>failed, results, errors"]:::act
        W4["Сообщение админу:<br/>коллекция, было → стало, %"]:::act
```

## Где процесс ещё не определён

| Место | Что открыто | Раздел |
|---|---|---|
| Запуск | планировщик отсутствует, только ручная команда | §5.1 |
| Розничная цена | правила расчёта не заданы, в 1С не пишется | §6.4 |
| Коэффициенты ЕИ | расхождения только сообщаются, править в 1С нечем | §17 |
| Условия поставки | `terms` — текст для админа, автоприведения цен нет | §16.6a |
| Наполнение справочника | первые прайсы дадут вопрос про каждого поставщика | §16.6b |
| IMAP | доступ к ящику отключён на тарифе — блокирует §4 | §16.7 |
