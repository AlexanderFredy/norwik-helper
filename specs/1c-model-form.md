# Форма 1С для модели прайсов

Спека обмена и формы. Модель и её правила — `specs/agent-workflow-model.md`; здесь только то,
что делается в 1С и как это связано с агентом. Обоснования решений модели, на которые тут
есть ссылки, — в `specs/agent-workflow-model-qa.md`.

**Вопросы помечены Ф1–Ф10 и ждут ответов прямо в этом файле.** До ответов реализация не
начинается: почти каждый меняет конструкцию, а не оформление.

## 1. Направление обмена

У агента **нет входящего HTTP-сервера** и не будет (решение В26): слушатель — открытая наружу
точка входа с портом и аутентификацией, и он не избавляет от очереди на стороне 1С, потому
что команда, присланная в момент перезапуска агента, иначе теряется.

Отсюда обе стрелки идут **от агента**:

```
агент ──GET  agent-commands──▶ 1С     забирает команды формы
агент ──POST set-model-state─▶ 1С     кладёт состояние модели
```

Форма 1С **никуда не ходит по сети**. Она пишет команды в свою таблицу и читает состояние из
своих же таблиц, которые наполняет агент. Побочно это делает её устойчивой: агент лежит —
форма открывается и показывает последнее известное состояние.

## 2. Хранение в 1С

Три набора данных. Первые два — **зеркало**: их содержимое целиком определяет агент, 1С в них
ничего своего не пишет.

### 2.1. `МодельПрайсы`

| поле | смысл |
|---|---|
| `Идентификатор` | номер прайса в модели; по нему адресуются команды |
| `Файл` | имя файла прайса |
| `Поставщик` | имя как в справочнике агента |
| `Статус` | к обработке / частично обработан / выполнен |
| `Готов` | булево: все задачи закрыты — подсказка, что можно закрывать |
| `ЕстьБолееСвежий` | булево |
| `НомерБолееСвежего` | на какой прайс смотреть вместо этого |
| `ЗанятКем` | пусто = свободен |
| `ЗанятДо` | до какого времени держится захват |
| `Принят` | когда прайс попал в модель |

### 2.2. `МодельЗадачи`

| поле | смысл |
|---|---|
| `Идентификатор` | номер задачи; по нему адресуются команды |
| `Прайс` | номер прайса |
| `Вид` | нормализация наименований / изменение свойств / перенос в снятые / добавление новых / изменение цен |
| `Порядок` | число 1–5 для сортировки: порядок видов задан спекой и не алфавитный |
| `Предмет` | коллекция или товар |
| `Адрес` | «марка / коллекция» для показа |
| `Статус` | к обработке / выполнена / частично обработана |
| `Описание` | что предстоит сделать |
| `Результат` | что вышло; заполняется после выполнения |
| `Выполнена` | дата и время последнего перевода в закрытый статус |

Статусов у задачи ровно три, четвёртого нет. `частично обработана` — **штатный** исход, а не
авария: часть задуманного не удалась, и причина написана в `Результат`.

### 2.3. `МодельКоманды`

Единственная таблица, в которую пишет ФОРМА.

| поле | смысл |
|---|---|
| `Идентификатор` | номер команды в 1С |
| `Вид` | выполнить задачу / сменить статус задачи / сменить статус прайса / изменить описание задачи / пересобрать задачи |
| `Прайс`, `Задача` | к чему относится |
| `Данные` | JSON: статус либо текст описания |
| `Пользователь` | кто нажал — по нему работает захват |
| `Создана` | время создания **на часах 1С** |
| `Состояние` | ждёт / принята агентом / отклонена |
| `Ответ` | причина отказа либо подтверждение |

> **Ф2.** Чем это делать в 1С: **регистрами сведений** (независимыми) или **справочниками**?

> удобнее, если на прайсы и задачи понадобится ссылаться из других объектов конфигурации.

## 3. Эндпоинты

Оба — в том же HTTP-сервисе `ai-tools`, рядом с `by-tm` и `set-prices`, с тем же заголовком
`X-API-Token` и той же функцией `ОтветJSON`.

### 3.1. `GET .../agent-commands` — агент забирает команды

Возвращает всё в состоянии «ждёт» и **своё текущее время**:

```json
{ "server_time": "2026-09-14T12:00:03",
  "commands": [
    { "id": 17, "kind": "выполнить задачу", "price_id": 1, "task_id": 5,
      "payload": {}, "actor": "Иванов", "created_at": "2026-09-14T12:00:01" } ] }
```

**`server_time` обязателен.** По нему агент считает расхождение часов и приводит метки к
своим. Порядок «кто первый» решается временем создания на стороне визуала, и сбитые часы
давали бы 1С либо вечный выигрыш, либо вечный проигрыш (§7.1 модели).

**Эндпоинт должен быть лёгким: читает только таблицу команд и Номенклатуру НЕ трогает.**
Замер на боевой базе: чистые накладные HTTP-сервиса — 231 мс, тривиальный запрос с
обращением к Номенклатуре — 1 263 мс. При лёгком эндпоинте пятисекундный опрос стоит 4,6 %
занятости 1С, при тяжёлом — 25,3 %.

### 3.2. `POST .../agent-commands/ack` — агент подтверждает приём

```json
{ "commands": [ { "id": 17, "state": "принята", "message": "" },
                { "id": 18, "state": "отклонена", "message": "прайс занят: Петров" } ] }
```

Приём и подтверждение разделены **намеренно**: между «отдал» и «принял» агент может умереть,
и тогда команда обязана остаться в состоянии «ждёт», а не пропасть.

### 3.3. `POST .../set-model-state` — агент кладёт состояние

**Полный снимок**, а не приращения:

```json
{ "prices": [ { "id": 1, "file": "Прайс Монарх 15.09.2026.xlsx", "supplier": "Монарх",
                "status": "к обработке", "ready": false,
                "has_newer": false, "newer_id": null,
                "locked_by": "Иванов", "locked_until": "2026-09-14T12:10:00",
                "created_at": "2026-09-14T11:33:00",
                "tasks": [ { "id": 5, "kind": "изменение цен", "order": 5,
                             "subject": "коллекция", "address": "Монарх / Vintage",
                             "status": "к обработке",
                             "description": "…", "result": "", "done_at": null } ] } ] }
```

Снимок целиком, потому что он маленький (десятки строк) и **самоисцеляющийся**: потерянное
обновление чинится следующим, тогда как с приращениями расхождение копилось бы молча. 1С
замещает зеркало полностью — прайс, которого в снимке нет, из зеркала удаляется.

## 4. Форма

```
┌─ Прайсы ─────────────────────┐ ┌─ Задачи прайса ───────────────┐
│ №1  Монарх 15.09  к обработке│ │ • 5  Монарх / Vintage         │
│ №2  Most Floor    частично   │ │ ✓ 6  Монарх / Adventure       │
└──────────────────────────────┘ └───────────────────────────────┘
 [Обновить задачи] [Статус ▾]     [Выполнить] [Статус ▾]

┌─ Описание задачи ────────────────────────────────────────────┐
│ Проверить, все ли позиции коллекции заведены в 1С: в прайсе  │
│ 14 артикулов, сверки с номенклатурой у агента не было.       │
└──────────────────────────────────────────────────────────────┘
```

**Поведение:**

- выделили прайс → во втором списке его задачи, **отсортированные по `Порядок`**, и стали
  доступны «Обновить задачи» и выбор статуса прайса;
- выделили задачу → в панели её описание (и результат, если есть), стали доступны «Выполнить»
  и выбор статуса задачи;
- ничего не выделено → кнопки недоступны;
- нажатие **пишет строку в `МодельКоманды` и больше ничего не делает**: состояние изменит
  агент, и оно приедет снимком. Это и есть правило «визуал только шлёт команды» (§1 модели).

**Статус прайса ставит админ, а не модель.** Модель лишь считает готовность (`Готов`):
если бы статус выводился автоматически, одна задача с исходом «частично обработана» запирала
бы прайс навсегда.

**«Обновить задачи» собирает список ЗАНОВО и НИЧЕГО не переносит** — ни статусы, ни правки
описаний. Задача, которую админ решил не делать, вернётся: условие, её породившее, никуда не
делось. Это принятое следствие, а не недосмотр; кнопку стоит подписать так, чтобы это было
видно заранее.

**Задачи устаревшего прайса показываются как обычно.** Модель их не блокирует —
предупреждать дело визуала: строку прайса стоит выделить и показать номер свежего.

## 5. За рамками

- Приём прайса из 1С: файл присылается в Telegram, 1С прайсы не загружает.
- Справочники поставщиков и сигнатур — правятся из Telegram.
- Отдельный канал уведомлений в 1С: его роль играет снимок состояния.
